# KI-Provider (`lib/ai/`)

Gilt zusaetzlich zur Root-[CLAUDE.md](../../CLAUDE.md) und [lib/CLAUDE.md](../CLAUDE.md). Ausfuehrlich: [docs/ai-providers.md](../../docs/ai-providers.md).


Drei Provider, konfiguriert via `API_PROVIDER` in `.env`:

| Provider | Env-Vars | Besonderheit |
|----------|----------|--------------|
| `claude` | `ANTHROPIC_API_KEY`, `MODEL_NAME` | Prompt-Caching (`cache_control: ephemeral`), grosses Kontextfenster |
| `ollama` | `OLLAMA_HOST`, `OLLAMA_MODEL`, `OLLAMA_TEMPERATURE` | Mutex-Serialisierung (VRAM-Schutz), dynamische `num_ctx`-Berechnung |
| `openai-compat` | `OPENAI_COMPAT_HOST`, `OPENAI_COMPAT_MODEL`, `OPENAI_COMPAT_TEMPERATURE`, `OPENAI_COMPAT_API_KEY` | OpenAI-kompatibler `/v1/chat/completions`-Endpoint (llama.cpp, vLLM, LiteLLM, OpenAI); optionaler Bearer-Token (`ai.openai-compat.api_key`), Semaphore-serialisiert (`ai.openai-compat.max_parallel`); Klassen-Schalter `ai.openai-compat.cloud` für gehostete Frontier-Modelle (volle Cloud-Prompts statt Slim-Prompts — SSoT `providerClass` in `lib/ai/config.js`, Details: [docs/ai-providers.md](../../docs/ai-providers.md)) |

**`ai.claude.max_tokens_out`** (App-Setting, Default 0 = aus dem effektiven Modell abgeleitet via `_claudeModelMaxOut`) setzt den globalen Output-Token-Cap (`MAX_TOKENS_OUT` in `lib/ai.js`); die Per-Provider-Pendants `ai.ollama.max_tokens_out` / `ai.openai-compat.max_tokens_out` löst `getContextConfigFor(provider)` pro Call auf. Job-spezifische Overrides werden per `Math.min` gegen den Provider-Cap gedeckelt. `.env`-`MODEL_TOKEN` dient nur als einmaliger Bootstrap in die DB (`env`-Feld des Deskriptors in [lib/app-settings/registry.js](../../lib/app-settings/registry.js)), danach ist der App-Setting-Wert massgeblich.

**`ai.claude.context_window`** (App-Setting, Default 0 = aus dem effektiven Modell abgeleitet via `_claudeModelContext`: moderne Generation 1M, ältere 200K) setzt das gesamte Kontextfenster (Input + Output). Daraus leitet `lib/ai.js` das `INPUT_BUDGET_TOKENS` (= `context_window − max_tokens_out − 2000`) ab. Alle kontextabhängigen Grenzen skalieren automatisch: `SINGLE_PASS_LIMIT`/`PER_CHUNK_LIMIT` (Komplettanalyse), `BOOK_CHAT_TOKEN_BUDGET`-Default, Buch-Chat-Tool-Result-Caps und das Classic-Buch-Chat-Text-Budget. Bei lokalen Modellen auf die native Kontextgrösse setzen (Mistral-Small3.2 / Gemma3 / Llama-3.1: 128 000, ältere: 32 000 / 8 000).

**JSON-Parsing:** `lib/ai.js` hat mehrstufigen Fallback: `JSON.parse()` → `extractBalancedJson()` → `jsonrepair()`.

**KI-Profile (`ai_profiles`) sind die Zuweisungs-Achse pro User.** Ein Profil trägt einen Provider plus beliebig viele Parameter-Überschreibungen und hängt an `app_users.ai_profile_id` (`ON DELETE SET NULL`, Admin: **Einstellungen → Provider → KI-Profile**, Routen `/admin/ai-profiles`). Damit laufen mehrere Modelle desselben Providers nebeneinander — ein lokales llama.cpp und ein gehostetes Frontier-Modell gehen beide über `openai-compat`. `lib/ai.js#resolveProvider({ userEmail })` löst per Call auf (Profil > globaler `ai.provider` > `'claude'`); Job-Pfade resolven am Job-Start einmal in `effectiveProvider`. Details: [docs/ai-providers.md](../../docs/ai-providers.md).
  - **Ein eingeladenes Konto erbt das Profil des Einladenden** — einmal bei der Anlage, in [db/app-users.js](../../db/app-users.js)#`createUser` (gelesen wird der Stand zur **Annahme**-Zeit aus `invited_by`, nicht ein Schnappschuss in `user_invites` — das wäre eine zweite Wahrheit über dieselbe Zuweisung). **Why:** wer einen Mitautor oder Lektor über die Buch-Freigabe hereinholt, holt ihn in den eigenen Betrieb; ohne Vererbung landet er stumm auf dem globalen `ai.provider`, den niemand für ihn gewählt hat. **Kopie, keine Verknüpfung:** ein späterer Profilwechsel des Einladenden zieht den Eingeladenen nicht mit, sonst wechselt sein Modell ohne Anlass. Hat der Einladende kein Profil, bleibt NULL (= globaler Provider). Die Herkunft steht in `app_users.invited_by`/`invited_at`, ist im Admin-Benutzer-Tab sichtbar (`invited_by_name` per JOIN, keine Snapshot-Spalte) und die geerbte Zuweisung landet als `ai-provider-changed` in der Audit-Spur.
  - **Eigener KI-Zugang = Profil mit `owner_email`** (Profil-Seite, `/me/ai-access`, Admin-Freigabe `ai.user_api.enabled`) — schlägt die Zuweisung, ist für den Admin unsichtbar und fällt **nie** auf Host oder Key der Instanz zurück (`aiApiKey`/`aiSetting` in [lib/ai/profile.js](../../lib/ai/profile.js)); sein Host läuft beim Call durch `safeFetch`, und `usesOwnAccess()` schaltet die Instanz-Overrides ab (Job-Bag ausser `timeoutMs`, Tier-Modell). Details: [docs/ai-providers.md](../../docs/ai-providers.md) → „Eigener KI-Zugang".
  - **NULL in einer Profil-Spalte heisst „globaler Wert", nicht „leer".** Aufgelöst wird das an genau einer Stelle: `aiSetting(provider, key, { userEmail })` in [lib/ai/profile.js](../../lib/ai/profile.js) — dort, wo sonst `appSettings.get('ai.<provider>.<key>')` stünde. **Kein neuer Direktzugriff auf einen `ai.<provider>.*`-Key in einem Pfad, der pro User laufen kann.** Das Overlay greift ausschliesslich beim eigenen Provider des Profils, sonst bekäme ein Call gegen einen anderen Provider fremde Modell-Parameter.
  - **Drei Stellen, die ein Profil mitziehen müssen:** `_modelName(provider)` ([routes/jobs/shared/model.js](../../routes/jobs/shared/model.js)) geht in jeden `cacheVersion`-String — der `provider`-Anteil im PRIMARY KEY der Cache-Tabellen trennt zwei Profile desselben Providers ja nicht; die Parallelitäts-Gates in [lib/ai/shared.js](../../lib/ai/shared.js) führen einen Bucket **pro Profil** (und lesen ihre Obergrenze über `aiSettingByProfileKey` gegen den Bucket, nicht gegen den ALS-Context — der Zähler wird im Kontext eines fremden Calls neu ausgewertet); und die Fenster-Kombination (`max_tokens_out + Puffer < context_window`) validiert [routes/admin-ai-profiles.js](../../routes/admin-ai-profiles.js) beim Speichern, weil der Boot-Check nur die globalen Keys kennt.
  - **Provider-Klasse statt Provider-Name für Strategie-Entscheidungen.** `providerClass(provider, opts)` / `effectiveProviderClass(opts)` ([lib/ai/config.js](../../lib/ai/config.js)) ist SSoT; der `cloud`-Schalter ist pro Profil überschreibbar. Daran hängen Prompt-Variante, Lektorat-Kontext + Split, Call-Serialisierung, die **gesamte Komplettanalyse-Strategie** (Extraktions-Split, Single-Pass, Gap-Pässe, Coverage, Judge, Soziogramm-Refine, Attribut-Check, Verify, Remap-Rescue, Buchtext-Preprocessing) und Kontinuität/Erzählprofil **auf allen drei Schichten**: `/config`-Gate, Karten-Gate (`requiresCloudModel` in [feature-registry.js](../../public/js/cards/feature-registry.js), gelesen aus `$store.config.effectiveProviderClass`) und Route-Guard (`400 CONTINUITY_PROVIDER_UNSUPPORTED` / `NARRATIVE_PROFILE_PROVIDER_UNSUPPORTED`). **Die drei müssen dieselbe Frage stellen** — ein Klassen-Gate im `/config` neben einem Namens-Guard an der Route heisst: Karte sichtbar, Knopf antwortet 400. Am Provider-**Namen** (`=== 'claude'`) bleibt nur, was eine Anthropic-API-Fähigkeit braucht: Prompt-Caching inkl. Warmup, Recherche-Chat (er braucht das `web_search`-Server-Tool, nicht bloss irgendein Tool-Protokoll), Tiered Routing, `phase1_concurrency`, `web_search`-Faktencheck (`FACTCHECK_CLAUDE_ONLY` bleibt darum ein Namens-Gate). **Tool-Use ist eine dritte Achse: eine Fähigkeitsfrage, weder Name noch Klasse** — SSoT `providerSupportsTools(provider)` ([lib/ai/config.js](../../lib/ai/config.js)), können es `claude` (native `tool_use`-Blöcke) und `openai-compat` (Function-Calling, Schalter `ai.openai-compat.tools`). **Dispatch und Pfadwahl müssen dieselbe Funktion fragen** (`lib/ai/core.js` und [book-chat.js](../../routes/jobs/chat/book-chat.js)#`_bookChatUseAgent`), sonst wählt der Job den agentischen Pfad und der erste Call wirft. Der Loop ([routes/jobs/agentic-chat.js](../../routes/jobs/agentic-chat.js)) bleibt provider-neutral: er spricht ausschliesslich die kanonische Anthropic-Form, jeder Provider übersetzt selbst ([lib/ai/tool-translate.js](../../lib/ai/tool-translate.js)) — kein zweites Message-Format im Loop. Ein Endpunkt, der Werkzeuge ablehnt, kostet keine Antwort: `AI_TOOLS_UNSUPPORTED` schaltet auf `config.fallbackJob` (klassischer Buch-Chat) statt den Job zu verlieren. **Die Job-seitigen Klassen-Gates lesen den EFFEKTIVEN Provider**, nicht `ai.provider` — sonst führt der Mischbetrieb genau in die Irre, gegen die die Zwei-Instanzen-Prompt-Schicht gebaut wurde.
  - **Per-Job-Konfiguration läuft über EINEN provider-skopierten ALS-Bag.** `setContext({ aiJob: { provider, model, contextWindow, maxTokensOut, timeoutMs, effort } })`, gelesen ausschliesslich über `jobOverride(provider, field)` ([lib/ai/config.js](../../lib/ai/config.js)). Gesetzt von `_komplettAiOverrides` ([routes/jobs/komplett/job-shared.js](../../routes/jobs/komplett/job-shared.js), Keys `ai.<provider>.{model,context_window,max_tokens_out,timeout_ms}.komplett` für **claude UND openai-compat**), `_bookChatClaudeOverrides` ([routes/jobs/chat/book-chat.js](../../routes/jobs/chat/book-chat.js), claude-only, weil der Tool-Loop es ist) und `applyLektoratAiOverrides` ([routes/jobs/lektorat-split.js](../../routes/jobs/lektorat-split.js), claude-only: `model` aus `ai.claude.model.lektorat`, `effort` nur, wenn das so gewählte Modell adaptiv denkt) und `applySynonymAiOverrides` ([routes/jobs/synonyme.js](../../routes/jobs/synonyme.js), dasselbe Muster mit `ai.claude.{model,effort}.synonym`). **Der `provider` im Bag ist Teil des Vertrags, kein Beiwerk**: `jobOverride` liefert nur, wenn der Anfrager derselbe Provider ist — sonst bekäme ein Call gegen einen anderen Provider fremde Modell-Parameter (dieselbe Falle, gegen die das Profil-Overlay in [lib/ai/profile.js](../../lib/ai/profile.js) abgesichert ist). Präzedenz: per-Call-Tier > Job-Bag > Profil > Instanz-Setting. **Ohne Komplett-Override fährt die Analyse mit dem Alltags-Fenster** — für ein 1M-Zeichen-Buch auf `openai-compat` ist das der Unterschied zwischen Single-Pass und einem Chunk-Sturm.
  - **Ein entfernter Endpunkt braucht Timeout und Retry-Ladder, egal welcher.** Beide Mechaniken liegen einmal in [lib/ai/shared.js](../../lib/ai/shared.js) (`combineSignals`/`timeoutError`/`withOverloadRetry`/`parseRetryAfter`/`retryDelayMs`/`overloadError`) und werden von Claude **und** openai-compat benutzt, der Timeout auch von Ollama (`ai.ollama.timeout_ms`); der Timeout gilt für fetch **und** jedes `reader.read()` im Stream. Ein Fehler-Chunk im Stream (`{"error":…}`) wirft mit der Server-Meldung; provider-eigen bleibt nur, **welche** Antwort transient ist (Anthropic 429/529 + `overloaded_error` im Body, OpenAI-kompatibel 408/429/5xx). Wiederholt wird nur, was **vor** dem ersten Delta scheitert — ein mitten im Stream abgerissener Call hat bereits Text emittiert; den fängt `retryOnTransientAi` in [routes/jobs/shared/ai.js](../../routes/jobs/shared/ai.js) ab. `state.timedOut` trennt Timeout von User-Abbruch (beides kommt als `AbortError` an) und ist die Voraussetzung dafür, dass ein hängender Endpunkt als `AI_TIMEOUT` retrybar wird statt als „vom User abgebrochen" zu verschwinden.
  - Cache-Tabellen haben weiterhin `provider` im PRIMARY KEY (verhindert Cross-Provider-Bleeding).
