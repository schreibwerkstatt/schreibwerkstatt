# Share-Link (Seite/Kapitel/Buch public teilen)

Opaker Token pro Seite, Kapitel **oder** ganzem Buch. Reader sehen Read-Only-View ohne Login, können (optional) kommentieren — **allgemein** am Seitenende **oder verankert** an einer markierten Textstelle (Beta-Leser-Feedback). Verankerte + allgemeine Kommentare bilden **Threads**, auf die Reader und Owner antworten (bidirektional). „Owner" eines Links ist sein **Ersteller** (`share_links.owner_email`) — nicht zwingend der Owner des Buchs; wer was sieht und widerrufen darf, steht unter [Sichtbarkeit + Lebensdauer](#sichtbarkeit--lebensdauer). Der Ersteller sieht seine Links in der „Geteilte Links"-Karte (Unread-Tracking); die Kommentare selbst (verankert **und** allgemein) liest und bearbeitet er in der Kommentar-Leiste der jeweiligen Editor-Ansicht — „Kommentare anzeigen" wechselt dorthin (Seiten-Share → Notebook-Leseansicht, Buch-/Kapitel-Share → Bucheditor).

## Architektur in einem Bild

```
Browser (anon)       → GET  /share/:token          → SSR-HTML
Browser (anon)       → GET  /share/:token/threads   → JSON (Threads, no-store)
Browser (anon)       → POST /share/:token/comment   → Redirect 303 oder JSON (+ optional Anker/parent_id)
Browser (anon)       → PATCH/DELETE /share/:token/comment/:id → JSON (eigenen Kommentar erledigt/löschen, via reader_token)
Browser (anon)       → POST /share/:token/tts        → Audio-Bytes (Vorlesen, token-skopiert, Ratenlimit + Inhaltsbindung, no-store)
Browser (anon)       → POST /share/:token/view-duration → 204 (Beacon: Verweildauer)
Browser (anon)       → POST /share/:token/read-depth  → 204 (Beacon: Gesamt- + pro-Kapitel-Lesetiefe)
Browser (anon)       → POST /share/:token/feedback    → JSON (Gesamt-Fazit: Sterne + Freitext, UPSERT pro reader_token)
Browser (anon)       → GET  /share/:token/feedback/mine → JSON (eigenes Fazit, Prefill)
Browser (anon)       → GET/POST /share/:token/review[/claim|/done] → JSON (Review-Link: Reviewer-Wahl, Abschluss)
Browser (auth Owner) → /share/api/links*            → JSON-CRUD (+ POST .../comments Reply, PATCH .../comments/:id/resolve)
Browser (auth Owner) → /share/api/links/:token/read-depth → JSON (Kapitel-Drop-off)
Browser (auth Owner) → /share/api/links/:token/feedback   → JSON (alle Fazits)
Browser (auth Owner) → /share/api/book-comments/:id  → JSON (alle Threads des Buchs; Kommentar-Leiste der Leseansicht)
```

Public (ohne Session) sind ausschliesslich die Reader-Routen unter `/share/:token…` ([routes/share/reader.js](../routes/share/reader.js): Leseansicht, Abschnitts-Bilder, Kommentar, Threads, Reader-Name; [routes/share/reader-stats.js](../routes/share/reader-stats.js): Fazit, Lesetiefe/-dauer; [routes/share/tts.js](../routes/share/tts.js): TTS); jede prüft Token-Gültigkeit über `isExpired`. Mount-Reihenfolge in [server.js](../server.js): Share-Router **vor** dem Session-Guard montiert; Owner-Calls unter `/share/api/` prüfen die Session selbst und bekommen wie jeder Nicht-Navigations-Request 401-JSON ([lib/auth-guard.js](../lib/auth-guard.js)). Reihenfolge nicht durcheinanderbringen, sonst landet der Reader im Login.

## Datenmodell (Migration 145)

Fünf Tabellen, alle via FK ans bestehende Schema gehängt:

- **`share_links`** — Token-PK, `kind IN ('page','chapter','book')` (`'book'` ab Migration 213), FKs auf `books`/`pages`/`chapters`/`app_users` (alle `ON DELETE CASCADE`), `intro` (Plaintext, max 2000 Zeichen), `expires_at`/`revoked_at`/`view_count`/`owner_last_seen_at`, `show_toc` (0|1, ab Migration 215 — optionales Inhaltsverzeichnis im Reader, nur bei `kind != 'page'` wirksam), `show_promo` (0|1, Default 1, ab Migration 370 — App-Hinweis im Reader, siehe [App-Hinweis](#app-hinweis-show_promo)). CHECK erzwingt je nach `kind` genau das passende Ref-Set (Sentinel-frei): `page` → `page_id` gesetzt, `chapter` → `chapter_id` gesetzt, `book` → **beide** NULL (Buch via `book_id`).
- **`share_views`** (Migration 237) — Zugriffs-Log der Leseansicht, **dedupliziert pro Besucher**: ruft derselbe Besucher (`share_token` + `ip_hash`) die Ansicht binnen `VIEW_DEDUPE_MS` (30 min) erneut auf, gibt `recordShareView` die bestehende `view_id` zurück (Beacons mergen per `MAX`) und legt keine neue Zeile an — sonst schriebe jeder Reload oder ein Skript in der Schleife unbegrenzt Zeilen in die öffentlich erreichbare Tabelle. `view_count` auf `share_links` zählt dagegen **jeden** gezählten Aufruf. **Nicht gezählt** (weder `view_count` noch `share_views`, kein `viewId` → keine Beacons): Link-Vorschauen und Crawler (`isPreviewBot` in [lib/share-helpers.js](../lib/share-helpers.js), User-Agent-Muster; ohne User-Agent gilt als Skript) und der **Ersteller selbst**, wenn er im selben Browser angemeldet ist (`sessionEmail(req) === owner_email`) — sie bekommen die Seite trotzdem. `share_token` FK auf `share_links(token)` CASCADE, `ip_hash` (SHA-256 mit Server-Salt, 16 Hex-Slice — gleiche Logik wie `share_comments`, GDPR: kein Klartext-IP; Basis für eindeutige Besucher via `COUNT(DISTINCT ip_hash)`), `duration_ms` (Lesedauer, nullable — vom Reader per `sendBeacon` nachgetragen, `MAX`-Merge bei mehreren Beacons), `viewed_at`. `view_count` bleibt der schnelle Gesamtzähler; `share_views` liefert die feinere Statistik (eindeutige Besucher + Ø-Lesedauer). Kein Retention-Cron — Zeilen bleiben bis der Link (CASCADE) gelöscht wird. **Migration 238** ergänzt hier `max_scroll_pct` (Gesamt-Lesetiefe 0-100, Beacon, `MAX`-Merge).
- **`share_view_sections`** (Migration 238) — pro Aufruf + Kapitel die erreichte Lesetiefe (`depth_pct` 0-100, `MAX`-Merge). `view_id` FK auf `share_views(id)` CASCADE, `chapter_id` FK auf `chapters(chapter_id)` CASCADE (echter FK, kein Snapshot — Kapitelname kommt per JOIN), `UNIQUE(view_id, chapter_id)`. Basis für den **Kapitel-Drop-off** des Autors (`readDepthByToken`: pro Kapitel Ø-Tiefe + Anzahl erreichter Aufrufe, sortiert nach `chapters.position`). Der Reader meldet die Tiefe pro Kapitel per Beacon ([read-depth.js](../public/js/share-reader/read-depth.js)); Kapitelgrenzen = aufeinanderfolgende Kapitel-Überschriften (Buch-Shares; Kapitel-Shares tracken nur die Gesamt-Tiefe).
- **`share_feedback`** (Migration 238) — Gesamt-Fazit eines Lesers: `rating` (1-5) + optionaler `body` (max 4000). `share_token` FK CASCADE, `reader_token` (Self-Key), `UNIQUE(share_token, reader_token)` → **UPSERT** (erneutes Absenden aktualisiert das eigene Fazit). `reader_name`/`ip_hash` nullable. Owner-Aggregat `avg_rating`/`feedback_count` in den List-Queries; Volltext-Liste via `/share/api/links/:token/feedback`.
- **Review (Migration 372):** `share_links.mode` (`leser` | `review`, CHECK), `share_comments.suggestion_text`/`suggestion_state` (`open` | `accepted` | `rejected`)/`suggestion_decided_at`, Tabelle **`share_link_reviewers`** (`share_token` FK CASCADE, `name` UNIQUE je Link ohne Gross/Klein, `position`, `reader_token` = beanspruchender Browser, `done_at`/`done_note`). Siehe [Review-Modus](#review-modus).
- **`share_comments`** — `share_token` FK auf `share_links(token)` CASCADE, `reader_name` (optional, max 80), `body` (max 4000), `ip_hash` (SHA-256 mit Server-Salt, 16 Hex-Slice — GDPR: kein Klartext-IP). **Threading + Anker (Migration 200):** `parent_id` (Self-FK CASCADE, NULL=Root, sonst Reply — Threads eine Ebene tief, Replies erben den Anker des Roots), `anchor_bid`/`anchor_quote`/`anchor_start`/`anchor_end` (verankert an einem Block via `data-bid`, NULL=allgemeine Anmerkung), `author_email` (FK app_users SET NULL — gesetzt bei Owner-Antwort; Identitäts-Quelle ist im Code exklusiv: entweder `author_email` ODER `reader_*`), `resolved_at` (Owner-Resolve, nur Root), `reader_token` (opaker Per-Browser-Token aus localStorage für Self-Erkennung — Basis für Reader-Self-Service: eigene Kommentare erledigt-markieren/löschen). Index auf `parent_id` + `author_email`.

## Verankerung an `data-bid`

Jede verankerte Anmerkung haftet an einem Block via dessen stabiler `data-bid`-ID ([lib/html-clean.js](../lib/html-clean.js)#ensureBlockIds, bereits im persistierten Page-HTML) + dem markierten Quote-Text. Der Inhalt ist **live** (Autor editiert weiter), darum ist der Quote der Robustheits-Anker: beim Rendern wird re-verankert (Block per `data-bid` finden → `anchor_quote` darin suchen, Offsets nur als Hinweis). Findet sich der Quote nicht mehr (Block gelöscht/Text geändert), bleibt der Thread gelistet, aber **ohne** Inline-Highlight (Markierung „Stelle geändert") — nie wird die falsche Stelle markiert.

## Threads (Reader + Owner)

- **Public-Endpunkte:** `GET /share/:token/threads?rt=<reader_token>` (no-store, JSON, serverseitig leser-sicher serialisiert — nie `author_email`/`reader_token`/`ip_hash`; `mine` gegen `rt` berechnet). `POST /share/:token/view-duration` (Beacon, `{viewId, durationMs}`, immer `204` — Verweildauer nachtragen, `viewId` stammt aus `#share-config`, serverseitig auf 6 h geklemmt, `MAX`-Merge). `POST /share/:token/comment` nimmt zusätzlich optional `parent_id`, `anchor_bid`/`anchor_quote`/`anchor_start`/`anchor_end`, `reader_token` (alle defensiv validiert: bid-Regex, Offset-Ints, Reply nur auf Root **dieses** Tokens).
- **Reader-Self-Service (eigene Kommentare):** `PATCH /share/:token/comment/:id/resolve` `{ reader_token, resolved }` markiert einen **eigenen** Root-Thread als erledigt / öffnet ihn wieder (teilt sich `resolved_at` mit dem Owner-Resolve), `DELETE /share/:token/comment/:id` `{ reader_token }` löscht einen **eigenen** Beitrag. Self-Identität ausschliesslich über `reader_token` + `author_email IS NULL` (kein Auth) — nie wird ein Owner-/Fremd-Beitrag getroffen. **Hart-Löschen nur ohne Antworten:** hat der Autor geantwortet, liefert die Route `409 HAS_REPLIES` (sonst risse die CASCADE die Owner-Antwort still mit); die Bedingung steht im DELETE selbst (`NOT EXISTS`, atomar), damit auch eine Antwort, die zwischen Prüfen und Löschen ankommt, nicht mitgerissen wird — das Frontend blendet den Lösch-Button dann aus und bietet nur „Erledigt" an.
- **Owner-API:** `POST /share/api/links/:token/comments` `{ parent_id, body }` (Owner-Antwort, `author_email`=Session), `PATCH /share/api/comments/:id/resolve` `{ resolved }` (Root als erledigt markieren/öffnen). Beide prüfen zusätzlich die Buchrolle des Erstellers (siehe [Sicherheits-Invarianten](#sicherheits-invarianten)).
- **Reader-Frontend** ([public/js/share-reader.js](../public/js/share-reader.js)): Selektion im Artikel → schwebender „Kommentieren"-Button → Composer; Inline-Highlights via **CSS Custom Highlight API** (`::highlight(share-anchor)`, kein DOM-Eingriff am Content → kein neuer XSS-Sink); Klick auf Highlight (caret-Mapping) fokussiert den Thread; Reader-Identität (`reader_token` + Name) in localStorage. Selbstständige Widgets unter `share-reader/`: **layout** (vertikale Verankerung der Karten, Google-Docs-Modell — teilt die pure Kollisions-Mathematik [public/js/comment-card-layout.js](../public/js/comment-card-layout.js) mit den zwei SPA-Leisten) + **composer** (Selektions-Button + Anmerkungs-Overlay; reicht die Markierung über mehrere Blöcke, wird nur der Teil im ersten verankert und der Composer sagt das) + **thread-render** (Thread-Karten, Antwort-Box, eigene Aktionen) + **sheet** (Mobile-Bottom-Sheet) + **api** (Public-Endpunkte) neben dom/identity/menu/theme/toc/progress. Composer, Namens-Modal und Sheet sind modale Dialoge (`role="dialog"`, `aria-modal`, Tab-Fang, Fokus-Rückgabe — `makeModal` in `share-reader/dom.js`); Strg/Cmd+Enter sendet in jedem Kommentar-Feld. Schreibfehler übersetzt eine Stelle (`errorText` in [share-reader/api.js](../public/js/share-reader/api.js)) für alle Formulare: Ratenlimit, ungültige Mail, Antworten vorhanden, Link nicht mehr aktiv, sonst allgemein. Der Composer verwirft beim Schliessen (Esc, Abbrechen, Klick daneben) den getippten Text nicht: derselbe Anker bzw. die allgemeine Anmerkung bekommt ihn beim nächsten Öffnen zurück, erst erfolgreiches Senden löscht ihn. Kommentar-Köpfe tragen einen Initialen-Pip (deterministische Hue pro Person) aus der pure SSoT [public/js/avatar.js](../public/js/avatar.js) — gleiche Person → gleiche Pip-Farbe in Reader und SPA (Presence-Pips + Kommentar-Leisten).
- **Zwei Kommentar-Zonen (Google-Docs-Modell).** **Verankerte** Anmerkungen schweben rechts als Margin-Rail (`.share-comments`) auf der **Höhe ihrer Textstelle** — Pendant zur Bucheditor-Leiste, hier standalone ohne Alpine. Die Positionierungs-Ebene ist `.share-comments__list`; pro Karte ein Marker-Tick (`.share-thread-marker`, echte Anker-Höhe vor Kollision). Layout-Logik ([public/js/share-reader/layout.js](../public/js/share-reader/layout.js)): Artikel + Spalte teilen den Fenster-Scroll und beginnen in derselben Grid-Zeile → Abstand „Textstelle → Spalten-Oberkante" scroll-invariant, Layout nur bei Render/Resize/Auswahl (Doppel-rAF, ResizeObserver auf Artikel + Karten), Kollisions-Auflösung greedy top-down mit Pin der aktiven Karte. Unter 1100px (Flach-Modus) fällt die Spalte auf eine statische Stapel-Liste unter dem Artikel zurück (`--comment-top`/`--marker-top` werden gelöscht, CSS stapelt; Überschrift `.share-comments__heading` nur dort sichtbar). Ein Tipp auf eine Markierung öffnet den Thread im Flach-Modus als **Bottom-Sheet** über der Lesestelle ([sheet.js](../public/js/share-reader/sheet.js)) statt ans Listenende zu scrollen — bei einem Buch-Share läge die Liste sonst hinter dem ganzen Buch. Ohne verankerte Anmerkungen ist die Leiste in **jeder** Breite ausgeblendet; der Hinweis „Markiere oben eine Textstelle …" steht dann unter der Überschrift der allgemeinen Kommentare. **Antwort-Box auf Abruf:** jede offene Karte trägt nur einen „Antworten"-Knopf, die Box klappt erst darauf auf (hält die schwebenden Karten kurz); offene Boxen und Entwürfe überleben das Re-Render. Klick auf eine verankerte Karte wählt sie aus (Highlight + Pin). Eigene Aktionen (Erledigt/Bearbeiten/Löschen) blenden auf Hover-Geräten erst bei Hover/Auswahl/Fokus ein, auf Touch immer sichtbar. **Allgemeine** (nicht verankerte) Kommentare leben in einer abgesetzten Sektion **ganz unten** (`.share-general`) mit **eigenem Formular** für neue allgemeine Anmerkungen (das klassische SSR-`<form>`, progressive Enhancement). Beide Zonen rendern volle Threads (Reply/Resolve/Delete). **Name zentral statt pro Formular** (`setupIdentity()`): beim **ersten Absenden** eines Beitrags (Composer, Antwort, allgemeine Form, Fazit — `ensureIdentity()` in [identity.js](../public/js/share-reader/identity.js)) öffnet ein Namens-Modal („Dein Name" + optionale Mail); reine Leser sehen es nie. „Speichern" und „Anonym bleiben" senden danach ab (Anonym merkt sich den Verzicht pro Tab-Session via `sessionStorage`), Esc/Klick daneben bricht das Absenden ab und lässt den Beitrag im Formular. Die Mail wird mit derselben Regel wie serverseitig (`READER_EMAIL_RE`) geprüft, eine ungültige wird nicht gespeichert (Fehler im Modal); eine früher gespeicherte ungültige gilt als nicht gesetzt — sonst scheiterte jeder Beitrag an `INVALID_EMAIL`, danach steht ein Identitäts-Chip oben rechts bei den Optionen (in den `#share-theme`-Cluster injiziert): „Als <Name> · Ändern" bzw. „Name setzen". Composer, Reply-Form **und** SSR-Form haben **kein** eigenes Namensfeld mehr — sie kommentieren mit `savedName()` (sonst anonym); Thread-Antworten tragen den Namen damit ebenfalls. SSR ohne JS: behält das beschriftete `reader_name`-Feld (JS entfernt es); die allgemeinen Threads samt Antworten rendert [lib/share-comments-ssr.js](../lib/share-comments-ssr.js) im **selben Karten-Markup und derselben Reihenfolge** wie der Client (Avatar + Gruppierung über die ESM-Bridge, Zeit als `<time>` in `app.timezone`) — die Hydration tauscht die Liste ohne Sprung aus. **Live-Poll (Reader-Seite):** `share-reader.js` pollt `GET /share/:token/threads` alle 10 s still — so erscheinen **Autor-Antworten ohne Reload**. `fetchThreads()` rendert nur bei echter Thread-Änderung (Signatur aus id/parent/resolved/`edited_at`/Name/body-Länge → kein Scroll-Reset bei jedem Tick, aber Bearbeitungen und Namenswechsel anderer Leser erscheinen); der Tick pausiert, solange der Leser interagiert (Composer offen, Text markiert, Eingabefeld fokussiert, halb getippter Beitrag) oder der Tab im Hintergrund ist (`document.hidden`). Gegenstück zum Owner-Poll, aber Reader-Richtung. Antwortet `/threads` mit 410/404 (Link seither widerrufen, abgelaufen oder gelöscht), stellt der Reader das Pollen ein, zeigt über dem Text den Hinweis `share.reader.link_gone` und blendet die Kommentier-Bedienelemente aus (`body.share-link-gone`); der geladene Text bleibt lesbar. **„Neue Antwort"-Badge:** fremde Antworten, deren ID dieser Browser noch nicht gesehen hat (localStorage `sw_share_seen_<token>`); beim **ersten** Besuch eines Links gilt alles Vorhandene als gesehen, sonst trüge jeder beantwortete Thread das Badge.
- **Owner-Karte:** listet **nur** die Links (Status, bei fremden Links „Angelegt von …", Ziel, View-Counts inkl. **eindeutige Besucher** + **Ø-Lesedauer** + **Ø-Lesetiefe** aus `share_views`, **Ø-Sternewertung** aus `share_feedback`, Comment-Counts, Unread-Badge) — **keine** Kommentar-Anzeige mehr in der Karte. Ein **Statistik-Toggle** pro Link klappt on-demand den **Kapitel-Drop-off** (Balken pro Kapitel aus `/read-depth`) + die **Gesamt-Fazits** (Sterne + Freitext aus `/feedback`) auf ([share-links-card.js](../public/js/cards/share-links-card.js#toggleStats)). „Kommentare anzeigen" (`showCommentsForLink`) markiert den Link als gesehen (`mark_seen=1`, Unread sofort 0) und **wechselt in die passende Editor-Ansicht**: **Seiten-Share → Notebook-Leseansicht** der Seite (`gotoPageById` + Event `comments-rail:goto`), **Buch-/Kapitel-Share → Bucheditor** (`toggleBookEditorCard` + Event `book-editor:goto-comment`). Beide Events tragen `{ token }` des Links: die Leiste geht auf, der Triage-Filter springt auf «Alle», und der geteilte Kern öffnet den ersten **offenen** verankerten Thread dieses Links in Dokument-Reihenfolge (sonst den ersten überhaupt) samt Sprung zur Stelle (`pendingGotoToken`). Dort liegen Threads, Reply, Resolve/Reopen und Delete — für verankerte **und** allgemeine Kommentare. Unread-Query zählt nur Reader-Kommentare (`author_email IS NULL`) neuer als `owner_last_seen_at` — eigene Antworten sind nie „neu".
- **Live-Poll:** Solange die Karte sichtbar ist, pollt sie alle 5 s still (`_quietRefresh`, kein Loading-Flicker): aktualisiert `view_count`/`unique_views`/`avg_duration_ms`/`comment_count`/`unread_count` aller Links in-place (kein vollständiger `x-for`-Reflow, solange das Token-Set gleich bleibt). So erscheinen neue Reviewer-Kommentare — egal ob über Buch-, Kapitel- oder Seiten-Share — binnen ~5 s als Unread-Badge beim Owner. Timer via `timerKeys: ['_pollTimer']` im Card-Lifecycle (Auto-Cleanup bei `book:changed`/`view:reset`/`destroy`); zusätzlich stoppt ein `$watch` auf `showShareLinksCard` den Poll beim Ausblenden, und `document.hidden` überspringt Polls im Hintergrund-Tab.
- **Per-Kommentar-Sprung in der Leiste:** Klick auf einen verankerten Thread in einer der beiden Editor-Leisten hebt die Stelle via `::highlight(comment-rail-anchor-active)` (Notebook) bzw. `::highlight(book-editor-comment-anchor-active)` (Bucheditor) hervor und scrollt hin. Die Re-Anchor-Logik (`locateRange`/`resolveCurrentQuote`) liegt als SSoT in [public/js/share-anchor.js](../public/js/share-anchor.js) und wird von Reader, Notebook-Leiste und Bucheditor-Leiste geteilt. Drei geteilte SSoT-Module tragen alle drei Kommentar-Oberflächen (Share-Reader, Notebook-Leseansicht, Bucheditor): **Re-Anchoring** [share-anchor.js](../public/js/share-anchor.js), **Kollisions-Geometrie** der schwebenden Karten (pure, Node-testbar) [comment-card-layout.js](../public/js/comment-card-layout.js) und **Avatar-Pips** [avatar.js](../public/js/avatar.js). Die beiden SPA-Leisten (Notebook + Bucheditor) teilen zusätzlich den Verhaltens-Kern [comment-rail-core.js](../public/js/editor/comment-rail-core.js) (Laden/Threads/Reply/Resolve/Delete/Triage-Filter) **und** die Layout-DOM-Glue [comment-rail-layout.js](../public/js/editor/comment-rail-layout.js); der Share-Reader hat seine eigene Vanilla-Glue ([share-reader/layout.js](../public/js/share-reader/layout.js)), nutzt aber dieselbe pure Geometrie.

### Live-Aktualisierung der Owner-Oberflächen

Jede Änderung an Share-Link-Kommentaren (Leser im Share-Reader: anlegen, bearbeiten, erledigen, löschen, Namenswechsel; Owner: antworten, erledigen, löschen, Vorschlag entscheiden) meldet `emitBookMeta(bookId, 'comments')`; Mechanik, Echo-Regel und Kosten: [live-sync.md](live-sync.md). Der Empfänger lädt die Abschnitts-Zähler offener Reviewer-Kommentare neu und dispatcht `EVT.SHARE_COMMENTS_CHANGED`, auf das **Notebook-Leseansicht** und **Bucheditor** ihre Leiste neu laden; die Kommentare selbst kommen weiter ACL-geprüft aus `/book-comments`. Der Share-Reader pollt selbst (10 s, Leser-Richtung).

### Kommentar-Leiste im Bucheditor

Der Bucheditor ([book-editor.md](book-editor.md)) zeigt Leser-Kommentare des **ganzen Buchs** als rechte Margin-Rail (dritte Layout-Spalte: Outline | Stream | Kommentare). Pendant zur Notebook-Read-Modus-Leiste, aber Scope = ganzer `.book-editor-stream` statt Einzelseite. Verhalten kommt aus dem geteilten Kern [public/js/editor/comment-rail-core.js](../public/js/editor/comment-rail-core.js) (SSoT mit der Notebook-Leiste; `createCommentRail(cfg)`); die vertikale Verankerung aus dem ebenfalls geteilten [public/js/editor/comment-rail-layout.js](../public/js/editor/comment-rail-layout.js) (`createCommentLayout(cfg)`, DOM-Glue um die pure `comment-card-layout.js`). [public/js/editor/book-editor-comments.js](../public/js/editor/book-editor-comments.js) liefert nur die Bucheditor-Glue (Scope, Highlight-Namen, Stream-Ready-Check) + spreadet beide Bündel und wird in `bookEditorCard` gespreadet. **Verankerte** Threads (mit „Stelle geändert"-Diff) **und** ein darunter abgesetzter Abschnitt mit **allgemeinen** (nicht-verankerten) Kommentaren — hier aller Link-Scopes des Buchs (`generalFilter: () => true`). Owner-Reply/Resolve/Delete identisch zur Notebook-Leiste; Daten aus `/share/api/book-comments/:book_id` (Zeilen tragen zusätzlich `link_kind`/`link_page_id`). Kein Eingriff in die Notebook-Leiste. **Live:** siehe [Live-Aktualisierung](#live-aktualisierung-der-owner-oberflächen).

**Kopf + Zähler (beide SPA-Leisten).** Die Leiste trägt einen Kopf (Anzahl der sichtbaren Threads, ×-Schliessen). Knopf und Badge in der Kopfzeile zählen **ungefiltert** (`totalCount`/`openCount` aus dem Kern): der Knopf steht, sobald es Threads gibt, das Badge zeigt die **offenen** — ein Triage-Filter ohne Treffer nimmt weder Knopf noch Leiste weg.

**Platz im Editor-Pane (`commentPaneMode`).** Massgeblich ist die Pane-Breite, nicht der Viewport ([book-editor-comments.js](../public/js/editor/book-editor-comments.js)#`paneMode`, vor jedem Layout-Pass und beim Öffnen): passt `Outline | Stream | Leiste` mit mindestens `STREAM_MIN` (480px) Textspalte, bleibt es dreispaltig (`full`); sonst weicht die Outline, solange die Leiste offen ist (`no-outline` — die Präferenz `outlineOpen` bleibt unberührt, `outlineShown()` ist die wirksame Sichtbarkeit); reicht auch das nicht, steht die Leiste als Liste unter dem Stream (`flat`, Klasse `book-editor-layout--comments-flat`). Holt der User die gewichene Outline per Knopf zurück (`_outlineForced`), rückt stattdessen die Leiste unter den Text. Unter 800px Viewport ist sie immer flach. Der Stream nimmt seine Breite aus der Spalte (`width: 100%`), nie aus dem Inhalt — mit `content-visibility: auto` meldet eine übersprungene Zeile sonst ihre alte Breite, und der Stream liefe unter die Leiste.

**Vertikale Verankerung (Google-Docs-Modell, `comment-rail-layout.js` + pure `comment-card-layout.js`).** Statt einer simplen sortierten Liste schwebt jede verankerte Karte auf der **Höhe ihrer Textstelle** und scrollt mit dem Stream mit. Verankerte Threads liegen absolut positioniert (`--comment-top`) in einer Positionierungs-Ebene `.book-editor-comments__layer` innerhalb der Spalte; ein Marker-Tick im linken Spaltenrand zeigt zusätzlich die **echte** Anker-Höhe (`--marker-top`, vor Kollision). Da Stream und Spalte denselben Scroll-Container teilen und in derselben Grid-Zeile beginnen, ist der Abstand „Textstelle → Spalten-Oberkante" scroll-invariant → Layout wird nur bei Render/Resize/Edit/Auswahl neu gerechnet (`_layoutCommentCards`, Doppel-rAF), **nicht** pro Scroll. Kollisions-Auflösung: greedy top-down mit `CARD_GAP`; bei Auswahl wird die aktive Karte auf ihre exakte Anker-Höhe **gepinnt** und die übrigen darum herum verteilt. Höhenänderungen (async „Stelle geändert"-Diff, aufgeklappte Reply-Form, Stream-Reflow) triggern via gemeinsamem `ResizeObserver` (Stream + alle Karten) ein Re-Layout; loop-sicher, weil das Layout nur `top` setzt. **Pflicht-Invariante:** Karten/Anker-Geometrie nie im reaktiven State halten (Range-Objekte brechen als Alpine-Proxy) — Anker-Y pro Pass frisch via `locateRange` lokalisieren; nur die numerischen `_anchorY`/`_railTop` landen reaktiv auf den Thread-Objekten. Im Flach-Modus (`commentPaneMode === 'flat'`) fällt die Spalte auf eine statische Stapel-Liste zurück, das JS überspringt das Layout (`isFlat`). CSS in [public/css/editor/book/book-editor.css](../public/css/editor/book/book-editor.css).

Schreib-/Lesepfad: ausschliesslich [db/share-links.js](../db/share-links.js). Reader-Content kommt über die **Content-Store-Facade** ([lib/content-store/](../lib/content-store/)), nicht direkt aus SQL. **Buch-Share** (`kind='book'`) rendert das ganze Buch in Lesereihenfolge über [lib/load-contents.js](../lib/load-contents.js) (`scope:'book'`): Kapitel-Überschrift + Seiten-Blöcke, inkl. Sub-Kapiteln mit eigener Überschrift in ihrer Tiefe (`.ms-chapter--d1/--d2`, Verzeichnis-Ebenen `share-toc__item--l1`…`l4`); ein Kapitel ohne eigenen Abschnitt, dessen Unterkapitel Text tragen, steht als reine Überschrift vor ihnen. **Kapitel-Share** (`kind='chapter'`) ist das Kapitel als **ganzer Teilbaum**: `loadContents({ scope:'chapter', includeSubchapters:true })` wie der Kapitel-Export (ausgeschlossene Unterkapitel fallen raus). Dieselbe Kapitelmenge (`chapterShareIds` in [lib/share-helpers.js](../lib/share-helpers.js), SSoT `chapterScopeIds` in load-contents) gilt für den Bild-Scope der Leseansicht (`/:token/page-image/:id`), den `data-bid`-Backfill und den Link-Zähler `/api/page-link-counts`. Das Stream-HTML baut der **geteilte Renderer** [public/js/manuscript-render.js](../public/js/manuscript-render.js) (`renderStreamHtml(fromGroups(groups))`) — serverseitig per dynamic `import()` geladen (Muster wie [lib/prompts-loader.js](../lib/prompts-loader.js)), dieselbe SSoT wie Bucheditor + Fassungen-Reader. Markup: neutrale `.ms-chapter`/`.ms-page`/`.ms-page__title`/`.ms-page__body`-Klassen ([public/css/components/manuscript-stream.css](../public/css/components/manuscript-stream.css), Token-Brücke `--ms-*`→`--share-*` in `share.css`). **Block-Typografie des Seiteninhalts** (Listen, Checkbox-Listen `ul.todo`, Bilder/Figuren, Tabellen, Trenner inkl. `hr.pagebreak`/`hr.blankpage`, Code, Gedichte `div.poem`, Callouts) kommt aus der geteilten SSoT [public/css/components/manuscript-content.css](../public/css/components/manuscript-content.css) — derselbe Regelsatz, den Notebook-Leseansicht und Bucheditor benutzen, über die Brücke `--mc-*`→`--share-*`; was der Notebook-Editor schreiben kann, muss der Reader zeigen können. `.share-content` (share/content.css) trägt nur noch die Reader-Abweichungen: px-Überschriftenskala, Prosa-Absatzmodell, Szenentrenner-Asterismus (der die Seitenumbruch-Marker ausnimmt, sonst wären sie nicht mehr von einem Szenenwechsel unterscheidbar). **Escaping-Invariante:** Namen `escHtml`, `pd.html` verbatim (bereits html-clean-sanitisiert, trägt `data-bid`). Kapitel-Share nutzt `omitChapterId` (nur die Überschrift des geteilten Kapitels entfällt — sein Name steht im Seiten-Header; Unterkapitel behalten ihre, alles rückt eine Verzeichnis-Ebene hoch), Seiten als `h2`. **Gleichnamiger erster Abschnitt:** heisst der erste Abschnitt eines Kapitels wie das Kapitel (`sameStructureTitle`, [public/js/structure-title.js](../public/js/structure-title.js) — dieselbe Regel wie PDF/Word), entfällt seine Überschrift samt TOC-Eintrag; der Text bleibt. Beiträge mit Schlagzeile (`article`) behalten ihren Kopf. Typischer Fall: Romane mit einem Abschnitt pro Kapitel. Owner-Trigger: Quick-Action in der Buch-Übersicht (`openShareLinksForBook`) + `'Ganzes Buch'`-Option im Create-Form der Karte. `locate` für verankerte Kommentare durchsucht bei `kind='book'` alle Buch-Seiten.

## Review-Modus

Ein Link mit `mode = 'review'` ist für Kollegen, die gegenlesen — ohne Konto, über denselben Reader. Was ihn vom Leser-Link unterscheidet:

- **Reviewer: vorgegeben oder selbst eingetragen.** Der Ersteller kann Namen vorgeben (`tagInput` in der Owner-Karte, `PUT /share/api/links/:token/reviewers`) — oder die Liste leer lassen, wenn er den Link frei teilt (Team-Chat): wer ihn öffnet, trägt sich selbst ein. Deckel für beide zusammen: 30 × 80 Zeichen (`REVIEWERS_MAX`; der Link ist öffentlich, Selbsteintragen darf die Liste nicht beliebig füllen → `409 REVIEWERS_FULL`). Im Reader ersetzt ein Wähler den freien Namens-Dialog ([share-reader/review.js](../public/js/share-reader/review.js) über `identity.js#setNameModalOpener`, auch vor dem ersten Beitrag; `ensureIdentity` wartet auf dessen Ladestand): Namen der Liste als Knöpfe (von einem anderen Browser gewählte tragen «vergeben»), darunter das Feld zum Selbst-Eintragen. `POST /share/:token/review/claim` nimmt `reviewer_id` (Name der Liste) oder `name` (selbst eintragen; gleicher Name ohne Gross-/Kleinschreibung beansprucht den bestehenden Reviewer, [db/share-review.js](../db/share-review.js)#`claimReviewerByName`) und bindet ihn an das `reader_token` des Browsers. **Ein Browser = ein Reviewer**, ein zweiter Browser darf den Namen übernehmen (Laptop → Telefon) — ohne Anmeldung gibt es keinen besseren Beweis, und unter Kollegen ist das gewollt. Der Server kommentiert danach unter **genau diesem Namen** (eingehender `reader_name` wird überschrieben) und benennt frühere Kommentare des Browsers um (`renameReaderComments`) — daran hängen Reviewer-Filter der Owner-Leisten und der Abschluss-Stand.
- **«Review abschliessen»** statt Sterne-Fazit (Slot `#share-feedback`, `feedback.js` tritt zurück): `POST /share/:token/review/done` mit optionaler Schlussnotiz (in der Owner-Karte als eigene Zeile, nicht nur Tooltip), wieder öffnen möglich. Ohne beanspruchten Namen `409 REVIEWER_NOT_CLAIMED`.
- **Kein App-Hinweis** (`buildPromo` bekommt `show_promo: 0`), Ratenlimit der Kommentare gilt auch für Anspruch und Abschluss.
- **Stand** (`reviewState`: Reviewer mit Abschluss, offene Root-Kommentare der Leser, offene Vorschläge, `complete`) steht an jeder Review-Zeile von `GET /share/api/links` und unter `GET /share/api/links/:token/review`. Die Owner-Karte zeigt ihn ([partials/share-links-review.html](../public/partials/share-links-review.html)) und bietet bei `complete` in redaktionellen Büchern «Als gegengelesen markieren» an ([bearbeitungsstand.md](bearbeitungsstand.md#oberflächen)) — nie automatisch.

### Änderungsvorschläge

Nur im Review-Modus und nur **verankert**: im Composer schaltet der Leser zwischen «Kommentar» und «Änderung vorschlagen» ([share-reader/composer.js](../public/js/share-reader/composer.js)); das Feld ist mit der markierten Stelle vorbelegt, die Begründung (`body`) wird optional. Der Server nimmt `suggestion` nur mit Anker an (`SUGGESTION_NEEDS_ANCHOR`), nicht unverändert (`SUGGESTION_UNCHANGED`), und setzt `suggestion_state = 'open'`. Reader und beide Owner-Leisten zeigen ihn gleich: das Anker-Zitat bleibt die normale Sprung-Zeile, darunter `.comment-suggestion` mit dem **Wort-Diff** Stelle → Vorschlag (`.comment-suggestion__diff`) und dem Entscheid ([components/comment-rail.css](../public/css/components/comment-rail.css), Marken aus [components/diff-marks.css](../public/css/components/diff-marks.css)). Der Diff ist auf die **geänderten Sätze** gekürzt ([diff/suggestion-diff.js](../public/js/diff/suggestion-diff.js)#`suggestionDiffParts`): Satzgrenzen zählen nur im unveränderten Text, unveränderte Sätze davor, dazwischen und danach werden zu «…». Ein **umgeschriebener** Satz (mehr als ein Drittel seiner Wörter geändert, mindestens drei) steht wie ein Lektorat-Befund als Ganzes alt → neu statt als Wortsalat — dieselbe Regel wie in allen Diff-Ansichten im Lesefluss ([diff/sentence-diff.js](../public/js/diff/sentence-diff.js)). **Why:** markiert wird oft ein ganzer Absatz, geändert ein Wort — voller Alt- und Neutext versteckten die Änderung. Ist der Text zu gross für den Wort-Diff, steht der neue Text ungemarkert als Einfügung.

Der Leser kann seinen **offenen** Vorschlag bearbeiten (`PATCH /share/:token/comment/:id` mit `suggestion`; Begründung darf dann leer sein, nach dem Entscheid `409 SUGGESTION_DECIDED`), aber nicht selbst erledigen (`409 SUGGESTION_OPEN`, im Reader fehlt «Erledigt» dort): ein erledigter, unentschiedener Vorschlag verschwände aus den Markierungen der Owner-Leisten und hielte `complete` für immer auf falsch. Nach dem Entscheid gilt wieder der normale Leser-Self-Service.

**Übernehmen** gibt es nur auf den Owner-Oberflächen (Notebook-Leseansicht **und** Bucheditor, Knöpfe im geteilten Fragment [comment-thread-body.html](../public/partials/comment-thread-body.html), Ablauf im geteilten Kern [comment-rail-core.js](../public/js/editor/comment-rail-core.js)#`_railDecideSuggestion`):

1. Abschnitt bestimmen (Glue `suggestionTarget`: Notebook = offene Seite; Bucheditor = Block, dessen HTML die `data-bid` trägt — hat er ungespeicherte Änderungen, einen laufenden Save oder Konflikt, wartet das Übernehmen mit Hinweis statt zu überschreiben).
2. Frisch laden, im **verankerten Block** ersetzen ([comment-suggestion.js](../public/js/editor/comment-suggestion.js)#`applySuggestionToHtml`): genau ein Treffer im Block, sonst Abbruch mit Grund (`blockGone`, `quoteGone`, `ambiguous`, `blocked` bei Quellen-Chip/Querverweis in der Stelle) — der Autor übernimmt dann von Hand. Fehlt die Stelle, steht aber der Ersatztext genau einmal im Block (`alreadyApplied`: von Hand übernommen oder ein früherer Versuch speicherte, ohne den Status zu setzen), wird nichts gespeichert, nur der Status gesetzt. Eingesetzt wird Klartext (`replaceInHtml`), nie Markup aus dem öffentlichen Reader.
3. Speichern mit `expected_updated_at` (409 → Hinweis, kein Blind-Retry), Revisions-Quelle `review` (Revisionsliste: «Review»; Whitelist in `editor/shared/save-pipeline.js` und `db/page-revisions.js`, gegated durch [review-revision-source.test.mjs](../tests/unit/review-revision-source.test.mjs)).
4. Der Glue zeigt den neuen Stand (Notebook: `_refetchCurrentPage`; Bucheditor: Block neu schreiben wie bei „Fremde Fassung übernehmen" — aktiver Block wird vorher deaktiviert, der Undo-Verlauf des Abschnitts fällt; hat der User während Laden/Speichern im Block getippt, bleibt seine Eingabe stehen und sein nächster Save landet im Konflikt-Dialog).
5. Erst danach `PATCH /share/api/comments/:id/suggestion { state: 'accepted' }` — ein gescheiterter Save steht nie als «übernommen» da. Scheitert nur dieser PATCH, meldet die Leiste das eigens (`statusFailed`); ein erneutes «Übernehmen» trifft dann `alreadyApplied`. `accepted` erledigt den Thread mit.

**Ablehnen** (`rejected`) lässt den Thread offen — der Owner antwortet meist, warum; «Zurücknehmen» setzt `open`. Warum der Server nicht selbst ersetzt: die tolerante Textsuche ([utils/html-find.js](../public/js/utils/html-find.js)) braucht den Browser-Parser für Entities, und beide Editoren müssen den neuen Stand ohnehin selbst nachziehen.

## Token

22 Zeichen base64url aus `crypto.randomBytes(16)` (~128 bit). UNIQUE-Constraint + 3x Retry bei Kollision. Regex-Vorvalidierung in der Reader-Route: `^[A-Za-z0-9_-]{16,32}$`.

Reader-Form benutzt **klassischen `<form method="POST">` mit 303-Redirect-Fallback** + progressive Enhancement via [public/js/share-reader.js](../public/js/share-reader.js) (fetch + inline Status). Darum verteilt der POST-Handler je nach `Content-Type` (`application/json` → JSON-Response, sonst → Redirect mit `?cmt=ok|rate|empty|long|err|gone`). Heisst: View funktioniert auch ohne JS.

Sprache wird per `Accept-Language` erkannt (DE Default, EN-Prefix → EN). Server-i18n via [lib/i18n-server.js](../lib/i18n-server.js); Owner-User-Setting ist explizit **nicht** massgeblich (Reader hat kein Konto).

## Rate-Limit + Spam-Schutz

POST-Comment hat **zwei** Schichten:

1. **Honeypot** `_hp`-Input (hidden via CSS, `tabindex="-1"`) — gesetzt → 400, geloggt mit Token-Prefix.
2. **In-Memory-Bucket** in [lib/share-ratelimit.js](../lib/share-ratelimit.js): Default 30 Kommentare pro `(token, ip_hash)` pro 60 min (App-Settings `share.comment.rate_limit_max`/`share.comment.rate_limit_window_min`; grosszügig, da Beta-Leser viele Inline-Anmerkungen pro Sitzung hinterlassen). Process-Restart resettet — bewusst, kein Cluster-Setup. IP-Hash: SHA-256 mit `SHARE_IP_SALT` + 16-Hex-Slice; ohne Env-Wert zufällig pro Prozess, dann gilt derselbe Leser nach jedem Neustart als neuer Besucher — auf Prod gesetzt, siehe [deployment.md](deployment.md). Bei Hit setzt der Handler `Retry-After`-Header. Alle Bucket-Sätze (`makeLimiter`) räumen abgelaufene Schlüssel alle `SWEEP_EVERY` Aufrufe weg.

**Leseansicht** (`GET /share/:token`) hat einen eigenen Bucket (`checkView`: 120 Aufrufe pro Minute pro Link + IP-Hash → `429` + `Retry-After`): jeder Aufruf rendert den ganzen geteilten Inhalt neu, bei einem Buch-Share das ganze Buch. Der `data-bid`-Nachzug (`backfillScopeBlockIds`) liest die Abschnittstexte nur, wenn sich der Seitenbestand des Links seit dem letzten Lauf geändert hat (Signatur aus Seiten-IDs + `updated_at`, In-Memory pro Token).

**Gesamt-Fazit** (`POST /share/:token/feedback`) läuft durch denselben Bucket-Mechanismus mit eigenem Schlüssel (`feedback:<token>`, gleiches Limit) → `429 RATE_LIMITED` + `Retry-After`. Grund: `reader_token` wählt der Client, ohne Drossel wäre jeder neue Token ein neuer UPSERT-Schlüssel. Vorlesen (`/tts`) hat einen eigenen, höheren Bucket (`checkTts`, siehe [tts.md](tts.md)).

`db/share-links.js#countRecentCommentsByTokenIp` ist als DB-Pendant da, wird aktuell nicht eingesetzt — für künftige Cluster-Persistenz vorbereitet.

### Sichtbarkeit + Lebensdauer

- **Wer sieht welche Links** (`GET /share/api/links?book_id=…`, Buch-Guard `viewer`): der **Buch-Owner** bekommt **alle** Links des Buchs (`listSharesForBook`, auch die anderer Mitarbeiter), alle anderen nur die selbst angelegten (`listSharesByOwnerAndBook`). Jede Zeile trägt `mine` (selbst angelegt) und `creator_access` (Ersteller hat noch die nötige Buchrolle, `creatorLostAccess`) sowie `owner_display_name`. Die Karte zeigt an fremden Zeilen „Angelegt von {name}" (`share.list.createdBy`); Bearbeiten, Kommentare und Statistik bleiben beim Ersteller (`mine !== false`).
- **Widerrufen** (`DELETE /share/api/links/:token`): den eigenen Link darf der Ersteller immer widerrufen (auch ohne Buchrolle — Widerrufen gibt nichts preis); einen fremden nur der Buch-Owner (`revokeShareLinkOnBook`, an `book_id` gebunden). Alle anderen bekommen `404`, damit der Token kein Existenz-Orakel ist.
- **Ein Link lebt nur, solange sein Ersteller die Anlege-Rolle hat** (`SHARE_CREATE_MIN_ROLE = 'editor'`, [db/share-links.js](../db/share-links.js)). Zwei Schichten:
  - **Beim Rollenwechsel** in [routes/book-access.js](../routes/book-access.js)#`_revokeSharesIfBelowShareRole` — Zugriff entziehen (`DELETE …/access/:email`), herabstufen (`PUT …/access/:email`) und erneut teilen mit niedrigerer Rolle (`POST …/share`) widerrufen in derselben Transaktion alle aktiven Links des Betroffenen auf diesem Buch (`revokeSharesByOwnerOnBook`).
  - **Zur Lesezeit** in [lib/share-helpers.js](../lib/share-helpers.js)#`isExpired`: `creatorLostAccess(link)` (Rolle unter `SHARE_CREATE_MIN_ROLE` oder Rollen-Lookup schlägt fehl) gilt als `'revoked'`. Das hält Alt-Links und jeden anderen Weg ab, auf dem eine `book_access`-Zeile verschwindet; alle Public-Endpunkte (Reader, Threads, Kommentare, Fazit, Bilder, TTS) laufen durch `isExpired`. Die Karte zeigt solche Links als widerrufen (`creator_access === false`).
- **Abschnitt in ein anderes Buch verschieben** ([lib/content-store/backends/localdb-move.js](../lib/content-store/backends/localdb-move.js)#`_revokeForeignShareLinks`, in der `movePage`-Transaktion): Seiten-Links, deren Ersteller im Zielbuch nicht mindestens `SHARE_CREATE_MIN_ROLE` hat, werden widerrufen; die übrigen ziehen mit (`share_links.book_id` = Zielbuch).

Unread-Tracking: `share_links.owner_last_seen_at` (eine Spalte, kein Bridge — pro Link gibt es genau einen Ersteller). Beim GET `/share/api/links/:token/comments?mark_seen=1` wird der Timestamp gesetzt. Owner-List-Queries liefern `comment_count` + `unread_count` als Sub-Selects mit.

**Pro-Seite-Zähler offener Reviewer-Kommentare** (`GET /share/api/page-comment-counts?book_id=…`, `db/share-links.js#openReaderCommentsForBook`): Map `pageId → Anzahl` offener Root-Reader-Kommentare (`parent_id IS NULL`, `author_email IS NULL`, `resolved_at IS NULL`) über **alle** Links des Buchs. Page-Shares attribuieren direkt via `link.page_id`; Chapter-/Book-Shares lösen verankerte Kommentare via `anchor_bid` über einen einmaligen Block-Scan der Buch-Seiten (Content-Store) der Seite zu (nur wenn überhaupt verankerte Kommentare vorliegen) — nicht-verankerte Kommentare zählen nicht (keiner Seite zuordenbar). Frontend: buchweit in [tree.js](../public/js/book/tree.js) (`shareCommentCounts`) geladen, `currentPageShareCommentCount` speist den `.btn-count`-Badge am „Teilen"-Eintrag des Page-Action-Menüs ([editor-notebook.html](../public/partials/editor-notebook.html)). `refreshShareCommentCounts()` (app-view) hält die Map nach Resolve/Delete in der Owner-Karte frisch.

### Kommentar-Leiste in der Leseansicht

Beim Lesen einer Buchseite (Notebook-Editor, **Read-Modus**) erscheinen Leser-Kommentare als Margin-Rail rechts neben dem Text (Google-Docs-Stil). Eigenständige, datengetriebene Sub-Karte — **keine** exklusive/Palette-Karte: sie blendet sich allein ein, sobald die offene Seite Kommentare hat.

- **Daten:** `GET /share/api/book-comments/:book_id` (`db/share-links.js#listCommentsByOwnerBook`) liefert alle vollen Threads (Root + Antworten, inkl. `resolved_at`/`author_*`/`anchor_*` + `link_kind`/`link_page_id`) über alle Links des Owners zum Buch; jede Zeile trägt `share_token`. Optional `?mark_seen=1` → `markOwnerSeenForBook`.
- **Frontend:** [public/js/cards/editor-comments-card.js](../public/js/cards/editor-comments-card.js) (State) + [public/js/editor/comments-rail.js](../public/js/editor/comments-rail.js) (Glue) über den geteilten Verhaltens-Kern [public/js/editor/comment-rail-core.js](../public/js/editor/comment-rail-core.js) + pure [public/js/editor/comment-threads.js](../public/js/editor/comment-threads.js) (`groupThreads`, unit-getestet). Partial [public/partials/editor-comments.html](../public/partials/editor-comments.html), CSS [public/css/editor/notebook/comments-rail.css](../public/css/editor/notebook/comments-rail.css). Pro Buch einmal geladen. **Verankerte** Kommentare via `locateRange` ([share-anchor.js](../public/js/share-anchor.js)) auf die gerenderte `.page-content-view` gefiltert; sie **stapeln** in Dokument-Reihenfolge in `.comment-rail__layer` — anders als im Bucheditor keine vertikale Verankerung, weil das Blatt ein eigener Scroll-Container ist (`comment-rail-layout.js` wird hier nicht genutzt). **Allgemeine** (nicht-verankerte) Kommentare landen in einer abgesetzten, zentrierten Bande **ganz unten** unter dem Seitentext (`.comment-rail--general`) — hier nur die des **Page-Shares genau dieser Seite** (`generalFilter`: `link_kind==='page' && link_page_id===currentPage.id`; Buch-/Kapitel-Share-Allgemeines hat keine eindeutige Seite und lebt im Bucheditor).
- **Auswahl:** Klick auf einen Thread (Kommentar oder Antwort) hebt die Textstelle hervor (`::highlight(comment-rail-anchor-active)`; alle Stellen dezent via `comment-rail-anchor`) und scrollt das Blatt hin; der Thread klappt Aktionen + Antwort-Box auf. Gegenrichtung: Klick auf eine markierte Stelle im Seitentext wählt ihren Thread und scrollt die Leiste zu ihm (`onTextCommentClick`, wie im Bucheditor). **Voll interaktiv** (antworten/erledigt/löschen) über die bestehenden Owner-Endpoints (Token aus `comment.share_token`).
- **Stelle seither geändert (Kommentar-Diff):** Hat der Autor den verankerten Text seit dem Kommentar geändert, findet `locateRange` keinen Range mehr. `resolveCurrentQuote(view, anchor)` ([share-anchor.js](../public/js/share-anchor.js)) trennt dann „andere Seite" (`gone` → übersprungen) von „Stelle geändert" (`changed` → Block via `data-bid` da, Quote weg). Solche Threads bleiben in der Leiste mit Badge `share.comments.textChanged` + einem Inline-Diff `anchor_quote` (damals) → aktueller Block-Text (jetzt), gerendert mit dem geteilten `renderInline` ([page-revision-diff.js](../public/js/page-revision-diff.js), `diffLib` lazy via `loadDiff`). Quote ist serverseitig auf 600 Zeichen gekappt → der Diff ist quote-scoped. Die beiden SPA-Leisten diffen gegen `quoteWindow(blockText, anchor)` ([share-anchor.js](../public/js/share-anchor.js)): den Ausschnitt, der dem Zitat heute entspricht (überlebender Kern wie bei `locateApprox`, sonst die alten Offsets), auf Wortgrenzen erweitert und mit „…" an abgeschnittenen Rändern. Owner-only; der öffentliche Reader behält seinen Text-Hinweis.
- **Layout:** Grid-Split `.editor-body-wrap.comments-split` (Text | Rail), gesteuert über das Root-Flag `pageCommentRailOpen`, das die Karte spiegelt. Ab 1100px ist die Rail eine eigene Scroll-Spalte auf Blatthöhe (`--pcv-max-h`); liegen unterhalb weitere Karten, blendet ihre Unterkante aus (`.has-more-below`, gesetzt aus `@scroll` und `x-resize` der Kartenliste). Darunter stapelt die Leiste unter dem Text, allgemeine Bande darunter. Im Edit-Modus und während des Lektorat-Splits (`checkDone`) ist die Leiste ausgeblendet. Toggle-Knopf in den Seiten-Actions: sichtbar ab einem Thread der Seite (`pageCommentTotal`, ungefiltert), Badge = offene (`pageCommentCount`). Die Leiste steht, sobald die Seite Threads hat — auch wenn nur allgemeine da sind oder der Filter nichts trifft, sie trägt die Filter für beide. Seitenwechsel klappt sie zu und setzt den Triage-Filter zurück.
- **Triage-Filter (geteilt mit Bucheditor):** Status (alle/offen/erledigt, `commentFilterStatus`) + Reviewer-Combobox (`commentFilterReviewer`, gespeist aus den distinct Leser-Namen via `_railReviewerNames`). Filter im geteilten Kern (`_railSetFilter` → Recompute); ein Filter, der den selektierten Thread ausblendet, deselektiert ihn. Das Markup (Segment, Reviewer-Combobox, Leer-Hinweis) steht einmal im Fragment [public/partials/comment-rail-filters.html](../public/partials/comment-rail-filters.html), eingebunden in beide Owner-Leisten — nicht im Share-Reader. i18n `share.comments.filter.*`.
- **Avatar-Pips (geteilt):** jeder Kommentar-Kopf trägt einen Initialen-Pip mit deterministischer Hue pro Person (`commentAvatar` → [avatar.js](../public/js/avatar.js)); Leser leiten Initialen/Hue aus dem Anzeigenamen ab, Owner-Antworten aus `author_display_name`/`author_email`. Gleiche Person → gleiche Farbe in Reader, Notebook- und Bucheditor-Leiste sowie den Presence-Pips.

## Sicherheits-Invarianten

- **Ersteller-Check + Buch-ACL**: Routen auf einem einzelnen Link oder Kommentar filtern via `link.owner_email === sessionEmail(req)` (fremd/unbekannt → `404`) **und** prüfen danach die Buchrolle des Erstellers per [lib/acl.js](../lib/acl.js)#`guardBook` — sonst behielte ein Ersteller nach Entzug des Buchzugriffs über seine Links Zugriff auf Kommentare und Statistik. Helfer in [routes/share/api.js](../routes/share/api.js): `ownLink(req, res, minRole)` (Lesen: Kommentare/Read-Depth/Fazit/Locate → `viewer`; Ändern/Antworten → `SHARE_CREATE_MIN_ROLE`) und `guardComment` (Resolve/Delete per Kommentar-ID → `SHARE_CREATE_MIN_ROLE`). Buch-skopierte Routen (`/api/links?book_id`, `/api/page-comment-counts`, `/api/page-link-counts`, `/api/book-comments/:book_id`) laufen durch `guardBook(…, 'viewer')`; Anlegen (`POST /share/api/links`) verlangt `SHARE_CREATE_MIN_ROLE`. Einzige Ausnahme ist der Widerruf (siehe [Sichtbarkeit + Lebensdauer](#sichtbarkeit--lebensdauer)).
- **CSRF bewusst aus**: Reader-Comment-POST kommt explizit cross-origin (Link auf WhatsApp/Mail → fremde Domain → eigene Domain). Kein State-Change auf Owner-Account, Body steht sowieso im UI — Risiko akzeptiert.
- **XSS**: Page-HTML aus DB ist bereits via html-clean sanitisiert; alles andere durchläuft `escHtml`. Owner-Karte rendert Kommentar-Body via Alpine-Text-Bindung, **keinen** `x-html`-Sink.
- **GDPR**: nur IP-Hash gespeichert. Reader-Name optional, vor Render Server-Side escaped.
- **Nie im Suchindex**: [routes/share.js](../routes/share.js) setzt `X-Robots-Tag: noindex, nofollow, noarchive` per Router-Middleware auf **jede** Antwort unter `/share` — nicht nur auf die Reader-View. Die Meta-Tags in [share.html](../public/share.html)/[share.gone.html](../public/share.gone.html) bleiben als zweite Schicht, decken aber nur den HTML-Weg ab; Bild-Stream, JSON und 404 haben keinen `<head>`. **Der Header ist der Garant, nicht die robots.txt** — und `/share` steht dort bewusst *nicht* auf `Disallow` ([routes/public.js](../routes/public.js)): ein Disallow verbietet das Abrufen und damit auch das Lesen des Headers, ein von aussen verlinkter Token käme dann als reiner URL-Eintrag ohne Inhalt trotzdem in den Index. Sperren heisst hier: crawlen lassen und `noindex` ausliefern. Gegated: [seo-robots.test.js](../tests/unit/seo-robots.test.js).

## Cache-Headers

Reader-Response setzt `Cache-Control: no-store` — Content ist live (Autor editiert weiter, ein Reload zeigt garantiert den neuesten Stand; neue Threads/Antworten holt zusätzlich der 10-s-Live-Poll, siehe „Threads"). Service-Worker-`SHELL_CACHE` precachet `/share` (Standalone-Shell) und `/js/share-reader.js`. Abschnitts-Bilder (`/:token/page-image/:id`) gehen mit `Cache-Control: private, max-age=3600` raus — kein geteilter Cache (Proxy/CDN) hält sie über einen Widerruf hinaus.

## Erweiterungs-Hinweise

- **Cluster/Mehrprozess-Setup**: Rate-Limit auf DB umstellen (Helper steht in `db/share-links.js`).
- **Page-Range statt ganzem Kapitel**: ein Kapitel-Share umfasst immer den ganzen Teilbaum des Kapitels; einen Ausschnitt daraus gibt es nicht.
- **Mail-Notification** bei neuem Kommentar: implementiert via `notify.maybeNotifyShareComment` (Template `share-comment-owner`, [lib/mailer-templates.js](../lib/mailer-templates.js)). Owner-Mail, gedrosselt pro Link (ein Throttle-Fenster — eine Lese-Sitzung mit vielen Inline-Anmerkungen löst nicht eine Mail-Flut aus), Opt-out via `mail.notify.owner_on_share_comment === false` (Default an). Owner-eigene Antworten lösen nichts aus.
- **Snapshot-Modus** (Inhalt zum Share-Zeitpunkt einfrieren) wäre eigene Spalte `frozen_html`/`frozen_at` plus Toggle bei Create — aktuell live.
