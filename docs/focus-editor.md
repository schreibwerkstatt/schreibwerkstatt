# Focus-Editor

Vollbild-Schreibmodus **für eine Seite** mit Absatz-/Satz-Spotlight, Typewriter-Scroll und Live-Word-/Char-Counter. Einer von drei unabhängigen Editoren der App; die anderen beiden sind der [Notebook-Editor](notebook-editor.md) (klassischer Einzelseiten-Edit-Modus, auf dem der Focus-Editor als Vollbild-Aufsatz läuft) und der [Bucheditor](book-editor.md) (eigenständige Karte mit Manuskript-Stream über das ganze Buch). Bei Änderungswünschen muss der User immer nennen, welcher Editor gemeint ist (Harte Regel in [CLAUDE.md](../CLAUDE.md)).

Heilige Kuh: jede Änderung an diesem Modul muss dieses Dokument konsultieren. Drift in den Invarianten = sichtbares „Flattern", verlorene Edits oder Phantom-Revisionen im Storage-Backend.

**Stale-Write-Konflikt:** Der Focus-Editor läuft auf der Notebook-Save-Pipeline (`saveEdit`/`quickSave` mit `source: 'focus'`) und erbt damit den **Block-Level-Merge** — kollisionsfreie Block-Edits zweier Geräte mergen still, echte Block-Kollisionen öffnen das Auflösungs-Modal. Details + Invarianten in [notebook-editor.md → Block-Level-Merge](notebook-editor.md#block-level-merge-bei-stale-write).

Code: [public/js/editor/focus.js](../public/js/editor/focus.js) (Facade) → [public/js/editor/focus/](../public/js/editor/focus/) (Submodule), [public/js/cards/editor-focus-card.js](../public/js/cards/editor-focus-card.js) (Alpine.data-Sub), [public/css/editor/focus/focus-mode.css](../public/css/editor/focus/focus-mode.css). Tests: vollständige Liste in der [Tests-Tabelle](#tests) unten (8 Unit-, 5 E2E- und 1 App-Suite-Datei) — `npm run test:focus` fährt davon nur `focus-editor.spec.js` + `focus-editor-app.spec.js`.

Trigger: Hotkey `Cmd/Ctrl+Shift+E` (überall im Editor; aus Lesemodus → startet Edit + Fokus in einem). Body-Listener in [public/index.html](../public/index.html) routet via `handleFocusHotkey`. Verlassen: **Escape oder derselbe Hotkey — beide speichern** (Invariante 16).

Tastengriffe **innerhalb** des Fokusmodus ([listeners.js](../public/js/editor/focus/listeners.js)#`onKey`) — die Liste ist vollständig, ein neuer Griff gehört hierher:

| Griff | Wirkung |
|---|---|
| `Escape` | Speichern + verlassen. Vorrang: laufende Composition (IME, Tote Taste — `e.isComposing`, Escape bricht dort nur die Eingabe ab), offene Popover (Synonym-Menü/-Picker → nur blocken, Figur-Lookup → schliessen), laufender Save → Exit vormerken (Invariante 16) |

## Root vs. Sub: Trampoline-Pattern

Root hält **sichtbare** Flags + Anzeigewerte, Sub hält **Lifecycle-State**. Trennung, weil Templates/CSS/andere Subs nur die Flag brauchen — Listener-Setup, Generation-Counter und RAF gehören zur Card-Lifecycle.

| Wohnt im Root (`focusState` + `shellState`) | Wohnt in Sub (`editorFocusCard`) |
|---|---|
| `focusActive` (bool, Template-Guard, body-class) | `_focusState` (`idle`/`entering`/`active`/`exiting`) |
| `focusGranularity` (`paragraph`/`sentence`/`window-3`/`typewriter-only`) | `_focusGen` (Re-Entry-Guard für async Nachzügler) |
| `focusCountWords` / `focusCountChars` (Live-Anzeige) | `_focusListeners` (ctx mit AbortController, Timer, Pointer-Flag, IO/MO, `visibleBlocks`, `progScrollTop`, `_marks`, …) |
| `focusCountWordsDelta` / `focusCountCharsDelta` (Tages-Delta) | `_focusRaf` (cancellable RAF-Handle für Recenter) |
| `contentLocale` (Sprache des Textes → Satz-Segmentierung) | `_focusAutoAddedP` (Auto-`<p>`-Slot — Referenz auf Exit-Cleanup) |
|  | `_restoreSnapshot` (Reload-Wiederaufnahme) |

Dirty-/Saving-Zustand hat **kein** Fokus-Pendant: der Focus-Editor läuft auf der Notebook-Save-Pipeline und liest/schreibt `editDirty`/`editSaving` aus `notebookState`. Die IO-getrackten Block-Refs leben ausschliesslich im ctx (`_focusListeners.visibleBlocks`) — ein zweites Feld auf der Karte wäre eine Referenz auf dasselbe Set, die beim Teardown getrennt genullt werden müsste.

Root-Methoden ([editor/focus/trampoline.js](../public/js/editor/focus/trampoline.js)) sind **reine Event-Dispatcher** — sie feuern `editor:focus:{toggle|enter|exit|start-edit}` aufs Window. Sub abonniert in `init()` mit `AbortController`-Signal. Root-Spread (`focusMethods`) bleibt minimal, damit Hot-Reload/HMR keine doppelten Listener anhängt.

## State-Machine

```
idle ──enterFocusMode──▶ entering ──$nextTick──▶ active ──exitFocusMode──▶ exiting ──await save──▶ idle
                            │                       │                          │
                            └───install fails───▶ idle                         └── Re-Entry blockt (Generation-Check)
```

- **Re-Entry-Guard:** Jeder `enter`/`exit`-Aufruf erhöht `_focusGen`. Async-Nachzügler (RAFs, `await quickSave`) prüfen `gen !== this._focusGen` → no-op. Schneller exit→enter→exit-Cycle hinterlässt keinen Geisterstand.
- **Doppel-Trigger im `entering`/`exiting`:** `toggleFocusMode` ignoriert beide Übergänge — kein Double-Enter, kein Halt-im-Halbgang.
- **`enterFocusMode` Pflicht-Sequenz** ([card.js](../public/js/editor/focus/card.js)): `_flushDraftSaveNow` → `focusActive=true` + body-class → `$nextTick` → `_focusInstall` → `_focusUpdateActive(true)` → `writeFocusSnapshot`. Fehler im Install → `_focusTeardown` + Snapshot-clear + Flag zurück, State zurück auf `idle`.
- **`exitFocusMode` Pflicht-Sequenz** ([card.js](../public/js/editor/focus/card.js)): Auto-`<p>` abräumen → `await quickSave` (wenn dirty) → `_focusTeardown` → Snapshot-clear → `mirrorToNormal` → body-classes weg → `--focus-vh*` zurück → restliche `.focus-paragraph-*`-Klassen + Custom-Highlight aufräumen → wenn clean: `editMode=false` + Autosave/Counter/OnlineRetry abreissen → `_syncPageStatsAfterSave` + `updatePageView` (idempotent zu Save-Pfad). Reihenfolge ist Pflicht: Cleanup VOR `editMode=false`, sonst rufen Autosave-Teardown auf bereits genullten Refs.
- **Der Exit hat ein `finally`-Sicherheitsnetz** (Invariante 15). Ohne es sperrt ein geworfener Cleanup-Schritt den Editor bis zum Reload.

## Granularitäten

`focusGranularity` lebt im Root (`shellState`) und ist **live umschaltbar** ohne exit/enter. Der `$watch` der SPA-Karte ([editor-focus-card.js](../public/js/cards/editor-focus-card.js)) ist nur der Alpine-Trigger; die Umschaltung selbst macht `applyFocusGranularity` ([card.js](../public/js/editor/focus/card.js)) → `applyGranularity` ([chrome.js](../public/js/editor/focus/chrome.js)) + Re-Render. Fremde Schalen gehen über denselben Weg (`standalone.js#setGranularity`).

| Wert | Was passiert |
|---|---|
| `paragraph` (default) | Aktiver Block hell, alle anderen via `:not(.focus-paragraph-active)` opacity 0.5 |
| `sentence` | Plus: aktiver Satz im aktiven Block hell, restliche Sätze via `::highlight(focus-sentence-dim)` (CSS Custom Highlight, kein DOM-Diff). **Teurer Pfad** — Range-Iteration via TreeWalker; nur bei Block/Granularity-Wechsel oder bei `sentence`-Live-Update. Segmentiert in der Sprache aus `contentLocale` (editor-host-Vertrag) — `Intl.Segmenter` kennt pro Sprache eigene Abkürzungsregeln |

**Satz-Zuordnung am Caret** ([sentence.js](../public/js/editor/focus/sentence.js) `findSentenceAtCaret`) — zwei Regeln, beide aus dem Löschen-Verhalten hergeleitet:
- **Caret-Offset auch aus Element-Containern.** Der Caret-Container ist nicht immer ein Textknoten: nach dem Leeren eines Absatzes, direkt nach einem `<br>` und unmittelbar nach einem Merge setzt Chromium ihn aufs Element, `startOffset` ist dann ein **Kindknoten-Index**. Eine reine Textknoten-Suche findet den Container nie und fiele auf Offset 0 zurück → aktiv wäre der erste Satz, obwohl der Caret im letzten steht (Spotlight sprang beim Löschen an den Absatzanfang).
- **Satz-Intervalle sind halboffen `[start, end)`.** Sitzt der Caret exakt auf einer Grenze, gewinnt der Satz, der dort **beginnt**. Der Segmenter schlägt den Trennraum dem Vorgänger zu — mit `<= end` galt nach jedem getippten Punkt-plus-Leerzeichen noch der abgeschlossene Satz als aktiv, und beim Rückwärtslöschen über eine Grenze sprang das Spotlight einen Satz zurück. Nur hinter dem letzten Satz (Blockende, Trailing-Whitespace) greift weiterhin der Last-Range-Fallback.
| `window-3` | Aktiver + direkter Vorgänger + direkter Nachfolger (`.focus-paragraph-near`) hell |
| `typewriter-only` | Keine Block-Markierung, alle Blöcke hell. Nur Caret-Scroll bleibt |

`_focusUpdateActive` ([card.js](../public/js/editor/focus/card.js)) hat einen **Short-Circuit-Cache** (`ctx._lastBlock` / `ctx._lastGranularity`): bleibt der aktive Block beim Tippen gleich, entfällt die Neuberechnung des Sentence-Highlights (ausser bei `opts.force`, siehe `compositionend`). Die Block-Marks (`applyBlockMarks`) laufen trotzdem jeden Tick — die Setter sind idempotent und der unbedingte Aufruf ist die Ghost-Klassen-Defense.

**Struktur-Repair synchron im `input`-Handler** ([listeners.js](../public/js/editor/focus/listeners.js) `onInput` → `repairMarksNow`): jedes `input`-Event prüft **im selben Task, vor dem Paint**, ob die Block-Markierung noch stimmt (`blockMarksIntact`), und korrigiert sie nur dann (`repairBlockMarks` + `ctx._lastBlock` nachziehen) — NICHT erst im RAF einen Frame später. Zwei Strukturwechsel brauchen das:

- **Split** (`insertParagraph`/`insertLineBreak`): Chromium kopiert die `.focus-paragraph-active`-Klasse auf beide `<p>` → kurz leuchten zwei Absätze.
- **Merge/Löschen** (`deleteContentBackward` & Co., auch `insertCompositionText` beim Wort-Ersatz): Backspace am Absatzanfang zieht den markierten `<p>` aus dem DOM → **kein** Element trägt die Klasse mehr → die Dim-Regel greift für den ganzen Text.

**Why repair-only statt unbedingt setzen:** der Ist-Soll-Vergleich macht den Aufruf im Normalfall (Tippen im selben Block) zum reinen Lesevorgang — keine Klassen-Mutation, kein Style-Recalc pro Keystroke — und erlaubt denselben Pfad **während einer Composition** (siehe IME-Abschnitt). **Why nicht auf inputTypes gefiltert:** Android-IMEs ersetzen ganze Wörter über `insertCompositionText`, Undo/Redo und Paste bauen ebenfalls Blöcke um; eine Whitelist wäre systematisch unvollständig. **Why nicht im `beforeinput` clearen:** das vermied zwar den Doppelflash, erzeugte aber einen **Dim-Flash** — für einen Frame ist nichts aktiv → der ganze sichtbare Text snappt auf `opacity 0.35` und zurück (die Dim-Regel snappt bewusst ohne Transition).

## Recenter-Pipeline

### Zielverhalten (Typewriter)

**Die Schreibzeile ruht auf dem Anker.** Schreibzeile = die visuelle Zeile, in der der Caret sitzt. Anker = `typewriterAnchor` × Höhe des **sichtbaren** Bereichs (Default `0.5` → Bildschirmmitte). Die Position ist über die ganze Seite konstant — erster Absatz, Mitte, letzter Absatz gleich. Beim Schreiben wandert der Text unter der Zeile nach oben, nicht die Zeile im Bild.

- **Anker-Knopf `typewriterAnchor`**: Root-`shellState` ([app-state.js](../public/js/app/app-state.js), Default `0.5`) und Teil des editor-host-Vertrags ([shared/editor-host.js](../public/js/editor/shared/editor-host.js)) — eine fremde Schale (Mac-Client via [standalone.js](../public/js/editor/focus/standalone.js)) setzt ihn beim Bootstrap. Kein SPA-UI-Setting. `0` = oberer Rand, `0.5` = Mitte, `0.33` = oberes Drittel; ungültig/fehlend → `0.5` (`normAnchorRatio` in [typewriter.js](../public/js/editor/focus/typewriter.js)). **Der Anker ist auch eine Layout-Grösse:** `markFocusChrome` publiziert ihn beim Eintritt als `--focus-anchor` auf `:root`, die Kopf-/Tail-Puffer in [focus-mode.css](../public/css/editor/focus/focus-mode.css) rechnen damit (Invariante 9). Ein in CSS hartcodierter Puffer klemmte jeden Anker ≠ 0.5 an Seitenanfang/-ende.
- **Seitenanfang und Seitenende sind keine Ausnahme**: die Puffer-Formeln (Invariante 9) sind so gesetzt, dass auch die erste und die letzte Zeile den Anker erreichen — auf jeder Viewport-Breite und für jeden Anker. Klemmt es dort, ist der Puffer falsch, nicht der Typewriter. Wer mobil weniger Leerraum über dem ersten Absatz will, senkt den **Anker**, nicht den Puffer.
- **Der Eintritt positioniert mit derselben Geometrie**: `_focusInstall` holt den Schreib-Slot per `scrollEntryTargetToAnchor` (= `typewriterScroll` mit Schwelle 0) auf den Anker. `jumpToTrailingParagraph` scrollt selbst **nicht** — ein `scrollIntoView({block:'center'})` dort wäre eine zweite Definition von „Zeile in die Mitte" (Box-Mitte statt Bildschirm-Anker) und beim ersten Tastendruck als Sprung sichtbar.

**Abschliessende Liste der Fälle, in denen die Zeile bewusst nicht auf den Anker gezogen wird** — alles andere ist ein Bug:

1. **Unter der Schwelle** `max(16px, line-height × 0.5)`: Tippen innerhalb derselben Zeile scrollt nicht (Jitter-Filter, Details unten).
2. **Klick-Schonfrist** `POINTER_GRACE_MS`: der Caret sitzt, wo der User hingeklickt hat.
3. **Aktive Textmarkierung**: kein Recenter, solange eine Auswahl offen ist.
4. **Lese-Scroll** (`preferCenter`): Spotlight folgt dem Viewport-Center, Typewriter-Scroll läuft gar nicht.
5. **Kein Caret-Rect ermittelbar**: Scroll bleibt aus statt auf die Block-Mitte auszuweichen (Invariante 14).
6. **Laufende IME-Composition**, solange die Caret-Zeile sichtbar bleibt (`imeSafe`, Details unten).

### Ablauf

Trigger feuern `_focusUpdateActive(scroll: boolean)`. Recenter passiert in einem **gecancelten RAF** — Burst-Inputs (Paste, Auto-Korrektur, IME) kollabieren auf einen Frame.

```
selectionchange / input / scroll / focus → _focusUpdateActive(…)
                                              │
                                       cancelAnimationFrame(_focusRaf)
                                              │
                                              ▼
                              ┌──── RAF-Body (try/catch) ────┐
                              │ 1. Generation-Check          │
                              │ 2. Block aus Caret-Anchor    │
                              │    (Fallback: Viewport-Center│
                              │    via IO-Set / QSA;         │
                              │    preferCenter → direkt     │
                              │    Viewport-Center)          │
                              │ 3. setActiveBlock + nearBlocks│
                              │    (Cache-Short-Circuit)     │
                              │ 4. Sentence-Highlight        │
                              │ 5. Typewriter-Scroll wenn:   │
                              │    scroll && block && !sel   │
                              └──────────────────────────────┘
```

- **Hervorhebung übersteht Löschen, Merge und transiente `block === null`-Ticks** — vier Schutzschichten gegen das „Hervorhebung verschwindet"-Phänomen (Caret sitzt nach Merge/Voll-Löschen kurz direkt auf dem Container → `findBlockFromNode` = null; oder der markierte Block ist mit der Löschung ganz aus dem DOM geflogen):
  1. **QSA-Fallback in [findBlockAtViewportCenter](../public/js/editor/focus/dom-blocks.js)**: liefert der bevorzugte IO-Pool (`visibleBlocks`) `null` (alle getrackten Blöcke transient Höhe 0 / abgehängt), wird auf den vollständigen `querySelectorAll`-Scan zurückgefallen, statt aufzugeben.
  2. **`_lastBlock`-Beibehaltung in [resolveActiveBlock](../public/js/editor/focus/recenter.js)**: ist `block` trotz Fallback `null` (paragraph/window-3/sentence), wird der vorige aktive Block beibehalten, solange er noch im Container hängt (`container.contains`). Der nächste echte Tick reconciliiert. **Greift nicht bei `typewriter-only`** (dort ist nie ein Block aktiv) und **nicht nach Blur** — `onBlur` setzt `ctx._lastBlock=null` und clear't bewusst, der absichtliche Blur-Clear bleibt also erhalten.
  3. **Synchroner Repair im `input`-Handler** (siehe „Struktur-Repair" oben): fängt den Fall, in dem der markierte Block mit der Löschung verschwunden ist — noch vor dem Paint, also ohne sichtbaren Frame ohne Hervorhebung.
  4. **Repair auch während laufender Composition** (siehe IME-Abschnitt): sonst bliebe die Hervorhebung auf Android bis zum `compositionend` weg — Gboard hält die Composition über ganze Wörter/Sätze offen.
- **Abgehängter Selection-Anchor blockt den Tick nicht** ([listeners.js](../public/js/editor/focus/listeners.js) `onSelection`): der Guard „Selection ausserhalb des Editors ignorieren" prüft zusätzlich `isConnected`. Ein Anchor, der gerade weggelöscht wurde, ist weder im Container noch anderswo — er darf nicht wie eine Fremd-Selection (Sidebar-Input, Modal) behandelt werden, sonst bleibt die Markierung auf dem verschwundenen Block stehen.
- **Center-Pick nimmt den sichtbaren Bildschirm als Bezug, nicht die Scroll-Box** ([dom-blocks.js](../public/js/editor/focus/dom-blocks.js) `visibleBoxRect` → Überschneidung Box ∩ `visibleViewportRect()`) — derselbe Bezug wie beim Typewriter-Anker. Die Box läuft mobil hinter der Tastatur weiter (Tail-Puffer ~100vh, Invariante 9), ihre geometrische Mitte liegt bei offener Tastatur also weit unter dem, was der User sieht: der Pick landete auf einem Absatz hinter der Tastatur, und alles Sichtbare war gedimmt — vom „Hervorhebung weg"-Fall nicht zu unterscheiden. Betrifft beide Pfade, die den Center-Pick nutzen (`preferCenter`-Lese-Scroll **und** den Caret-Fallback). Kein Überlapp / kein `visualViewport` → Box-Bezug, damit der Pick nie leer ausgeht.
- **Manueller Scroll verschiebt das Spotlight** ([listeners.js](../public/js/editor/focus/listeners.js) `onScroll` → `_focusUpdateActive(false, { preferCenter: true })`): beim Lese-/Scroll-Durchlauf bestimmt nicht der (unsichtbare) Caret den aktiven Block, sondern der Absatz in der Viewport-Mitte. Die Granularitäts-Regel (paragraph/sentence/window-3) greift unverändert auf diesen Block. `preferCenter` gilt **ausschliesslich** für den User-Scroll-Pfad — `applyViewport` (Mobile-Tastatur/Resize) bleibt caret-basiert (ohne `preferCenter`), sonst springt das Spotlight bei jedem KB-Frame. Programmatischer Typewriter-Scroll wird über die prog-Scroll-Marke verschluckt und löst kein Center-Pick aus.
- **Der Center-Pick prüft die Sichtbarkeit seines Treffers nach** ([dom-blocks.js](../public/js/editor/focus/dom-blocks.js) `findBlockAtViewportCenter` → `overlapsBand`): IntersectionObserver-Callbacks laufen asynchron, der Recenter-Tick im RAF sieht also ein Set, das einen Frame alt ist. Beim laufenden Scroll ist das harmlos (die Sets zweier Frames überlappen fast vollständig), nach einem **Sprung** (Page-Down, Scrollbar-Zug, programmatischer Sprung) liegt es komplett off-screen — der Pick landete weit ausserhalb des Bildes und der ganze sichtbare Text blieb gedimmt, und weil ein IO-Callback selbst keinen Tick auslöst, bis zum nächsten Event. Schneidet der Treffer das Bezugsband nicht mehr, übernimmt der QSA-Vollscan. Kostet im Normalfall nichts (der Treffer liegt im Band) und nur im Sprung-Fall einen Scan.
- **Aktive Textmarkierung blockt Recenter** — User zieht Auswahl auf, Viewport darf nicht springen.
- **Klick markiert `pointerIntent`** ([listeners.js](../public/js/editor/focus/listeners.js) `markPointer`) — folgender `selectionchange` recentert NICHT (Klick ist absichtliche Positionsänderung). Flag fällt automatisch zurück (Klick in leeren Margin erzeugt keinen selectionchange): nach `POINTER_GRACE_MS=300` ms, bei `pointerType === 'touch'` nach `POINTER_GRACE_TOUCH_MS=700` ms.
- **Cursor-Auto-Hide zählt Klicks als Aktivität** ([listeners.js](../public/js/editor/focus/listeners.js) `onPointerActivity` → [cursor-hide.js](../public/js/editor/focus/cursor-hide.js)): nach `CURSOR_HIDE_MS=2000` ms ohne Zeiger-Aktivität setzt `.focus-cursor-hidden` (`cursor: none`) den Mauszeiger unsichtbar; zurück holt ihn **`pointermove` und `pointerdown`/`pointerup`**. **Why:** hing das Aufdecken nur an der Bewegung, blieb der Zeiger über den ganzen Klick unsichtbar, wenn er zuvor auf einer Stelle geruht hatte — die Selektion entstand korrekt, aber Markieren wurde zum Blindflug (Doppelklick aufs Wort, Auswahl aufziehen). Gegated: [tests/e2e/focus-editor.spec.js](../tests/e2e/focus-editor.spec.js) („Cursor-Auto-Hide: Klick ohne Mausbewegung …", „Doppelklick markiert ein einzelnes Wort …").
- **Klick in die leere Seitenfläche landet auf der Zeile, nicht am Buchrand** ([listeners.js](../public/js/editor/focus/listeners.js) `onGutterMousedown` + [dom-blocks.js](../public/js/editor/focus/dom-blocks.js) `resolveGutterCaretPoint`). Das mousedown-Target ist genau dann der Container selbst, wenn kein Block getroffen wurde — also im Padding. Dann gilt: **seitlich neben einer Zeile** → Caret an deren erstes (links) bzw. letztes (rechts) Zeichen (y bleibt, x wird an den Rand der Textspalte geclamped, `caretRangeFromPoint` liefert die Position); **im Kopf-/Tail-Puffer** (über dem ersten, unter dem letzten Block) → nichts. Shift-Klick erweitert die Auswahl bis zum Zeilenrand. Der Browser-Default (`preventDefault` in **beiden** Fällen) würde stattdessen an Buchanfang/-ende springen, weil der Container der nächste Treffer ist. Gegated: [tests/unit/editor-focus.test.mjs](../tests/unit/editor-focus.test.mjs) (`resolveGutterCaretPoint`-Block) + [tests/e2e/focus-editor.spec.js](../tests/e2e/focus-editor.spec.js) („Klick in die Seitenfläche …", „Klick in den Kopf-Puffer …").
- **Typewriter-Schwelle dynamisch** ([typewriter.js:18-25](../public/js/editor/focus/typewriter.js#L18-L25)): `max(16, line-height * 0.5)`. Statisches 16 px scrollte schon bei subpixel-Jitter — halbe Zeilenhöhe ist die natürliche „echte Zeilenwechsel"-Grenze. Die Schwelle ist der **einzige** Jitter-Filter: die Ruheposition der Schreibzeile bleibt exakt der Anker.
- **Anker-Bezug ist der sichtbare Bildschirm, nicht die Scroll-Box** (`visibleViewportRect()` → `computeTypewriterDelta(…, viewportRect)`): die Box `.focus-editor__content` beginnt unter der Focus-Topbar und läuft mobil hinter der Tastatur weiter, ihre Mitte liegt also unter der Bildschirmmitte. Bezug ist `visualViewport` (`offsetTop` + `height`, Android Chrome schiebt den fixed Container nach oben), Fallback `window.innerHeight`. Der Anker wird in die Box geclampt, sonst wäre er für den Caret unerreichbar und der Scroll liefe ins Leere.
- **Prog-Scroll-Marke statt Zähler** ([typewriter.js](../public/js/editor/focus/typewriter.js)): `typewriterScroll` merkt die selbst geschriebene Zielposition samt Box in `ctx.progScroll`, `consumeProgrammaticScroll` (aus `onScroll`) vergleicht Box-Identität + ±1 px gegen den aktuellen `scrollTop` und **löscht die Marke bei jedem Event**. Damit kostet ein verlorenes oder zusätzliches `scroll`-Event höchstens einen Tick; ein Zähler bliebe im Fehlerfall dauerhaft desynchron und liesse `onScroll` danach jeden echten User-Scroll verschlucken (Spotlight bleibt beim Blättern stehen). Gesetzt wird die Marke **erst nach dem Scroll und nur bei echter Bewegung** (`behavior: 'instant'` schreibt `scrollTop` synchron, die Strecke ist sofort messbar) — ein am Anschlag geklemmter Scroll feuert kein Event und darf keine Marke hinterlassen.
- **`getCaretRect`-Dreistufenpfad** ([typewriter.js](../public/js/editor/focus/typewriter.js)):
  1. `range.getClientRects()[0]` — Standardfall, deckt 95 %.
  2. `range.getBoundingClientRect()` — Fallback bei leerer Rect-Liste.
  3. **Probe-Range-Expansion**: Range um 1 Position erweitern (`setEnd(off+1)`, sonst `setStart(off-1)`), Rect lesen, Probe verwerfen. Fängt den collapsed-Range-Bug am Soft-Wrap-Bruch und direkt nach `<br>`, wo Browser sonst Höhe 0 / leere Rects liefern. Non-collapsed Ranges liefern deterministisch das Rect der angrenzenden Glyphe → korrekte visuelle Zeile.
- **Kein Block-BBox-Fallback im Recenter** ([recenter.js](../public/js/editor/focus/recenter.js) `runTypewriter`): Wenn `getCaretRect` `null` liefert, bleibt der Scroll aus — kein Rückfall auf `block.getBoundingClientRect()`. Begründung: bei langen Absätzen ohne neue Absatzmarken (User schreibt Riesensatz mit Soft-Wraps und shift-enter-Brüchen) bewegt sich die Block-Mitte nicht mit dem Caret. Block-BBox als Ziel hätte den Typewriter stehenbleiben lassen, obwohl der Cursor visuell mehrere Zeilen tiefer sitzt. Wenn das Caret-Rect wirklich nicht ermittelbar ist (leerer Absatz ohne Text-Kind, kein Fokus), liefert der nächste echte Input bereits valides Rect.

## Lifecycle-Sequenzen (Pflichtreihenfolge)

### Enter
1. Guards: nur aus `idle` heraus, nur wenn `showEditorCard && editMode`.
2. `_flushDraftSaveNow` — offene Debounce-Drafts ins Backend, damit kein getippter Inhalt verloren geht, falls späterer Cancel im Fokus.
3. `_focusGen++` → `focusActive=true`, body-class `focus-mode` setzen; die `focus-mode--<granularity>`-Klasse sitzt auf `.focus-editor` (nicht am Body — der Dim-Selektor scoped via `.focus-editor.is-active:not(.focus-mode--typewriter-only)`).
4. `$nextTick(_focusInstall)`: erst nach Alpine-Render → `--editing`-Container existiert.
5. `_focusInstall`: Container holen, `AbortController` aufmachen, IO/MO setzen, alle Listener mit `{ signal }` registrieren, `applyViewport` direkt (ohne Debounce), Cursor zeigen, `--editing`-Container fokussieren, `jumpToTrailingParagraph` (legt Auto-`<p>` an oder recycelt leeren letzten Absatz).
6. `_focusState='active'` → erstes `_focusUpdateActive(true)` → `writeFocusSnapshot(pageId)`.

### Exit
1. `_focusState='exiting'`, `_focusGen++` (RAFs werden no-op).
2. Auto-`<p>`-Slot prüfen: wenn unverändert leer → entfernen. Sonst bleibt er stehen (User hat darin getippt).
3. `await quickSave` wenn `editMode && editDirty && !editSaving`. Offline/Fehler → `editDirty` bleibt true, Draft im LocalStorage, User bleibt im Edit-Modus (Banner zeigt Status, kein erzwungener Exit).
4. Race-Check: wer in der Zwischenzeit `enter` gerufen hat → abbrechen, kein Cleanup.
5. `_focusTeardown`: AbortController killt alle Listener auf einen Schlag, IO/MO disconnect, Timer clear, RAF cancel.
6. `clearFocusSnapshot`, body-classes weg, `--focus-vh*` löschen, Restklassen + `::highlight(focus-sentence-dim)` defensiv aufräumen.
7. Wenn `editMode && !editDirty` (sauberer Save): `_stopAutosave` → `_uninstallOnlineRetry` → `_editCounterCtx.teardown` → `editMode=false` + `editSaving=false` + `saveOffline=false`. **Reihenfolge Pflicht.** Synonym-Menü, Synonym-Picker, Figur-Lookup zu.
8. Idempotent: `_syncPageStatsAfterSave` + `updatePageView` — garantiert dass Stats-Badges + View-HTML den aktuellen `originalHtml` reflektieren.
9. `_focusState='idle'`.

## Auto-`<p>`-Slot

Beim Enter springt der Caret an Buchende. `jumpToTrailingParagraph` ([dom-blocks.js:23-56](../public/js/editor/focus/dom-blocks.js#L23-L56)):
- Letzter Block ist leerer `<p>` → recyceln, `added = null`.
- Sonst neuen `<p><br></p>` anhängen, `added = p`.

**Pflicht-Eigenschaften:**
- NICHT als dirty markieren (kein `_markEditDirty`). Der Slot ist nur Schreibanker; tippt der User, greift `@input`-Handler regulär.
- Exit räumt den Slot ab, falls noch leer — sonst Phantom-Revision (Backend-agnostisch via Content-Store) bei jedem Open-Close-Cycle.
- Nur `<p>` recyceln, keine leeren Headings/Listen — sonst zerstört Recycling User-Struktur.

## Snapshot-Wiederaufnahme

`writeFocusSnapshot(pageId)` schreibt `{ pageId, ts }` in sessionStorage. Überlebt F5 + OIDC-Roundtrip, nicht Tab-Close. TTL 1 h **ab der letzten Speicher-Aktivität**, nicht ab dem Eintritt: die SPA-Karte frischt `ts` per `$watch` auf `lastAutosaveAt` und `lastDraftSavedAt` über `refreshFocusSnapshot` ([card.js](../public/js/editor/focus/card.js)) auf, nur im Zustand `active`. **Why:** der Snapshot ist für den Reload nach abgelaufener Sitzung da, und der kommt typischerweise erst nach langem Schreiben — eine TTL ab Eintritt war genau dann verfallen. Gegated: [focus-editor.spec.js](../tests/e2e/focus-editor.spec.js) („Speichern im Fokus frischt den Wiederaufnahme-Snapshot auf …") + Verdrahtungs-Guard in [focus-counter.test.mjs](../tests/unit/focus-counter.test.mjs). Sub-`init` ([editor-focus-card.js:54-62](../public/js/cards/editor-focus-card.js#L54-L62)) liest und wartet via `$watch` auf `currentPage.id` + `renderedPageHtml` + `showEditorCard` — wenn alle drei matchen → `startFocusEdit`. Snapshot wird **vor** dem Restore-Versuch konsumiert (`_restoreSnapshot=null` + `clearFocusSnapshot`), sonst Loop bei kaputter Seite.

## Counter (Wörter/Zeichen + Tagesdelta)

`installEditCounter` ([shared/edit-counter.js:63-102](../public/js/editor/shared/edit-counter.js#L63-L102)) wird **im Edit-Mode** gestartet, nicht erst beim Focus-Enter. Damit zählen Edits ausserhalb des Fokusmodus zum „heute"-Delta.

- `compute()` liest `container.textContent`, debounced (`COUNTER_DEBOUNCE_MS=220`).
- Tagesbaseline pro `pageId` in localStorage. Erste Messung des Tages = Baseline; spätere Messungen liefern Delta. Stale Einträge (andere Tage) werden lazy bei jedem Read entfernt.
- `fmtSigned`: `+12` / `−5` (Unicode-Minus für Tabulator-Look) / `±0`.
- Idempotent: zweiter Install-Aufruf liefert dieselbe Teardown-Funktion ohne Listener-Doppelung. Teardown nullt `_editCounterCtx`.

## IME / Mobile-Tastatur / Resize

- **IME-Composition**: `compositionstart` setzt `ctx.composing=true`, `onSelection`/`onInput` laufen ab da im **`imeSafe`-Modus** (`_focusUpdateActive(scroll, { imeSafe: true })`): das DOM wird **nicht** angefasst (keine Block-Klassen, kein Satz-Highlight), damit weder das Kandidatenfenster wandert noch composition-empfindliche IMEs abbrechen. Der Typewriter bleibt als **Notnagel** scharf, greift aber nur, wenn die Caret-Zeile den sichtbaren Bereich verlassen hat (`caretWithinViewport(rect, visibleViewportRect(), threshold * 2)` — ein Zeilenumbruch bleibt also unbeantwortet). **Why:** ein harter Block wäre nur für CJK richtig — Android-Soft-Keyboards halten auch für gewöhnliche lateinische Wörter eine Composition offen, teils über ganze Sätze; die Schreibzeile liefe dort unter die Tastatur weg.
  - **Einzige Ausnahme: der Repair-Pfad** (`repairBlockMarks` in [card.js](../public/js/editor/focus/card.js) `_focusUpdateActive` + `repairMarksNow` in [listeners.js](../public/js/editor/focus/listeners.js)). Ist die Markierung nachweislich kaputt — der markierte Block wurde weggelöscht oder gemerged —, wird sie wiederhergestellt und Satz-Highlight/Cache nachgezogen. **Why:** genau derselbe Grund, aus dem der Typewriter-Notnagel existiert. Gboard hält die Composition über ganze Wörter/Sätze offen; ohne Repair bliebe der Text nach einer Merge-Löschung **bis zum `compositionend`** komplett gedimmt (der User-Report „Fokushervorhebung verschwindet beim Löschen auf Mobile"). Der Eingriff ist ein reiner Attribut-Toggle auf Block-Elementen, kein Struktur-Eingriff; das Kandidatenfenster hängt am Caret und bleibt stehen. Im intakten Zustand (Normalfall) mutiert der Pfad nichts.
  - `compositionend` triggert das volle Reconcile mit **`{ force: true }`** — das erzwingt das Recompute des Satz-Highlights auch dann, wenn der Repair `_lastBlock` zwischenzeitlich schon korrekt gesetzt hat und der Short-Circuit-Cache sonst „nichts geändert" meldete.
- **visualViewport** (Mobile-Tastatur): `applyViewport` setzt `--focus-vh` (Höhe) und `--focus-vh-top` (offsetTop — Android Chrome schiebt den sichtbaren Ausschnitt gegen den Layout-Viewport, WKWebView beim Pinch-Pan). `--focus-vh-top` wandert als `top` auf **`.focus-editor.is-active`** — das tatsächlich sichtbare Overlay; an `#editor-card.focus-host` allein erreichte die Kompensation die nativen Schalen nie ([standalone.js](../public/js/editor/focus/standalone.js) baut nur `.focus-editor`) und der eigene Focus-Header wanderte über den oberen Bildschirmrand hinaus. Debounced via `VV_DEBOUNCE_MS=100`. Ohne Änderung wird nur der aktive Block re-validiert (`_focusUpdateActive(false)`) — ein Recenter pro Viewport-Tick liesse den Editor bei jedem KB-Frame, URL-Leisten-Scroll und Pinch-Zoom flattern. **Ändert sich Höhe ODER Versatz** um mehr als 1 px (`shouldRecenterOnViewport(prev, next, isWriting)` mit `{ h, top }`; beide gehen in den Anker `offsetTop + height × ratio` ein, ein reiner Versatz driftete sonst unbeantwortet weg) und sitzt der Fokus im Editor (`document.activeElement`), wird **einmal** recentert: der Anker liegt in der Mitte des sichtbaren Bereichs und springt mit. Sass der Caret exakt auf dem Anker, kompensiert die Puffer-Formel (Invariante 9) das ohnehin; ist er vorher weggedriftet (Lese-Scroll, lange Composition), stünde er sonst hinter der Tastatur.
- **Touch** (`markPointer`): Fingertipp bekommt `POINTER_GRACE_TOUCH_MS=700` statt `POINTER_GRACE_MS=300`. Tippen ist mobil die einzige Art, den Caret zu setzen, und das `selectionchange` kommt dort spät (Soft-Keyboard-Animation, langsame Geräte) — mit der Maus-Karenz wäre das Flag abgelaufen und der Recenter risse die getippte Stelle weg.
- **Resize/Orientation/DevTools-Sidebar**: `window.resize` deckt den Desktop-Fall ab, wenn visualViewport-Event nicht feuert. Beide Pfade abonniert.

## Pflicht-Invarianten (zusätzlich zu CLAUDE.md)

0. **`focus/` + `shared/active-editor.js` greifen nie direkt auf `window.__app` zu.** Root-Zugriff ausschliesslich über `editorHost()` aus [shared/editor-host.js](../public/js/editor/shared/editor-host.js) — Voraussetzung dafür, dass der Editor in einer fremden Schale (nativer Mac-Focus-Writer in WKWebView, ohne Alpine-Root) per `setEditorHost()` lauffähig ist. SPA-Glue ([cards/editor-focus-card.js](../public/js/cards/editor-focus-card.js), `$watch`) darf `window.__app` nutzen — das ist die SPA-Adaption, kein Bestandteil des bündelbaren Editor-Kerns.
1. **`focusActive → editMode`** (CLAUDE.md schon). Sub-`enterFocusMode` bricht ab, wenn `!app.editMode`. `cancelEdit` ruft `exitFocusMode` zuerst.
2. **Listener nur via `AbortController`-Signal.** Jeder `addEventListener` im `_focusInstall` bekommt `{ signal }`. Kein manueller `removeEventListener`. Teardown ist ein `abort()`.
3. **IO observe nur addedNodes, unobserve removedNodes.** Vollscan bei jeder Mutation = O(n²) bei grossen Pastes. Removed-Nodes müssen aus `visibleBlocks` raus, sonst IO-Refs auf abgehängten Knoten.
4. **`setActiveBlock` querySelectorAll, nicht querySelector.** Chromium kopiert beim Paragraph-Split die `.focus-paragraph-active`-Klasse auf beide `<p>` — Vollscan räumt die Leiche ab.
5. **`classList.remove` + `removeAttribute('class')` wenn leer.** Sonst bleibt `class=""` stehen → unnötige Revision beim nächsten Save (Diff zur ursprünglich attributlosen Fassung).
6. **`findBlockFromNode` liefert outermost-Ancestor.** Innermost-Match würde bei `<blockquote><p>…</p></blockquote>` nur den inneren `<p>` aktiv markieren — der äussere Wrapper bleibt opacity-gedimmt und multipliziert auf das Kind.
7. **DIV NICHT in `BLOCK_TAGS`.** Chromium Default-Paragraph-Separator soll `<p>` erzeugen; DIV-Aufnahme würde Garantie aushebeln und Margin-/Spacing-Annahmen kippen.
8. **`_focusUpdateActive` RAF in try/catch.** Ein DOM-Edge-Case (Shadow-Root-Range, obskurer Range-Fehler) darf den Editor nicht stillstellen. Fehler → `reportError('updateActive', err)`, nächster Tick versucht neu.
9. **Kopf- und Tail-Puffer auf `.focus-editor__content` müssen gross genug bleiben, dass erste und letzte Zeile die Schreiblinie erreichen.** Beide messen **dieselbe** Strecke — `--focus-head`, die Ankerlage **innerhalb der Box**: `clamp(0px, var(--focus-vh) * var(--focus-anchor) - var(--focus-box-top), var(--focus-box-h) - var(--focus-pad-reserve))`. Kopf = `--focus-head` (negativen Scroll gibt es nicht, also muss die Strecke oberhalb des Textes liegen), Tail = `var(--focus-box-h) - var(--focus-head) - var(--focus-pad-reserve)` (unter der letzten Zeile muss der Rest der Box scrollbar bleiben). `--focus-anchor` kommt aus `markFocusChrome`, `--focus-vh`/`--focus-box-h`/`--focus-box-top` aus [viewport.js](../public/js/editor/focus/viewport.js) (`measureBoxGeometry`).
        - **Der Abzug `--focus-box-top` ist Pflicht, keine Feinheit**: der Anker ist eine BILDSCHIRM-Position (`vvTop + vvH × ratio`), die Puffer wirken innerhalb der Box, und die beginnt unter der Topbar. Ohne ihn ist der Kopf um die Topbar-Höhe zu lang und nimmt sie dem Tail weg — die letzte Zeile bleibt darum eine Zeilenhöhe unter der Linie stehen.
        - **`--focus-box-h` ist der Layout-Slot, nicht `clientHeight`**: die Box ist border-box und kann nicht kleiner werden als ihre eigenen Paddings, ihr `clientHeight` liefert also die Puffer-Summe zurück statt den Slot. Direkt gelesen wäre die Formel zirkulär (jede Messung bestätigt das aktuelle Padding und die Summe schrumpfte pro Viewport-Tick um die Reserve). `measureBoxGeometry` neutralisiert die Paddings darum für die Messung.
        - **Die Puffer-Summe ist strukturell `--focus-box-h − --focus-pad-reserve`** und muss STRIKT unter dem `clientHeight` der Scroll-Box bleiben: darauf oder darüber zerlegt WebKit die contenteditable-Selektion (Doppelklick markiert bis zum Absatzende, Zieh-Select liefert nichts). Beide Bedarfe zusammen ergeben genau die Box-Höhe, die Reserve ist also der einzige zulässige Fehler — sie geht vom **Tail** ab (der Kopf bleibt exakt) und bleibt unter der Typewriter-Schwelle. Gegated: [tests/e2e/focus-selection.webkit.spec.js](../tests/e2e/focus-selection.webkit.spec.js) (eigenes WebKit-Projekt in [playwright.config.js](../playwright.config.js) — Chromium sieht die Fehlerklasse strukturell nicht).
        - **Kein Media-Query-Override dieser Werte** — ein gekürzter Kopf-Puffer klemmte den Seitenanfang mobil mehrere Zeilen über der Linie, ein gekürzter Tail das Seitenende („man kommt nur bis zum zweitletzten Absatz"). Gilt genauso für schalen-seitige Overrides (macOS-/Android-Client, die dasselbe Bundle-CSS laden). Gegated: [tests/e2e/focus-editor.spec.js](../tests/e2e/focus-editor.spec.js) („Erste + letzte Zeile erreichen die Schreiblinie" über Desktop/Mobile/Mobile-mit-Tastatur/Anker 0.33/Anker 0 + „Erste Zeile ruht tatsächlich auf der Schreiblinie (Mobile)"; die Matrix liest `--focus-pad-reserve` aus dem CSS, statt die Zahl zu spiegeln).
9a. **Prog-Scroll wird über Position **und Box** erkannt, nicht gezählt** — `ctx.progScroll = { box, top }` hält die zuletzt selbst gefahrene Scroll-Position samt der Box, die sie trägt (im Fallback-Fall scrollt ein Vorfahr, und dort feuert auch das Event). `consumeProgrammaticScroll` verbraucht die Marke bei **jedem** `scroll`-Event, auch wenn sie zu einer anderen Box gehört. Ein Scroll ohne `scrollTop`-Änderung (Anschlag, Sub-Pixel-Rundung) darf keine Marke setzen. Kein Zähler: der bliebe nach einem verlorenen/zusätzlichen Event dauerhaft desynchron und der Editor ignorierte danach jeden User-Scroll. Die Position allein genügt nicht als Kriterium — Container und Vorfahr können auf demselben `scrollTop` stehen und verschluckten sich gegenseitig die Marke. Gegated: [tests/unit/editor-focus.test.mjs](../tests/unit/editor-focus.test.mjs) (`typewriterScroll`- + `consumeProgrammaticScroll`-Block).
10. **Sentence-Highlight nur via `CSS.highlights`.** Keine DOM-Span-Wraps — sonst Save-Diff bei jedem Caret-Move. Browser ohne Custom-Highlight-API → Sentence-Mode degradiert lautlos auf Paragraph-Visual.
11. **`overflow-anchor: none`** auf `.focus-editor__content`. Chrome's Scroll-Anchoring kämpft sonst mit Typewriter-Scroll → sichtbares „Flattern".
11a. **Die Textspalte wird über seitliches Padding zentriert, nicht über `max-width` + `margin:0 auto`.** `padding-inline: max(2rem, safe-area, calc((100% - 60ch) / 2))` auf `.focus-editor__content` — die Box selbst bleibt damit über die **ganze** Overlay-Breite Scroll- UND Klickfläche, die Spalte darin bleibt 60ch. Eine 60ch-breite Box liess die Flächen daneben als toten Raum zurück: Klicks trafen `.focus-editor` (kein Handler, kein Caret) und das Mausrad fand keinen scrollbaren Vorfahr (Body ist `overflow:hidden`) — Scrollen ging nur über dem Text. Dazu `box-sizing: border-box` **explizit** am Container: im content-box-Modell addiert sich das Prozent-Padding auf die `width:100%` und die Box läuft breiter als das Fenster. Der globale `*`-Reset steht in [layout/base.css](../public/css/layout/base.css), die weder die Test-Harness noch die nativen Client-Schalen laden. Gegated: [tests/e2e/focus-editor.spec.js](../tests/e2e/focus-editor.spec.js) („Mausrad über der Seitenfläche …" + die beiden Klick-Tests prüfen, dass es überhaupt eine Seitenfläche neben der Spalte gibt).
11b. **`text-wrap: wrap` auf `.focus-editor__content` — greedy, nie absatzweit optimierend.** `pretty`/`balance` bewerten den ganzen Absatz und brechen dafür bereits gesetzte Zeilen neu um; beim Tippen rutscht ein Wort eine Zeile nach unten und beim nächsten Zeichen wieder zurück. Die Deklaration sitzt am **Container**, nicht pro Block-Tag: `text-wrap` ist vererbt, so gilt die Garantie für `p`, `li`, `blockquote` und `h1`–`h6` gleichzeitig, und ein künftiger UA-Default oder ein Host-Stylesheet kann keinen einzelnen Block-Typ still auf `pretty` kippen. In einer Pro-Block-Regel **nicht** wiederholen — sonst gilt die Garantie wieder nur für das dort genannte Tag. Für fremde Schalen gilt Invariante 13 sinngemäss: eine unlayered Host-Regel schlägt auch diese Deklaration, ein `text-wrap: pretty` im Client-CSS holt das Flattern also zurück.
11c. **`white-space: pre-wrap` auf den Schreibblöcken — pro Block, nie auf dem Container.** Unter `normal` schreibt Blink für einen Leerschlag, der am Zeilenende kollabieren würde, ein `&nbsp;` in den Text und wandelt es beim nächsten Zeichen zurück („whitespace rebalancing"). Ein `&nbsp;` ist umbruchfest: passt Wort + `&nbsp;` nicht mehr in die Zeile, fällt das ganze Wort eine Zeile runter und springt beim nächsten Zeichen zurück — ein Zucken bei jedem Leerschlag an der Umbruchkante, im einzigen Modus, der nur zum Schreiben da ist. Unter `pre-wrap` hängt der Leerschlag über den Zeilenrand hinaus und das Wort bleibt stehen.
    - **Warum pro Block und nicht am Container** (anders als 11b): das gespeicherte Seiten-HTML trennt die Blöcke mit `\n`-Textknoten, die Kinder des Containers sind — mit `pre-wrap` auf `.focus-editor__content` würde jede dieser Trennungen als Leerzeile rendern. Die Tag-Liste ist die der Dim-Regel **minus `pre`** (dort regelt `white-space: inherit`).
    - **11b bleibt unberührt.** `white-space` ist das Kurzschreiben für `white-space-collapse` + `text-wrap-mode`; es setzt `text-wrap-mode` auf den ohnehin geltenden Wert `wrap` und lässt das vererbte `text-wrap-style` in Ruhe. Der Container-Guard gegen `pretty`/`balance` gilt weiter für alle Blöcke.
    - **Gekoppelt an den Soft-Break-Handler — die beiden fallen nur gemeinsam.** Unter `pre-wrap` schreibt Chromiums `insertLineBreak` bei Shift+Enter ein rohes `\n` statt eines `<br>` (mitten im Text eines, am Blockende zwei). Das `\n` rendert nur unter `pre-wrap` als Umbruch; in Notebook-Leseansicht, Share-Reader und allen Exporten kollabiert es zum Leerzeichen — der Umbruch wäre nach dem Speichern still verloren. Darum fängt [listeners.js](../public/js/editor/focus/listeners.js) (`onSoftBreak`) Shift+Enter am **Container** ab und setzt den Umbruch über [shared/soft-break.js](../public/js/editor/shared/soft-break.js) (`insertSoftBreak`) selbst als `<br>`. Container-Level, weil der Handler vor dem delegierten Toolbar-Dispatcher laufen muss (`stopPropagation`, sonst setzt dessen `_kbSoftBreak` zusätzlich ein `insertLineBreak`) **und** weil er so auch in der Standalone-Schale der nativen Clients greift, die gar keine Toolbar-Karte mountet.
    - **Am Blockende gibt es keinen execCommand-Weg.** `insertHTML('<br>')` fügt dort nichts ein **und** setzt den Caret in den nächsten Absatz — Probieren-und-Messen scheidet als Strategie aus, die Caret-Lage muss vorher feststehen (`caretAtBlockEnd`). Der manuelle Zweig setzt dann `<br>` **plus Platzhalter-`<br>`**: ein einzelnes `<br>` am Blockende erzeugt keine sichtbare Leerzeile. Dasselbe Paar erzeugt Chromiums `insertLineBreak` im Notebook auch heute schon, die Persistenz ändert sich also nicht — bleibt die Zeile leer, kollabiert `collapseEmptyBlocks` das Paar beim Save auf ein `<br>`. Rückgängig machbar ist der manuelle Zweig wie der execCommand-Zweig über die eigene Undo-Historie (Invariante 19): sie hängt am synthetisch nachgereichten `input`-Event, nicht am nativen Stack.
    - **Der Flattener für Inline-Styles muss `white-space: pre-wrap !important` sagen, nie `normal`** — sein Attribut-Selektor greift auch auf Block-Elementen (`<p style="text-align:center">` aus dem Import), und `normal` holte genau dort das Zucken zurück.
    - **Alt-Bestände müssen beim Mount eingeebnet werden.** `pre-wrap` macht sichtbar, was überall sonst kollabiert: ein `\n` im Blockinneren rendert als Umbruch (gemessen: aus einer Zeile werden drei), führende Leerzeichen als Einzug (15 px). Solche Bestände kommen aus Importen und hübsch formatiertem Quell-HTML — der Server-Cleaner fasst Textknoten nicht an, er trimmt nur die Blockränder. [soft-newlines.js](../public/js/editor/focus/soft-newlines.js) normalisiert deshalb an allen drei Mount-Stellen; die Ersetzung ist für jeden Konsumenten bedeutungsgleich (alle kollabieren Whitespace ohnehin). **`pre` und `.poem` bleiben zwingend aussen vor** — dort ist der Umbruch echte Struktur, ein Kollaps wäre Datenverlust, der beim nächsten Save persistiert. Ebenso die Textknoten **zwischen** den Blöcken: der Container ist `white-space: normal`, dort rendert nichts, und eine Ersetzung wäre eine grundlose Änderung am gespeicherten HTML.
    - Nebenwirkung, bewusst in Kauf genommen: `.poem`-Absätze brechen im Fokus jetzt an ihren `\n`, wie in der Leseansicht (`pre-line`) auch. Und Seiten mit Alt-`\n` erzeugen beim ersten Fokus-Exit eine einmalige, semantisch neutrale Heil-Revision.
    - Gegated: [tests/e2e-app/focus-editor-app.spec.js](../tests/e2e-app/focus-editor-app.spec.js) („Leerschlag an der Umbruchkante …", mutationsgeprüft) — **App-Suite, nicht Harness**: die Umbruchkante hängt an der echten Spaltenbreite und Schriftmetrik. Dazu [tests/e2e/focus-editor.spec.js](../tests/e2e/focus-editor.spec.js) (vier Shift+Enter-Fälle: mitten im Text, am Blockende, Dedup, Auswahl-Ersatz — je mit der Assertion „kein `\n`"; dazu „Alt-Bestand: rohe Umbrueche …" und „Gedicht behaelt seine Umbrueche …") und [tests/unit/focus-soft-newlines.test.mjs](../tests/unit/focus-soft-newlines.test.mjs) (Kollaps, Rand-Trim, `pre`/`.poem`-Skip, Inter-Block-Whitespace, Idempotenz).
12. **`x-show="!focusActive"`-Guards für Findings-Close-Button, Toolbar, Bubble.** Findings sind im Fokus ohnehin via CSS ausgeblendet; Buttons trotzdem mit `x-show` raus, damit Tab-Reihenfolge sauber bleibt.
13. **Die Scroll-Box wird aufgelöst, nicht angenommen — `resolveScrollBox` ist die SSoT.** Normalfall ist `.focus-editor__content`. Fremde Schalen (macOS-/Android-Client) laden dasselbe Bundle-CSS, bringen aber eigenes Host-CSS mit; **unlayered** Host-Regeln schlagen jede Regel aus `focus-mode.css` (`@layer components`) unabhängig von Spezifität, der Editor kann sich per CSS also nicht wehren. Kann der Container grundsätzlich nicht scrollen (`scrollHeight <= clientHeight`), liefert [resolveScrollBox](../public/js/editor/focus/typewriter.js) den nächsten scrollbaren Vorfahr bzw. das Dokument. **Am regulären Scroll-Anschlag greift der Pfad nicht** (Box ist scrollbar, steht nur am Ende), sonst zöge er die Seite unter dem Editor weg. `canScroll` genügt als Diskriminator, weil die Kopf-/Tail-Puffer (Invariante 9) eine Box mit intakter Höhenkette auch bei leerer Seite scrollbar machen.
    - **Alle Konsumenten hängen an derselben Auflösung**, sonst rettet der Pfad nur den Typewriter und der Rest läuft weiter gegen eine Box, die nicht scrollt: `typewriterScroll` scrollt sie, `ctx.scrollBox` (neu aufgelöst in jedem `applyViewport`-Tick — Host-CSS kann die Kette per Media-Query umhängen) speist den IntersectionObserver-`root` und die `--focus-box-h`-Messung, und `onScroll` filtert darauf.
    - **`onScroll` hängt am `document` in der Capture-Phase**, nicht am Container. Scroll-Events bubbeln nicht, die Capture-Phase läuft aber für jedes dispatchte Event den vollen Pfad ab — ein Listener erwischt damit Container **und** Fallback-Box. Am Container allein wäre in genau diesen Schalen der Lese-Scroll unsichtbar (`preferCenter` liefe nie, das Spotlight bliebe beim Blättern stehen). Gefiltert wird auf Boxen, die den Editor enthalten (`box.contains(container)`), damit fremde Scroller (Sidebar, Modal) keinen Tick auslösen.
    - Gegated: [tests/unit/editor-focus.test.mjs](../tests/unit/editor-focus.test.mjs) (`resolveScrollBox`- + `typewriterScroll`-Block) und **im echten Browser** [tests/e2e/focus-shell-host.spec.js](../tests/e2e/focus-shell-host.spec.js) gegen [shell-host-harness.html](../tests/fixtures/shell-host-harness.html) — die Schalen-Konstellation (Scroll am Vorfahr + `scroll-behavior: smooth` im Host-CSS), die das reguläre `focus-harness.html` strukturell nicht sieht.
14. **Typewriter folgt ausschliesslich dem Caret-Rect.** Kein Block-BBox-Fallback im Recenter. `getCaretRect` ist die einzige Ziel-Rect-Quelle; liefert sie `null`, bleibt der Scroll aus. Block-Mitte als Ersatz täuscht Stabilität vor und blockiert Typewriter in langen Absätzen mit Soft-Wraps / `<br>`-Brüchen — `getCaretRect` deckt diese Edge-Cases via Probe-Range-Expansion ab.
14a. **Programmatische Scrolls immer `behavior: 'instant'`.** Nicht `'auto'` und nicht die Kurzform: beide delegieren laut CSSOM-View an die computed `scroll-behavior`. Eine Schale mit unlayered `scroll-behavior: smooth` animierte den Scroll dann — `scrollTop` stünde direkt danach noch auf dem Altwert, die gefahrene Strecke wäre 0, es gäbe **keine** prog-Scroll-Marke, und das später eintreffende `scroll`-Event gälte als User-Scroll und risse das Spotlight auf den Center-Block. Im Web deckt das nur der `prefers-reduced-motion`-Block in [layout/base.css](../public/css/layout/base.css) ab — den lädt weder eine Schale noch die Test-Harness. Betrifft `typewriterScroll` und den `window.scrollTo` beim Eintritt ([card.js](../public/js/editor/focus/card.js)#`_focusInstall`). Gegated: [focus-editor.spec.js](../tests/e2e/focus-editor.spec.js) („Typewriter-Scroll ist immer instant") + [focus-shell-host.spec.js](../tests/e2e/focus-shell-host.spec.js).
15. **`exitFocusMode` endet immer in `idle` und immer ohne Chrome.** Der ganze Cleanup läuft in `try`; das `finally` setzt (wurffrei, als erste Anweisung) `_focusState='idle'` und wiederholt danach die fünf idempotenten Sichtbarkeits-Schritte `mirrorToNormal` → `_focusTeardown` → `focusActive=false` → `unmarkFocusChrome` → `clearAllFocusMarks`. **Why:** ohne das Netz sperrt ein einziger geworfener Schritt den Editor bis zum Reload — `enterFocusMode` verlangt `idle`, `exitFocusMode` verlangt `active`, beide Türen zu, und das Overlay steht sichtbar da, nachdem die Listener bereits abgeräumt sind (kein Tastatur-Ausweg). Reihenfolge im Netz ist dieselbe wie oben: spiegeln, solange `.is-active` den Focus-Container noch findet. `clearAllFocusMarks` gehört mit hinein, weil die Marks über `mirrorToNormal` in den Normal-Container wandern — bleiben sie nach einem Wurf stehen, sitzt der User in einer Leseansicht mit einem hellen und sonst durchgehend gedimmtem Text, und der nächste Save persistiert sie. Gegated: [tests/e2e/focus-editor.spec.js](../tests/e2e/focus-editor.spec.js) („Wirft ein Cleanup-Schritt im Exit …", „Exit räumt body-/Cardroot-Chrome ab …" — Wurfstelle bewusst **vor** `unmarkFocusChrome`, prüft zusätzlich, dass keine `.focus-paragraph-*` zurückbleiben).
16. **Beide Verlassen-Wege speichern.** Escape und Cmd/Ctrl+Shift+E rufen `exitFocusMode`. Escape darf **nicht** auf `cancelEdit` (Verwerfen-Dialog) umgeleitet werden: zwei Tasten mit gegensätzlichem Ausgang, und ausgerechnet die intuitivste Verlassen-Taste im ablenkungsfreien Vollbild wäre die einzige, die Text wegwerfen kann. Verwerfen bleibt dem expliziten Abbrechen-Knopf vorbehalten. Vorrang haben nur offene Popover (Synonym-Menü/-Picker, Figur-Lookup) und ein laufender Save (`editSaving`) — mit verschiedenem Ausgang: ein offenes Popover **verwirft** den Exit-Griff, ein laufender Save **merkt ihn vor**. [listeners.js](../public/js/editor/focus/listeners.js)#`deferExitUntilSaved` fragt `editSaving` im Takt `EXIT_DEFER_POLL_MS` ab und ruft `exitFocusMode`, sobald der Save durch ist; geht in der Wartezeit ein Popover auf, endet der Modus auf anderem Weg oder ist `EXIT_DEFER_MAX_MS` erreicht, verfällt die Vormerkung. Der Timer liegt als `ctx.exitTimer` im ctx und fällt mit `_focusTeardown`. **Why:** ein Autosave nach einer Tipp-Pause fällt oft genau auf den Moment des Escape — verworfen sah das aus, als reagiere die Taste nicht. Exit mitten im PUT bleibt ausgeschlossen. Unterscheidung über `isFocusPopoverOpen` ([constants.js](../public/js/editor/focus/constants.js)), aus dem `isFocusExitBlocked` sich zusammensetzt.
    - **Die Vorrang-Regel gilt für BEIDE Chord-Pfade.** Der Toggle-Chord erreicht `exitFocusMode` auf zwei Wegen: über den Body-Listener ([trampoline.js](../public/js/editor/focus/trampoline.js)#`handleFocusHotkey`, der auch den Eintritt aus dem Lesemodus trägt) und über den Container-Listener ([listeners.js](../public/js/editor/focus/listeners.js)#`onKey`). `exitFocusMode` selbst kennt ausser dem State-Guard keine Vorbedingung — ein Guard in nur einem Pfad ist darum wirkungslos, der andere verlässt den Modus trotzdem. Vorbedingung deshalb als `isFocusExitBlocked` in [constants.js](../public/js/editor/focus/constants.js), SSoT neben `isFocusToggleChord`. Der Escape-Zweig prüft dieselben Felder bewusst inline, weil er zusätzlich den Figur-Lookup schliesst; wer die Feldliste erweitert, zieht ihn mit. **Der Eintritt bleibt ungegated:** ein laufender Save ausserhalb des Fokus darf ihn nicht blockieren, sonst ist der Modus während jedes Autosaves per Tastatur unerreichbar.
    - **Der Doppel-Dispatch des Chords im Fokusmodus ist bewusst.** Beide Listener feuern für dasselbe `keydown`; der zweite Aufruf läuft in den State-Guard (`_focusState !== 'active'`) und ist ein No-op. Der Body-Listener bleibt nötig, weil nur er den Eintritt aus dem Lesemodus kennt. Gegated: [tests/e2e/focus-editor.spec.js](../tests/e2e/focus-editor.spec.js) („Escape speichert und verlässt …", „Escape während editSaving wird vorgemerkt …", „Toggle-Chord während editSaving wird vorgemerkt …", „Vorgemerkter Exit verfällt …", „Vorgemerkter Exit: Teardown …"), [tests/unit/focus-chrome.test.mjs](../tests/unit/focus-chrome.test.mjs) (`isFocusExitBlocked`, `isFocusPopoverOpen` + `handleFocusHotkey`-Routing) und der Quelltext-Guard [tests/unit/editor-modes.test.mjs](../tests/unit/editor-modes.test.mjs) (beide Pfade müssen die geteilte Vorbedingung prüfen).
17. **Der near-Vollscan ist zustandsgated.** `applyBlockMarks` läuft weiterhin **jeden** Tick (Ghost-Klassen-Defense), aber `setNearBlocks` überspringt sein `querySelectorAll('.focus-paragraph-near')`, solange `ctx._marks.near === false` und kein Block gewünscht ist — also in jedem Tick ausserhalb von `window-3`. Gegated: [tests/e2e/focus-perf.spec.js](../tests/e2e/focus-perf.spec.js) (P4 + P4b) und [tests/unit/focus-granularity.test.mjs](../tests/unit/focus-granularity.test.mjs).
18. **Die Hervorhebung darf nie „einfach weg" sein.** (Ergänzt Invariante 15: dort geht es um den Ausgang des Exits, hier um jeden Tick davor.) Genau ein Block trägt `.focus-paragraph-active`, solange der Editor Fokus hat und die Granularität nicht `typewriter-only` ist — die CSS-Dim-Regel ist ein `:not(.focus-paragraph-active)`, ein Zustand ohne Markierung dimmt also den **ganzen** Text. Jeder Pfad, der Blöcke strukturell verändert (Split, Merge, Löschen, Undo/Redo, Paste, IME-Wortersatz), muss die Markierung **im selben Task** reparieren, nicht erst im RAF; wo das DOM bewusst nicht angefasst wird (Composition), gilt der Ist-Soll-Repair als Ausnahme. Das gilt symmetrisch: einzige erlaubte markierungsfreie Zustände sind `typewriter-only` und der absichtliche Blur-Clear. **Bewusst nur auf den aktiven Mark bezogen:** `blockMarksIntact` vergleicht `.focus-paragraph-active`, nicht die `-near`-Nachbarn von `window-3`. Ein Split-Ghost auf einem near-Block wird darum erst im nächsten RAF-Tick abgeräumt, nicht synchron — sichtbar wäre höchstens ein Frame mit einem zu vielen hellen Nachbarn, während der fehlende **aktive** Mark den ganzen Text dimmt. Nur Letzteres rechtfertigt den synchronen Eingriff. Gegated: [tests/e2e/focus-editor.spec.js](../tests/e2e/focus-editor.spec.js) („Merge-Löschung …", „Löschen während laufender IME-Composition …"), [tests/unit/focus-sentence.test.mjs](../tests/unit/focus-sentence.test.mjs) (`blockMarksIntact`/`repairBlockMarks`).

19. **Der Fokusmodus fährt eine EIGENE Undo-Historie, und `Cmd/Ctrl+Z` wird abgefangen.** Beides ist Pflicht, und zwar aus zwei unabhängigen Gründen:
    - **Der browsereigene Stack ist unter WebKit unbrauchbar grob.** WebKit (Safari/iOS/WKWebView) hält seinen TypingCommand offen, bis ein **echter Mausklick** kommt — eine ganze Tippstrecke ist dort EIN Undo-Schritt. Gemessen am 2026-08-22 gegen WebKit 26.x mit echten `NSEvent`-Anschlägen: 66 in einem Rutsch getippte Zeichen fielen einem einzigen `Cmd+Z` zum Opfer, `canUndo` war danach `false`. Einzeln gegengeprüft und **wirkungslos** als Schrittgrenze: Pfeiltasten, Enter, Backspace, Auto-Save, `blur()`/`focus()`, Fenster-Deaktivierung, JS-Selektions-Reset (`removeAllRanges` + `addRange`), `execCommand('bold')`, `insertText('')` und die nativen AppKit-Kommandos `moveLeft:`/`moveRight:`/`moveWordLeft:`. Nur der echte `leftMouseDown` trennte. Praktische Folge: wer eine Weile durchschreibt, ohne in den Text zu klicken, verliert mit einem versehentlichen `Cmd+Z` alles davon — und der Auto-Save (1,5 s) persistiert die Löschung anschliessend still weiter. Chromium ist von dieser Körnung nicht in dieser Härte betroffen, **Chromium-Tests sehen die Fehlerklasse also nicht** (gleiche Lage wie Invariante 9 / `focus-selection.webkit`). Betrifft **beide** Oberflächen: Safari/iOS-Web-SPA im Fokusmodus und den macOS-Client.
    - **`preventDefault` ist Verhalten, keine Formalie.** Ohne es laufen eigener und Browser-Stack parallel und ein `Cmd+Z` wirkt doppelt.
    Der Handler hängt am **Container** (nicht am Window), damit er vor dem document-Level-Dispatcher der Toolbar-Karte läuft, und verbraucht das Event per `stopPropagation` — dasselbe Muster wie `onSoftBreak`. **Welche** Historie er bedient, entscheidet der Aufrufer über `ctrl.focusUndo`/`focusRedo`: in der SPA die Session-Historie der Notebook-Karte (der Fokusmodus ist derselbe Edit-Vorgang auf einem gespiegelten Container — `_getEditEl` löst dorthin auf und `@input="_markEditDirty()"` schiebt die Snapshots schon dorthin, ein zweiter Stack wäre eine zweite Wahrheit), in der fremden Schale deren eigene Instanz. **Der Stack wird beim Speichern NICHT geleert** — hier wird ununterbrochen weitergeschrieben und alle 1,5 s automatisch gespeichert; ein Clear am Save nähme dem User genau die Schritte weg, die er zurückholen will. Zurückgesetzt wird nur bei Seitenwechsel und Unmount (Historie ist **pro Seite**). Snapshots sind rohes `innerHTML`, `data-bid` bleibt damit unangetastet — der 3-Wege-Merge des Clients hängt an stabilen IDs, eine Block-Neunummerierung im Restore-Pfad würde ihn brechen. Gegated: [tests/e2e/focus-undo.webkit.spec.js](../tests/e2e/focus-undo.webkit.spec.js), [tests/unit/edit-history.test.mjs](../tests/unit/edit-history.test.mjs).

## Bewusst nicht aufgeräumt

Damit die Entscheidung nicht jede Session neu diskutiert wird — diese Punkte sind bekannt und bleiben, weil die harte Regel „Focus-Editor ist stabilisiert" Änderungen ohne beobachtbares Verhalten ausschliesst und jeder Umbau hier Regressionsrisiko ohne Gegenwert bedeutet:

- Toter Re-Export `isEmptyParagraph` in [dom-blocks.js](../public/js/editor/focus/dom-blocks.js) (Quelle ist `shared/auto-slot.js`).
- `overlapsBand` und `SENTENCE_HL` sind exportiert, aber nur modul-intern genutzt.
- Die Facade [focus.js](../public/js/editor/focus.js) re-exportiert `shouldRecenterOnViewport`, `measureBoxGeometry` und `jumpToTrailingParagraph` nicht — die Unit-Tests importieren sie darum direkt aus dem Submodul.
- Das Invariante-5-Cleanup (`classList.remove` + `removeAttribute('class')` wenn leer) steht handkopiert an vier Stellen.
- Die Buchführung „Block auflösen → reparieren → `_lastBlock` nachziehen" existiert dreifach ([card.js](../public/js/editor/focus/card.js) imeSafe- und Normal-Zweig, [listeners.js](../public/js/editor/focus/listeners.js)#`repairMarksNow`) mit leicht unterschiedlicher null-Behandlung.

## Erweitern (Checkliste)

Neuer Granularitätsmodus, neue Hotkey, neuer Listener-Pfad:
1. Konstante in [constants.js](../public/js/editor/focus/constants.js) oder neues Sub-File anlegen — Submodule sind nach Verantwortung geschnitten (dom/sentence/typewriter/chrome/mirror/storage), nicht nach Reihenfolge.
2. **Neuer Granularitätsmodus:** Wert in `GRANULARITIES` ([chrome.js](../public/js/editor/focus/chrome.js)) ergänzen, CSS-Regel für `.focus-mode--<wert>` in [focus-mode.css](../public/css/editor/focus/focus-mode.css), Verhalten in `applyBlockMarks` ([recenter.js](../public/js/editor/focus/recenter.js)). Eintritt, SPA-`$watch` und `standalone.js#setGranularity` gehen alle über `applyGranularity` und ziehen automatisch mit. Sonstiger neuer Body-Class-Marker: in `markFocusChrome` add, in `unmarkFocusChrome` remove.
    - **Bringt der Modus eine neue Mark-Klasse mit, muss sie `focus-paragraph-`-präfigiert sein.** `stripFocusArtefacts` ([utils/html.js](../public/js/utils/html.js)) räumt am Persistenz-Chokepoint präfix-basiert ab; eine anders benannte Klasse landet im gespeicherten HTML und erzeugt Phantom-Revisionen. `clearAllFocusMarks` ([dom-blocks.js](../public/js/editor/focus/dom-blocks.js)) zählt die Klassen dagegen einzeln auf — dort mit ergänzen.
3. Wenn neuer Listener: ausschliesslich am `ctx.container` oder `window` registrieren mit `{ signal }` in [listeners.js](../public/js/editor/focus/listeners.js). KEIN globaler `window.addEventListener` ohne AbortController.
    - **Neuer Tastengriff:** in die Hotkey-Tabelle oben aufnehmen (sie ist als vollständig deklariert). Griffe, die den Modus **verlassen**, prüfen `isFocusExitBlocked` ([constants.js](../public/js/editor/focus/constants.js)) — und zwar in jedem Pfad, über den sie ankommen (Invariante 16).
4. State-Machine berühren? Generation-Check im async-Body Pflicht (`if (gen !== this._focusGen) return`).
5. CSS für neue Markierungs-Klasse in [focus-mode.css](../public/css/editor/focus/focus-mode.css) — selber `@layer components`, Container-Selektor ist `.focus-editor__content` (entkoppelt von Notebook-Editor / `.page-content-view`).
6. Tests in [tests/unit/editor-focus.test.mjs](../tests/unit/editor-focus.test.mjs) ergänzen (pure Helpers) und ggf. E2E-Case in [tests/e2e/focus-editor.spec.js](../tests/e2e/focus-editor.spec.js).
7. CLAUDE.md „Editor-Modi"-Tabelle prüfen — bei strukturellen Änderungen am Modus-Set Invarianten-Liste updaten.
