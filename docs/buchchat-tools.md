# Buch-Chat Tools (Agentic Mode)

Tool-Inventar für den Agentic Buch-Chat. Claude ruft pro Iteration Tools auf, deren Resultate als neue `user`-Turns im Loop landen. Schema-Definitionen (Anthropic-Tool-Format) für das Modell: [public/js/prompts/book-chat-tools.js](../public/js/prompts/book-chat-tools.js)#`BOOK_CHAT_TOOLS` (re-exportiert über `prompts/chat.js` und die Facade `public/js/prompts.js`). Implementierungen: [routes/jobs/book-chat-tools/](../routes/jobs/book-chat-tools/) (ein `tools-<bereich>.js` je Domäne, `TOOLS`-Map in [index.js](../routes/jobs/book-chat-tools/index.js)); sämtliche SQL-Abfragen der Tools in [db/book-chat/](../db/book-chat/) (ein Modul je Bereich: `analysis`, `catalog`, `figures`, `text`, `timeline`) bzw. in bestehenden `db/`-Modulen (`db/plot`, `db/motifs`, `db/draft-figures`, `db/page-revisions` …) — die Tool-Module selbst führen kein SQL aus. Agent: [routes/jobs/chat/book-chat-agent.js](../routes/jobs/chat/book-chat-agent.js)#`runBookChatJobAgent` (Buch-Chat-Achsen) auf dem geteilten Loop [routes/jobs/agentic-chat.js](../routes/jobs/agentic-chat.js)#`makeAgenticChatJob`; Dispatcher klassisch/agentisch: [routes/jobs/chat/book-chat.js](../routes/jobs/chat/book-chat.js)#`runBookChatJobDispatch`.

## Vertrag

Jede Tool-Funktion: `(input, ctx) → JSON-serialisierbares Objekt` (sync oder async). Dispatcher: `executeTool(name, input, ctx)` aus [book-chat-tools/index.js](../routes/jobs/book-chat-tools/index.js).

**Fehler:** `{ error: '<Text fürs Modell>', errorKey: 'chat.toolError.<fall>', errorParams? }`. `error` bleibt deutscher Klartext mit Handlungshinweis fürs Modell; `errorKey` (+ `errorParams`) ist für die Werkzeug-Liste im UI und steht in **beiden** Locales. Der Loop nimmt `errorKey`/`errorParams` vor dem Senden aus dem `tool_result` heraus und legt sie in `toolLog[]` ab; das Frontend übersetzt sie (`toolRows` in [book-chat.js](../public/js/chat/book-chat.js)), ohne Key zeigt es den Rohtext (unerwartete Ausnahme).

`ctx` (gebaut in `prepare` von [book-chat-agent.js](../routes/jobs/chat/book-chat-agent.js)):
- `bookId` — aus `chat_sessions.book_id` der aktiven Session.
- `sessionId` — `chat_sessions.id` der aktiven Session (für Tools mit Session-Bindung, z.B. `generate_image` → `chat_images`).
- `images` — Array, in das `generate_image` `{image_id,prompt,mime}` pusht; der Loop persistiert es in `context_info.images`.
- `userEmail` — Owner-Scope für alle Reads (Reviews, Ideen, Werkstatt sind user-scoped).
- `jobSignal` — `AbortController.signal`, wird vor jedem Tool-Call und im Loop geprüft.
- `resultCapChars` — Ergebnis-Deckel des Loops (`toolResultCap`); `executeTool` kürzt strukturiert darauf (siehe Truncation).
- `inputBudgetChars` — Input-Budget des effektiven Providers (Kapazitäts-`hint` von `list_chapters`).
- `citations` / `recherche` — von `final_answer` gefüllt, landen in `context_info` (siehe Endpunkt).
- `logger` — Job-Child-Logger.

## Truncation

1. **Strukturiert** — `_truncateResult(obj, maxChars)` ([book-chat-tools/shared.js](../routes/jobs/book-chat-tools/shared.js) → [truncate.js](../routes/jobs/book-chat-tools/truncate.js)), aufgerufen von den Tools selbst und noch einmal von `executeTool` mit `resultCapFor(ctx)` = min(`MAX_RESULT_CHARS`, `ctx.resultCapChars`). Reihenfolge: (a) das jeweils grösste Array auf oberster Ebene halbieren (`results`, `pages`, `items`, `chapters` …), bis es passt oder jedes Array nur noch ein Element hat — Skalarfelder (Summen, `hint`, `total_*`) bleiben stehen; (b) lange Strings stufenweise kürzen; (c) letzter Ausweg harter String-Schnitt. Kennzeichnung `truncated: true`, für `results` zusätzlich `total_results` (falls das Tool es nicht selbst setzt), für andere Felder `truncated_fields[key] = {shown,total}`. Endlich in jeder Stufe — keine Rekursion. Gegated: [tests/unit/book-chat-truncate.test.js](../tests/unit/book-chat-truncate.test.js).
2. **Hart im Loop** — [agentic-chat.js](../routes/jobs/agentic-chat.js) schneidet ein Ergebnis über `toolResultCap` ([book-chat-agent.js](../routes/jobs/chat/book-chat-agent.js)#`_toolResultCapChars` = `max(4000, inputBudgetChars / (maxIter · 6))`) als String ab. Weil Stufe 1 schon auf denselben Deckel kürzt, greift das praktisch nie; `toolLog[].truncated` meldet beide Fälle.
3. **Pro Runde** — höchstens `AGENT_MAX_TOOLS_PER_ROUND` (8) ausgeführte Aufrufe und zusammen höchstens `_roundResultCapChars` (ein Viertel von `inputBudgetChars`, mindestens zwei volle Einzelergebnisse) Ergebnis-Zeichen. Was darüber liegt, wird **nicht ausgeführt**, bekommt aber ein `tool_result` mit `is_error` und Hinweis «in der nächsten Runde erneut anfordern» (`errorKey` `chat.toolError.roundLimit`/`roundBudget`) — jeder `tool_use` braucht genau ein `tool_result`, sonst ist die Folgerunde ein 400. **Why:** der Prompt fordert gebündelte `get_chapter_text`-Aufrufe; ungedeckelt hängt eine einzige Runde mehr an, als das Fenster trägt, und erst der nächste Call merkt es.

`MAX_RESULT_CHARS = max(4000, INPUT_BUDGET_CHARS / 36)` — skaliert mit `MODEL_CONTEXT`. Listen-Limits (`MAX_SEARCH_RESULTS = 30`, `MAX_PAGES_PER_FETCH = 20`) bleiben fix (UI-Ergonomie). Ergebnisse so bauen, dass **Zusammenfassungen vorne** stehen (Einfüge-Reihenfolge überlebt auch den harten Schnitt).

## Buch- und User-Scope

Jedes Werkzeug mit `page_id`/`chapter_id`/`ids`-Input prüft die Zugehörigkeit zu `ctx.bookId`, **bevor** es Inhalt lädt: `get_pages` meldet eine fremde Seite wie eine fehlende (`missing`, ohne Text), `quote_passage`/`quote_match`/`list_revisions`/`diff_page_revisions`/`get_chapter_text` antworten mit Fehler, die Listen-/Such-Werkzeuge filtern im SQL auf `book_id`. **Why:** die IDs kommen vom Modell und damit indirekt aus jeder Userfrage — ohne Prüfung liest ein «zeig mir Seite 4711» das Manuskript eines fremden Buchs. Szenen, Figuren, Orte und Welt-Fakten sind Analyse-Daten **pro User**, der Embedding-Index hängt nur am Buch: `search_similar` und die Erst-Kontext-/RAG-Blöcke lösen Treffer über `resolveEntityTitle(kind, id, { userEmail })` auf, die eines Mitautors fallen weg (Recherche-Einträge sind buchweit geteilt und bleiben). Gegated: [tests/integration/book-chat-scope.test.js](../tests/integration/book-chat-scope.test.js).

## Erst-Kontext + Kosten-Leiter

**Der Agent startet nicht mehr bei null.** Vor der ersten Iteration holt `prepare` über [routes/jobs/chat/book-chat-retrieval.js](../routes/jobs/chat/book-chat-retrieval.js)#`preContextPassages` die semantisch nächsten Passagen zur aktuellen Frage — dieselbe Pipeline wie das Tool `search_similar` ([lib/semantic-retrieval.js](../lib/semantic-retrieval.js)#`semanticQuery`, `kinds: ['page','scene','figure','location','fact']`) — und legt sie als Block in den System-Prompt. `semanticQuery` liefert je Entität nur ihren besten Chunk; `withNeighbors` erweitert ihn um die Nachbar-Chunks (`chunk_ix ± 1`), damit die Antwort nicht an der Chunk-Grenze abreisst. Passt die Nachbarschaft nicht mehr unter den Zeichendeckel, bleibt der Treffer-Chunk allein.

- **Warum:** die häufigste Frageform ist eine schmale Faktenfrage («wie alt war Stefan», «wann hat Stefan die Schule abgeschlossen»). Ohne Erst-Kontext beginnt der Agent bei jeder davon mit einer Werkzeug-Runde und eskaliert im Zweifel auf `get_chapter_text` — ein Kapitel-Volltext kostet ein Vielfaches der einen Passage, in der die Antwort steht. Ein paar Tausend Tokens vorne sind billiger als eine einzige Volltext-Runde.
- **Grösse:** `jobs.book_chat.pre_rag_top_k` (Default 8) Treffer, hart gedeckelt auf `jobs.book_chat.pre_rag_chars` (Default 12000 Zeichen ≈ 3k Tokens). **`top_k = 0` oder `chars = 0` schaltet den Erst-Kontext ab** (Agent verhält sich wie vorher).
- **Non-fatal:** kein Embedding-Index, Backend down oder keine Treffer → der Block sagt das ausdrücklich, und der Agent arbeitet rein über seine Werkzeuge. Der Block **fehlt nie ganz**: ein fehlender Block liest sich für das Modell wie «kein Index» und führt direkt zu den Volltext-Werkzeugen.
- **Cache-Lage (Pflicht-Invariante):** `buildBookChatAgentSystemPrompt` liefert **einen** System-Block (`ttl: '1h'`) mit dem über die Session stabilen Anteil (System, Strategie, Figuren, **Welt-Fakten**, Review, `final_answer`-Pflicht). Der Erst-Kontext (`buildBookChatPreContext`) trägt pro Frage andere Bytes und steht darum **nicht** im System, sondern als eigener Textblock **vor der Frage in deren User-Nachricht** (`userPreamble` des Loops; persistiert wird nur die Frage). So sind Werkzeuge + System + bisheriger Verlauf ein stabiler Präfix über alle Iterationen **und** Turns; den Verlauf deckt ein eigener Breakpoint am Historien-Ende (`cacheHistory`, siehe „Claude-/Opus-Call“). Stünde der Erst-Kontext im System, bräche er den Präfix direkt hinter Block 1 — der ganze Verlauf würde jeden Turn neu bezahlt.
- **Suchtext = Frage + letzte Runde** (`retrievalQuery` in [book-chat-retrieval.js](../routes/jobs/chat/book-chat-retrieval.js), geteilt von allen RAG-Pfaden: Buch-Chat klassisch + agentisch, Plot-Chat klassisch + agentisch, Buch-Kontext des Abschnitts-Chats): vorige User-Frage (≤ 400 Zeichen) + Anfang der vorigen Antwort (≤ 300) + aktuelle Frage. **Why:** Folgefragen («und wie alt war sie da?») tragen ihr Subjekt nicht selbst. User-Scope wie `search_similar` (siehe „Buch- und User-Scope“).
- **Sichtbar:** `context_info.pre_context = {count, chars}` → Plakette «Erst-Kontext: N Stellen» neben den Werkzeug-Plaketten ([public/partials/chat.html](../public/partials/chat.html)). Damit lässt sich im Verlauf ablesen, ob eine Antwort ohne Werkzeug-Runde zustande kam.

**Welt-Fakten-Block** ([public/js/prompts/chat.js](../public/js/prompts/chat.js)#`buildWeltfaktenBlock`): die etablierten Welt-Fakten des Buchs (`world_facts`) im **stabilen Block 1**, gedeckelt über `weltfaktenBlockChars` ([routes/jobs/chat/shared.js](../routes/jobs/chat/shared.js), 10 % des Input-Budgets, Minimum 2000 Zeichen — kein eigenes App-Setting, gleiche Ableitung wie der Figuren-Deckel), im agentischen Pfad zusätzlich absolut gedeckelt auf `AGENT_WELTFAKTEN_MAX_CHARS` ([routes/jobs/chat/book-chat-agent.js](../routes/jobs/chat/book-chat-agent.js)). **Why:** auf einem 1M-Fenster griffen die 10 % nie, und ein ausanalysiertes Buch trug mehrere hundert Fakten in jede Iteration; den Rest holt `list_world_facts` gezielt. **Why Block 1 und nicht Erst-Kontext:** die Fakten hängen am Buch, nicht an der Frage — im ungecachten Erst-Kontext-Block würde derselbe Inhalt jede Iteration neu bezahlt. Zwei Regeln: was der Deckel geschluckt hat, wird im Block ausgewiesen (die Weltgesetze `regel`/`technik` stehen vorn, damit zuerst das Beiwerk fällt), und ein **nicht erhobener** Index liefert **keinen** Block — ein leerer würde als «diese Welt hat keine Regeln» gelesen (dass der Index fehlt, sagt `list_world_facts`, wenn der Agent fragt).

**Kosten-Leiter im System-Prompt** ([public/js/prompts/chat.js](../public/js/prompts/chat.js)#`buildBookChatAgentSystemPrompt`): Stufe 1 = Erst-Kontext + Figuren-/Welt-Fakten-/Review-Block (gratis, schon da) → Stufe 2 = gezielte Index-Tools, die Passagen liefern (`search_similar`, `search_passages`, `get_figure_profile`, `get_figure_mentions`, `get_timeline`, `quote_match`) → Stufe 3 = Volltext (`get_pages`, `get_chapter_text`). Schmale Faktenfragen werden auf Stufe 1 oder 2 beantwortet.

**Aussenwelt-Regel** (`BOOK_CHAT_OUTSIDE_WORLD_RULE` in [prompts/book-chat-tools.js](../public/js/prompts/book-chat-tools.js), im Job an Block 1 gehängt): der Buch-Chat hat **keine Web-Suche**. Fragen zu realen Ereignissen/Fakten ausserhalb des Manuskripts beantwortet er nur, soweit das Buch etwas dazu sagt, sagt das offen und setzt in `final_answer` `recherche_hinweis: true` + `recherche_frage` — das Frontend bietet dann «Im Recherche-Chat fragen» an (Übergabe: [chats.md](chats.md#übergabe-buch-chat--recherche-chat)). **Ausnahme Lebensnormen:** allgemeine Normen (Einschulung ~6, Volljährigkeit, Pensionsalter …) darf er als Prüfmassstab an die Buchdaten anlegen («wann sollte X eingeschult werden?»), als Allgemeinwissen gekennzeichnet, Alter via `get_figure_age` — ohne Recherche-Hinweis. **Why:** sonst wich er gerade der Plausibilitätsfrage aus, für die Lebenslauf und Alters-Index da sind.

**Der `hint` aus `list_chapters` ist eine Kapazitätsaussage, kein Auftrag.** «Das ganze Buch passt in den Kontext» nennt darum zuerst die Bedingung (die Frage muss den ganzen Text sichten müssen) und danach die Erlaubnis — sonst wird Voll-Lektüre der Standardweg und ein einzelner Fakt kostet ein Kapitel. Die Voll-Lektüre-Strategie bleibt für ihren eigentlichen Fall bestehen: Auswahl oder Vollständigkeit über das ganze Buch (lustigste/schönste Stelle, alle Stellen zu X, Zusammenfassung, Ton des Buchs). Stellen nach einer Eigenschaft ohne Stichwort-Signatur (Beispiele für ein Stilmittel, eine Stimmung, ein Motiv, Umschreibungen) sucht der Agent dagegen zuerst mit `search_similar` und grossem `snippet_chars` (STRATEGIE-Zeile im System-Prompt, Werkzeug-Beschreibungen von `search_passages`/`search_similar`).

## Loop-Constraints

- Max. Tool-Iterationen: App-Setting `jobs.book_chat.max_tool_iter` (Default 12). Für Provider der Klasse `local` klemmt `jobs.book_chat.max_tool_iter_local` (Default 6) zusätzlich nach unten — ohne Prompt-Caching kostet jede Iteration den vollen Prompt erneut. Erschöpft ohne `final_answer` → **erzwungene Synthese-Runde**: nur noch `final_answer` als Werkzeug, Aufforderung `BOOK_CHAT_FORCE_FINAL_INSTRUCTION`.
- **Kosten-Deckel pro Antwort:** `jobs.book_chat.max_input_tokens_per_answer` (Default 500 000, 0 = aus; Admin → Jobs) begrenzt die **kumulierten** Input-Tokens aller Iterationen einer Antwort (cache-inklusiv, derselbe Wert wie die Token-Anzeige). Erreicht → die Ergebnisse der laufenden Runde werden noch angehängt, dann dieselbe Synthese-Runde wie beim Iterationsdeckel (Aufforderung `BOOK_CHAT_BUDGET_FINAL_INSTRUCTION`) — kein Hart-Abbruch. Die Synthese-Runde selbst kommt noch obendrauf. Daneben bleibt `jobs.book_chat.token_budget` der **Pro-Iteration**-Schutz des Kontextfensters.
- **Reihenfolge in einer Runde** ([agentic-chat.js](../routes/jobs/agentic-chat.js)): (1) `pause_turn` (serverseitiges Werkzeug pausiert, nur Recherche-Chat/Web-Suche) → Assistant-Inhalt anhängen, nächste Runde, kein Abschluss; (2) `final_answer` vorhanden → **erst** die übrigen Werkzeuge derselben Runde ausführen (Seiteneffekte in `ctx`: `generate_image`, `propose_research_item`), dann `final_answer` auswerten — auch wenn die Runde das Kontext-Budget überschritten hat; (3) Prosa-Abschluss; (4) Kontext-Budget überschritten → diese Werkzeug-Runde **nicht** mehr ausführen (der Erzähltext davor ist keine Antwort) und in die Synthese-Runde; (5) Werkzeuge ausführen, Kosten-Deckel prüfen. **Vor** jedem weiteren Call schätzt der Loop den Prompt (System + Werkzeugkatalog + Nachrichten, `charsPerToken`); läge er über `token_budget`, geht er direkt in die Synthese, die die Ergebnisse der letzten Runde bei Bedarf aufs Budget kürzt (die `tool_result`-Blöcke bleiben stehen). Ein `final_answer` mit kaputtem Argument-JSON (`parseError`) ist keine Antwort: in der Schleife läuft er als fehlgeschlagenes Werkzeug und das Modell ruft ihn neu, in der Synthese-Runde wird er zum Job-Fehler `job.error.agentFinalAnswerInvalid`; andere Werkzeuge mit `parseError` werden nicht mit `{}` ausgeführt, sondern bekommen ein ehrliches Fehler-`tool_result`. Die Synthese-Runde prüft `truncated` wie jede Runde (`job.error.aiTruncated`); ein Provider-Fehler dort endet als Job-Fehler (`job.error.agentSynthesisOverloaded` bzw. `…agentSynthesisFailed`, i18n-keyed Fehler unverändert) — nie als gespeicherte Platzhalter-Antwort. Eine leere Antwort wird nie roh gespeichert, sondern als `__i18n:chat.errors.emptyAnswer__`. Der Abbruchgrund steht in `context_info.stop_reason` (`final_answer|prose|max_iter|input_cap|context_budget`); für `input_cap`, `max_iter` und `context_budget` zeigt die Antwortzeile einen Hinweis (`_bookChatStopNote`). Gegated: [tests/unit/agentic-chat-loop.test.js](../tests/unit/agentic-chat-loop.test.js).
- **Kosten gescheiterter Läufe:** endet ein Lauf ohne Assistant-Nachricht (Fehler, Abbruch, Truncation), bucht der Loop den bis dahin verbrauchten Input/Output über `recordChatLedgerForFailedRun` ([db/cost-ledger.js](../db/cost-ledger.js), `source_ref = chatjob:<jobId>`) ins Ledger — sonst fehlten gerade die teuersten Läufe im Budget-Gate.
- **Verlauf** (`buildAgenticHistory`, geteilt von agentischem und klassischem Pfad): Anker (erste Runde) + die letzten 10 Nachrichten, **Rollen strikt alternierend ab `user`** (führende Antworten des Tails fallen weg). Gespeicherte Fallback-Marker (`__i18n:…__`) erscheinen dem Modell als neutraler Platzhalter, und an frühere Antworten hängen ihre gültigen Belege (`context_info.citations`, höchstens 6 à 160 Zeichen) als `[Belege dieser Antwort: …]` — Folgefragen kennen so die Stellen, auf die sich die Antwort stützte.
- **Opt-in-Hooks des Loops** (Recherche-Chat): `prepare` darf `toolsForIter({ iter, webSearches })` liefern (Werkzeugliste pro Runde; die Synthese-Runde bietet immer nur `final_answer` aus `tools`); `buildContextInfo` bekommt neben `webSearches`/`webResults` auch `webQueries` (Suchanfragen der `server_tool_use`-Blöcke).
- Aktivierung (`_bookChatUseAgent`): `providerSupportsTools(effektiver Provider)` und `jobs.book_chat.mode != 'classic'`. Werkzeuge können `claude` (native `tool_use`-Blöcke) und `openai-compat` (OpenAI-Function-Calling, Schalter `ai.openai-compat.tools`); Ollama und `mode='classic'` nutzen den klassischen Single-Pass-Chat ohne Tools (`runBookChatJob`). Lehnt ein Endpunkt Werkzeuge ab, übernimmt derselbe klassische Pfad den Job (`AI_TOOLS_UNSUPPORTED` → `fallbackJob`), statt ihn scheitern zu lassen — nur solange noch kein Call geantwortet hat. Wire-Format-Details des openai-compat-Pfads: [ai-providers.md](ai-providers.md#tool-use).
- **Werkzeugsatz** (`jobs.book_chat.tool_set` = `auto|slim|full`): `auto` gibt Cloud-/Frontier-Modellen den vollen Katalog und lokalen den **Slim-Satz** — 18 Werkzeuge, SSoT `BOOK_CHAT_SLIM_TOOL_NAMES` in [prompts/book-chat-tools.js](../public/js/prompts/book-chat-tools.js) (Überblick, Suche in Wortlaut + Sinn, Volltext, Zitat-Verifikation, Figuren-Achse inkl. `get_figure_age`, Orte/Szenen, **Welt-Fakten**, Bewertung, `final_answer`). `list_world_facts` ist dort, weil es schon verdichtete Buchaussagen liefert statt Passagen, die erst gelesen werden müssen — ohne das Werkzeug eskaliert ein kleines Modell für «welche Regel gilt hier» auf `get_chapter_text`. **Why:** der volle Katalog kostet ~10 000 Input-Tokens **pro Iteration**, die ein Endpunkt ohne Caching jede Runde neu bezahlt, und ein kleineres Modell wählt aus der kleinen Auswahl zuverlässiger als aus dem vollen Katalog. Keine zweite Definitionsliste — nur Namen, Drift gegated durch `tests/unit/ai-tool-translate.test.js`. Der System-Prompt bekommt die tatsächlich angebotenen Namen (`opts.toolNames`) und empfiehlt nur diese; bei lokaler Prompt-Variante kommt ein Block **Werkzeug-Disziplin** dazu (keine erfundenen Namen, Aufruf nie als Text, Abschluss via `final_answer`). Gelaufener Satz + Anzahl stehen in `context_info.tool_set`/`tools_offered`.
- Per-Job-Claude-Override (analog Komplettanalyse): `ai.claude.model.bookchat` / `…context_window.bookchat` / `…max_tokens_out.bookchat` / `…timeout_ms.bookchat` / `…effort.bookchat` (App-Settings, leer/0 = folgt global). Greift nur bei `ai.provider = claude`, für **beide** Buch-Chat-Pfade (klassisch + agentisch). Gebunden via `setContext` in [routes/jobs/chat/book-chat.js](../routes/jobs/chat/book-chat.js)#`_applyBookChatAiOverrides` **vor** `getContextConfigFor`, damit Token-Budget/Tool-Result-Cap das Override-Kontextfenster reflektieren. Kein eigener Timeout-Default (anders als komplett). So läuft z.B. der Tool-Loop auf Opus, während global Sonnet 4.6 fürs Lektorat bleibt.

## Claude-/Opus-Call (Tool-Use)

Der agentische Loop ruft `callAIWithTools` → bei Claude `_callClaudeWithToolsAttempt` ([lib/ai.js](../lib/ai.js)) — ein **eigener Pfad** neben dem Nicht-Tool-`_callClaudeAttempt`. Wer den Buch-Chat auf Opus optimiert, fasst diesen Pfad an, nicht den Nicht-Tool-Pfad. Die folgenden vier Punkte sind Claude-API-Eigenheiten; der openai-compat-Pfad hat weder Thinking-Blöcke noch Caching noch `effort` (sein Wire-Format: [ai-providers.md](ai-providers.md#tool-use)).

- **Adaptive Thinking:** auf Opus 4.7+ sendet der Tool-Pfad `thinking:{type:'adaptive'}` (Modell-Erkennung `_claudeUsesAdaptiveThinking`, identisch zum temperature-Verbot). **Pflicht-Invariante:** die im Stream erfassten `thinking`/`redacted_thinking`-Blöcke (inkl. `signature`) werden in `rawContentBlocks` in Originalreihenfolge zurückgespielt — der assistant-Turn MUSS mit dem Thinking-Block beginnen, sonst quittiert die Folge-Iteration mit HTTP 400. Sonnet 4.6 / Opus 4.6 / lokale Provider: kein `thinking`-Feld → unverändert. **Folge:** Thinking zählt gegen `max_tokens_out` — Output-Cap (`…max_tokens_out.bookchat`) großzügig halten (≥ 32–64K), sonst Truncation-Wurf.
- **Prompt-Caching (Multi-Turn):** System + Tools tragen einen Cache-Breakpoint (über `_buildClaudeSystemBlocks`); zusätzlich setzt `_withMessageCacheBreakpoints` pro Iteration einen Breakpoint auf den letzten Block der letzten Nachricht — die wachsende `tool_result`-History wird damit ab Iteration 2 aus dem Cache gelesen statt voll bezahlt — und einen auf jede mit `cacheBreakpoint: true` markierte Nachricht (Buch-Chat: Ende des Verlaufs vor der aktuellen Frage, `cacheHistory`). Damit liest der **nächste Turn** Tools + System + Verlauf aus dem Cache, obwohl Frage und Erst-Kontext neu sind (Render-Order tools→system→messages; 3 von max 4 Breakpoints, das Limit rechnet die Funktion gegen die System-Breakpoints). Die Markierung ist kein API-Feld und wird immer entfernt; openai-compat ignoriert sie. Nur der Tool-Pfad; das Original-`messages`-Array bleibt unangetastet (geklont).
- **effort:** `ai.claude.effort.bookchat` (`low|medium|high|xhigh|max`) → `output_config.effort`, nur für den Buch-Chat (ALS-Override `claudeEffort`; andere Jobs unberührt). Tier-Mismatch wird geklemmt (`max`→Opus-only, `xhigh`→Opus-4.7+, sonst `high`) statt 400. Leer = API-Default (`high`).

## Tools

38 Tools, gruppiert nach Domäne. Alle Read-Only ausser `final_answer` (Pflicht-Endpunkt, kein DB-Read) und `generate_image` (Seiteneffekt + externer Bild-Call — bewusste Ausnahme zum Read-Only-/deterministisch-/kein-KI-Call-Vertrag, siehe unten).

### Endpunkt

| Tool | Input | Zweck | Quelle |
|------|-------|-------|--------|
| `final_answer` | `antwort: string`, `zitate?: [{page_id, offset, length, quote}]`, `recherche_hinweis?: bool`, `recherche_frage?: string` | Pflicht-Endpunkt der Loop: Modell ruft das Tool als letzten Schritt mit der finalen Antwort an den User. Der Loop fängt es vor `executeTool` ab; stehen in derselben Runde weitere Werkzeuge, laufen **die zuerst** (Seiteneffekte), dann terminiert `final_answer`. **Halluzinationsschutz:** Wenn `zitate` mitgeliefert wird, validiert `validateFinalAnswerCitations` (Content-Store-Reload pro Seite, Buch-Scope) jeden Eintrag — `text.slice(offset, offset+length) === quote`. Stimmt das Zitat, aber nicht die Position, wird es **neu verankert** statt verworfen (exakt an der nächsten Fundstelle zum genannten `offset`, sonst tolerant gegenüber Anführungs-/Strich-/Whitespace-Varianten via [lib/quote-verify.js](../lib/quote-verify.js); `relocated: 'exact'|'tolerant'`, mindestens 12 Zeichen). **Why:** verzählte Offsets sind der häufigste `quote_mismatch`; die Neu-Verankerung kostet keinen KI-Call (ein zweiter Synthese-Turn schon) und zeigt das gemeinte Zitat — `actual` wäre der Text an der falschen Stelle. Ergebnis: `citation_validation` + `citations_invalid` im `toolLog`, und **als Fussnoten** in `context_info.citations[{n, page_id, page_name, quote, valid, reason?}]` (Seitenname/Sprungziel nur für Seiten des eigenen Buchs, Zitat ≤ 400 Zeichen). Ungültige werden nicht verworfen, sondern im UI markiert. `recherche_hinweis`/`recherche_frage` (Aussenwelt-Regel) → `context_info.recherche_hinweis`/`recherche_frage`. | – (kein DB-Read; Validierung nutzt Content-Store) |

3. **Kein SQL im Tool-Modul** — weder auf `pages`/`chapters`/`books` (auch kein blosser Namens-JOIN, Root-CLAUDE.md „Content-Store-Facade als einziger Eintrittspunkt") noch auf abgeleitete Tabellen (figures, locations, page_stats, continuity_*, zeitstrahl_*, world_facts …). Das Tool importiert weder den `db`-Handle (aus `db/connection` oder `db/schema`) noch ruft es `db.prepare`/`db.exec`. Die Abfrage gehört als benannte Funktion ins Bereichsmodul unter [db/book-chat/](../db/book-chat/) (statische Statements einmal auf Modulebene vorbereitet, optionale Filter und IN-Listen baut die Funktion); vorhandene Lookups zuerst wiederverwenden, wenn SQL, Reihenfolge und Felder wirklich übereinstimmen ([db/content-names.js](../db/content-names.js), [db/books.js](../db/books.js)#`getBookName`, `getBookSettings`/`worldFactsScanState` aus `db/schema`). Seitentext lädt das Tool über `contentStore.loadPage`. Gegated durch [tests/unit/book-chat-tools-content-sql.test.mjs](../tests/unit/book-chat-tools-content-sql.test.mjs).
4. Schema in [prompts/book-chat-tools.js](../public/js/prompts/book-chat-tools.js)#`BOOK_CHAT_TOOLS` ergänzen: `name`, `description` (kostet Input-Tokens — knapp halten, aber **Beispiele** für „wann nutzt das Modell mich" reinpacken), `input_schema`. Property-Descriptions geben Default-/Max-Werte an, damit das Modell sie nicht aus Resultaten zurückrechnen muss.
5. Result-Shape so wählen, dass die strukturierte Kürzung greift: Zusammenfassungsfelder (`total_*`, `hint`) **vor** die Listen, Listen als Arrays auf oberster Ebene (`results`, `pages` …) — die werden halbiert statt als String abgeschnitten. Eine fremde `page_id`/`chapter_id` vor dem Laden gegen `ctx.bookId` prüfen (siehe „Buch- und User-Scope“).
6. Bei Content-Store-/DB-Reads `userEmail`-Scope nicht vergessen — alle user-scoped Daten (Reviews, Ideen, Werkstatt, Lektorat-Checks) sind pro User isoliert.
7. `jobSignal` ist im Loop bereits überwacht; lange Reads sollten ihn dennoch konsultieren wenn praktikabel.
8. Der [Plot-Chat](plot-chat.md) nutzt dieselben Handler, bietet aber nur eine Teilmenge an: soll er das neue Werkzeug auch haben, den Namen in [prompts/plot-chat.js](../public/js/prompts/plot-chat.js)#`PLOT_CHAT_READ_TOOL_NAMES` (und ggf. `PLOT_CHAT_SLIM_READ_TOOL_NAMES`) ergänzen.

## Frontend

Buch-Chat-Karte ([public/partials/chat.html](../public/partials/chat.html), Zusätze pro Antwort per String-Include [book-chat-msg-extras.html](../public/partials/book-chat-msg-extras.html), Methoden [public/js/chat/book-chat.js](../public/js/chat/book-chat.js)). Quelle ist `chat_messages.context_info` (JSON) der Antwort:

- **Plaketten**: Erst-Kontext + Werkzeuge gruppiert (`_toolSummary`).
- **Werkzeug-Verlauf** (klappbar, `collapsible`): jede Zeile Name, Runde, Dauer, «gekürzt»/«Fehler» und die Argumente (gekürzt, `x-text`). `final_answer` erscheint nicht — es ist die Antwort.
- **Belege**: nummerierte Fussnoten aus `context_info.citations`, Link springt via `$app.gotoPageById`; ungültige Zitate durchgestrichen + Plakette «nicht bestätigt».
- **Recherche-Hinweis**: bei `recherche_hinweis` (und aktivem Recherche-Chat) Knopf «Im Recherche-Chat fragen» → Window-Event `EVT.RESEARCH_CHAT_ASK` (siehe [chats.md](chats.md#übergabe-buch-chat--recherche-chat)).
- **Abbruchgrund** (`stop_reason` `input_cap`/`max_iter`) als Hinweiszeile, **Kosten** der Antwort (`context_info.cost_usd`, nur Claude, aus [lib/pricing.js](../lib/pricing.js) zur Schreibzeit) in der Token-Zeile.
- **Abbrechen**: Knopf im Kartenkopf, solange die sichtbare Session läuft — Job-ID über `/jobs/active?type=book-chat&book_id=<sessionId>`, Abbruch über die Root-Mechanik `$app.cancelJob` (`DELETE /jobs/:id`).

Alle KI-/User-Felder laufen über `x-text`; die Antwort selbst über `_renderChatMarkdown` (escaped zuerst).
