# Shell- und Content-Cache (Service Worker)

Code: [public/sw.js](../public/sw.js), [public/sw-offline.js](../public/sw-offline.js), [public/sw-manifest.js](../public/sw-manifest.js), [scripts/sw-manifest.js](../scripts/sw-manifest.js), [public/js/repo/content.js](../public/js/repo/content.js), [public/js/app/boot/](../public/js/app/boot/).

- **Shell-Cache: kein manueller Bump** — `SHELL_CACHE` leitet sich aus dem Content-Hash `__SHELL_BUILD` in [public/sw-manifest.js](../public/sw-manifest.js) ab (generiert via `npm run sw:manifest`, läuft automatisch auf `prestart`). Jede Asset-Änderung (JS/Partial/CSS/i18n/Icon-Sprite/index.html) verschiebt den Hash → neue SW-Generation, ohne dass man eine Konstante hochzählt. Der SW precacht den vollständigen kohärenz-kritischen Asset-Satz atomar beim Install und serviert ihn **cache-only** — ein lazy-gefetchtes Partial oder dynamisch importiertes Modul zieht nie eine fremde Generation vom Netz (verhindert „neues Partial trifft altes JS-Modul"-Skew → ReferenceError). Drift zwischen [public/sw-manifest.js](../public/sw-manifest.js) und einem frischen Scan ist durch [tests/unit/sw-manifest-drift.test.mjs](../tests/unit/sw-manifest-drift.test.mjs) gegated (Teil von `test:unit` → blockiert den Deploy-Job); nach Asset-Änderungen lokal `npm run sw:manifest` laufen lassen und das Ergebnis **mitcommiten**. **Im Entwicklungsprozess passiert das automatisch:** ein PostToolUse-Hook ([.claude/settings.json](../.claude/settings.json) → [scripts/hooks/regen-sw-manifest.js](../scripts/hooks/regen-sw-manifest.js)) regeneriert das Manifest nach jeder `Edit`/`Write`/`MultiEdit`-Änderung an einem Shell-Asset (partials/*.html, js/**.{js,mjs,json}, css/**.css, icons.svg, index.html); Backend-/Test-/Doku-Edits lösen ihn bewusst nicht aus (kein Hash-Einfluss). Der regenerierte `public/sw-manifest.js` muss dann nur noch mitcommittet werden — manuelles `npm run sw:manifest` bleibt nötig, wenn der Hook deaktiviert ist (`/hooks`) oder ein Asset ausserhalb der Editor-Tools geändert wurde. Prod regeneriert **nicht** beim App-Start (systemd-Unit startet via `node server.js`, das `prestart`-Hook greift nur bei lokalem `npm start`) — stattdessen ruft [deploy/deploy.sh](../deploy/deploy.sh) nach `npm install` explizit `node scripts/sw-manifest.js` auf, sodass Prod den Hash aus dem deployten Asset-Stand selbst regeneriert. vendor/* + fonts/* bleiben bewusst aus dem Manifest (self-contained) und liegen im generationsunabhängigen `VENDOR_CACHE` (cache-first), sodass sie nicht bei jedem Deploy mit dem `SHELL_CACHE` weggeworfen und neu geladen werden. Weil ihn kein Generationswechsel mitnimmt, räumt der SW ihn beim `activate` selbst auf (`pruneVendorCache`): Einträge, deren Pfad nicht mehr in `__VENDOR_SET` steht (vom Generator aus `vendor/` + `fonts/` gelistet, **nicht** Teil des Build-Hashes), fallen weg — sonst bliebe jede ersetzte Vendor-Version für immer liegen. Fehlt die Liste, bleibt der Cache unangetastet. Gegated durch [tests/unit/sw-vendor-prune.test.mjs](../tests/unit/sw-vendor-prune.test.mjs).

- **Der Precache ist begrenzt parallel, wiederholt pro Asset und meldet sein Scheitern selbst** ([public/sw.js](../public/sw.js)#`precacheWithRetry`/`reportInstallFailure`). Höchstens `PRECACHE_CONCURRENCY` Requests gleichzeitig, jedes Asset bis zu `PRECACHE_ATTEMPTS`-mal; erst ein endgültig scheiterndes Asset bricht den Rest ab, geschrieben wird weiterhin nur der vollständige Satz. Scheitert der Install im Precache, postet der SW selbst nach `/telemetry/js-error` (`kind='boot'`, `SW-Install gescheitert: … [build= ok=n/N]`, `source` = das Asset). **Why:** ein gescheiterter Erst-Install hinterlässt nichts Sichtbares — die Seite bleibt einfach ohne Controller, revalidiert bei jeder Navigation den ganzen Satz vom Netz und ist offline tot; ein Install ohne Session scheitert dagegen absichtlich und wird nicht gemeldet. Den Client-Zustand zeigen die `boot`-Einträge in `js_errors` (`sw=controlled|uncontrolled`). Gegated durch [tests/unit/sw-shell-coherence.test.mjs](../tests/unit/sw-shell-coherence.test.mjs).
- **Eine verlorene Generation heilt der SW selbst, nicht der Client** ([public/sw.js](../public/sw.js)#`GENERATION_COMPLETE_PATH`/`repairGeneration`). Der Install legt als letzten Eintrag eine Vollständigkeits-Marke ab. Fehlt sie im Cache des laufenden SW, ist die Generation als Ganzes weg (Cache-Wurf der Heilungspfade in [boot/sw-register.js](../public/js/app/boot/sw-register.js)#`applyUpdate` und [failsafe-reveal.js](../public/js/failsafe-reveal.js), Storage-Druck) — dann gehen Shell **und** Assets ungecacht ans Netz, **ohne** `shell-incoherent`, und der SW füllt im Hintergrund nach. Nachgefüllt wird nur, wenn der Server noch genau diesen Build meldet (`/sw-manifest.js`); ist er weiter, gibt es nur `registration.update()`, sonst lägen Bytes einer fremden Generation in diesem Cache. **Why:** `unregister()` ist kein verlässlicher Neustart — Chromium holt die Registrierung beim nächsten `register()` derselben Script-URL ohne Install zurück. Ohne Marke lief derselbe SW mit leerem Cache weiter: jeder Asset-Request ein Miss, jede Meldung ein Reload, der Banner-Klick ohne wartenden SW wieder in denselben Cache-Wurf — heraus kam nur Ctrl-F5. `shell-incoherent` bleibt für die echte Einzel-Eviction in einer sonst vollständigen Generation. Gegated durch [tests/unit/sw-shell-coherence.test.mjs](../tests/unit/sw-shell-coherence.test.mjs).

- **Ein wartender SW wird eingespielt, sobald nichts verloren geht — nicht erst auf Klick** ([boot/update-policy.js](../public/js/app/boot/update-policy.js) entscheidet, [boot/sw-register.js](../public/js/app/boot/sw-register.js) führt aus). Der SW selbst macht kein `skipWaiting`; aktiviert wird per `skip-waiting`-Nachricht, den Reload macht `controllerchange` in jedem Tab nach dessen eigener `isBusy`-Prüfung. Aktiviert wird: beim Boot sofort, wenn schon ein SW wartet; danach, sobald der Tab im Hintergrund liegt oder `AUTO_APPLY_IDLE_MS` keine Eingabe kam; und aus dem Build-Guard bzw. `shell-incoherent` (`requestCoherentReload` aktiviert zuerst, statt nur neu zu laden). Wer editiert (Edit-/Fokusmodus, `editDirty`), bekommt nur das Banner. **Why:** ein Reload aktiviert keinen wartenden SW — der alte kontrolliert die Seite über den Reload hinweg, und auch ein neuer Tab bekommt die alte Generation, solange ein Tab offen ist. Wer das Banner übersah, blieb beliebig lange auf dem alten Stand, und der Build-Guard lud nur dieselbe alte Shell neu.
- **Kein Tab spielt ein Update ein, während irgendein Tab editiert** ([boot/busy-lock.js](../public/js/app/boot/busy-lock.js)). `skip-waiting` wechselt die Generation für **alle** Tabs der Origin, und `activate` wirft die alte weg. Jeder Tab, der laut `isBusy` editiert, hält darum den Web Lock `schreibwerkstatt-sw-busy` geteilt (abgeglichen im Sekundentakt und bei jeder Eingabe); `activateWaiting` aktiviert nur, wenn es denselben Lock exklusiv mit `ifAvailable` bekommt. Gilt für Auto-Apply, Boot-Pfad und `requestCoherentReload`; der Banner-Klick (`applyUpdate`) und das Pflicht-Update bleiben ausdrückliche Entscheidungen und gehen durch. `isBusy` kennt neben Notebook- und Focus-Editor (Root-Felder) auch den Bucheditor über `registerBusySource` ([update-policy.js](../public/js/app/boot/update-policy.js)) — dessen Block-Zustand liegt nicht an der Root. **Why:** ein Hintergrund-Tab (Auto-Apply) oder ein frisch geöffneter zweiter Tab (Boot-Pfad) zog dem schreibenden Tab sonst die Generation unter den Füssen weg: alte Module im Speicher, neue Partials vom SW → `ReferenceError`. Ohne Web Locks entscheidet der eigene Tab allein. Gegated durch [tests/unit/busy-lock.test.mjs](../tests/unit/busy-lock.test.mjs).
- **Buch offline halten** ([public/sw-offline.js](../public/sw-offline.js), Client [app/app-offline-books.js](../public/js/app/app-offline-books.js), Knopf in der Sidebar). Ein angeheftetes Buch liegt **komplett** im eigenen `schreibwerkstatt-offline-v1`: Buchliste, Buch, Baum und jeder Abschnitt — ohne den `MAX_CONTENT_CACHE_ENTRIES`-Deckel, der ein grosses Buch im `CONTENT_CACHE` nie vollständig halten kann. `_handleSwr` fällt nach einem `CONTENT_CACHE`-Miss darauf zurück; jede Netzantwort für einen angehefteten Pfad frischt die Kopie auf; `invalidate-content` lädt angeheftete Pfade **nach** statt sie zu löschen (sonst fehlte der eben gespeicherte Abschnitt bis zum nächsten Sync). Der Sync ist inkrementell (pro Abschnitt `updated_at` aus dem Baum) und sichert alle 25 Abschnitte einen Zwischenstand, weil der Browser einen SW auch mit `waitUntil` nach einigen Minuten beendet. Der Cache fällt mit `SESSION_CACHE_DROP_TYPES`; die **Absicht** liegt pro Konto in localStorage (`offline_books_u:<email>`) und stösst den Sync nach dem Boot neu an. Beim ersten Anheften fragt die App `navigator.storage.persist()` an — ohne diese Freigabe darf der Browser Caches und localStorage bei Speicherdruck räumen. Navigations-Reads (`listBooks`, `bookTree`) fallen offline vom `fresh`-Read auf den Cache zurück ([repo/content.js](../public/js/repo/content.js)#`_getNav`), sonst scheitert schon der Buchwechsel (er liest fresh); Abschnitts-Reads bekommen das bewusst nicht, ihr `fresh` ist die Konsistenzzusage vor einem Schreiben. `sw.js` lädt das Modul per `importScripts` (am LOC-Deckel); `/sw-offline.js` steht wie `/sw-manifest.js` in `PUBLIC_ASSETS`. Gegated durch [tests/unit/sw-offline-books.test.mjs](../tests/unit/sw-offline-books.test.mjs) und [tests/unit/offline-launch.test.mjs](../tests/unit/offline-launch.test.mjs).
- **Pflicht-Update über `SHELL_PROTOCOL`** ([public/js/shell-protocol.js](../public/js/shell-protocol.js)) — von Hand hochzählen, wenn eine Server-Änderung eine ältere offene Shell bricht (Request-/Antwort-Vertrag, Route), nicht bei jedem Deploy. Server und Shell lesen dieselbe Datei ([lib/version.js](../lib/version.js)#`getShellProtocol` → `/config.shellProtocol`); geprüft wird beim Boot und bei jedem neu installierten SW gegen ein frisches `/config`. Liegt die Shell darunter, wartet das Update nur noch auf ungespeicherte Änderungen (nicht auf Edit-/Fokusmodus) und das Banner sagt „Pflicht". Gegated durch [tests/unit/update-policy.test.mjs](../tests/unit/update-policy.test.mjs).

- **Die Build-ID der Seite kommt aus dem SW, der sie bedient** — `/sw-manifest.js` (von index.html klassisch geladen, nicht im eigenen Manifest) beantwortet der SW aus seinen eigenen Konstanten; nur im Netz-Modus einer verlorenen Generation geht die Datei ans Netz. Der Build-Guard in [app-init.js](../public/js/app/app-init.js) bestätigt einen Mismatch gegen `/config?__fresh=1`, bevor er neu lädt: `/config` ist SWR und trägt direkt nach dem Generationswechsel noch den Build von vorher.

- **Content-Cache: die Strategie folgt der Art der Aussage, nicht dem Pfad-Prefix** — `/content/*`-GETs laufen im Service Worker ([public/sw.js](../public/sw.js)) per Default als **Stale-While-Revalidate** im `CONTENT_CACHE` (das ist das Offline-Versprechen: Baum + Seiteninhalt bleiben lesbar). Drei Klassen, und ein neuer `/content/*`-Endpunkt muss sich einer zuordnen:
  - **Stand** (Seite, Kapitel, Baum, Order, Voll-Body EINER Revision) → SWR. Der Cache-Hit ist hier die richtige Antwort; beim Voll-Body einer Revision sogar dauerhaft, weil sie unveränderlich ist.
  - **Log / Abfrage** (`/content/pages/:id/revisions`, `/content/search`, `CONTENT_VOLATILE_REGEX`) → **Netz zuerst, Cache nur als Offline-Rückfall**. **Why:** ein Stale-Hit auf einem wachsenden Log zeigt den Stand des letzten Besuchs, und der Hintergrund-Revalidate füllt nur den Cache, nicht die schon gerenderte Karte — bei einer frisch angelegten Seite also eine leere Fassungsliste, während der Server längst Revisionen hält. Der Write-seitige Bust (`_invalidateContentCache` in [public/js/repo/content.js](../public/js/repo/content.js)) rettet das nicht: er greift nur im **schreibenden** Browser, und Revisionen entstehen auch auf einem zweiten Gerät, im Mac-/Android-Client und in Server-Apply-Pfaden. Die Schreiber eines Logs vollständig aufzuzählen ist die verlorene Wette — die Regel ist „ein Log wird nicht stale ausgeliefert".
  - **Poll** (`/changes`, `/presence`, `CONTENT_LIVE_REGEX`) → **gar nicht cachen** (unbehandelt ans Netz). Ein gecachter Heartbeat ist eine Falschaussage, und `/changes` trägt pro Poll einen eigenen `since`-Stempel: jede Antwort wäre ein eigener Cache-Key, zwölf pro Minute, und der `MAX_CONTENT_CACHE_ENTRIES`-Deckel hätte den offline lesbaren Buchinhalt in einer Viertelstunde verdrängt.
  - **Der Server darf widersprechen:** deklariert eine gecachte Antwort `no-cache`/`no-store`, wird sie nicht stale ausgeliefert (`_forbidsStale` in [public/sw.js](../public/sw.js)) — betrifft die drei `/content/*/release.json`, deren ganzer Zweck die Frage „gibt es eine neuere Client-Version?" ist. Ein neuer Endpunkt dieser Art braucht damit **keinen** Eintrag in der Regex, nur seinen Header.
  - **`/config` ist SWR (Offline-Bootstrap) und braucht seinen Bypass IM SW** — `handleConfig` matcht auf `CONFIG_PATH` und ignoriert damit die Query, ein `?__fresh=1` am Aufrufer allein träfe weiter den Cache-Eintrag. **Why:** der Wake-Refresh holt `/config` ausschliesslich, um eine abgelaufene Session an den globalen 401-Wrapper zu geben; aus dem Cache beantwortet, konnte dieser Check per Konstruktion nie auslösen und der User erfuhr vom Ablauf erst beim nächsten Schreibversuch.
  - **Jeder Body-Write bustet über `contentRepo`, nie per rohem `fetch`** — auch der, der wie ein reiner Befehl aussieht (`POST …/revisions/:rev/restore` schreibt einen Body und erzeugt selbst eine Revision). Ohne den Bust auf `pages/:id` liefert ein späterer nicht-frischer Read den Stand **vor** dem Schreiben, und der nächste Save schreibt ihn darüber.
  - **Stale-While-Revalidate hat ZWEI Hälften — ohne Nachzug ist es bloss „stale"** ([public/sw.js](../public/sw.js)#`notifyContentUpdated`, Client-Seite [boot/content-updated.js](../public/js/app/boot/content-updated.js) + [book/tree/catchup.js](../public/js/book/tree/catchup.js)). Der SW vergleicht die Revalidierung mit dem Stand, den er ausgeliefert hat, und meldet eine Abweichung als `content-updated` an seine Tabs; der Client zieht daraufhin **leise** nach (kein `treeLoading`, kein State-Clearing, kein Plaketten-Refetch — der Baum wird ersetzt, sonst nichts). **Why:** SWR gibt den Cache-Hit an die UI und die Netzantwort nur in den Cache — die schon gerenderte Sidebar erfährt davon nie, und der Baum wird erst beim **zweiten** Reload aktuell. Der Netz-Request läuft ohnehin; hier wird nur sein Ergebnis nicht mehr weggeworfen. **How to apply:** zwei Listen, und sie sagen Verschiedenes — `CONTENT_NOTIFY_REGEX` im SW sagt, was überhaupt **verglichen** wird (heute Buchliste + Baum; ein Seiten-Body ist bewusst draussen, sonst kostet jeder Seiten-Read einen Klon samt Textvergleich für eine Meldung ohne Konsumenten), `parseContentPath` im Client sagt, was ein Pfad **bedeutet**. Der SW meldet nie eine Bedeutung, er kennt keine Karten; wer dort einen Pfad aufnimmt, braucht hier einen Zweig. Der Vergleich läuft über den **ETag**, wenn die Antwort einen trägt — darum setzen Buchliste und Baum `private, max-age=0, must-revalidate` ([routes/content/books.js](../routes/content/books.js)#`TREE_CACHE_CONTROL`): der HTTP-Cache des Browsers beantwortet die Revalidierung dann mit 304, und der SW entscheidet per Header statt per Textvergleich über den ganzen Body. **Nicht `no-cache`** — das liest der SW als `_forbidsStale` und schaltet den Pfad auf Netz-zuerst um, also genau gegen die sofortige Sidebar. Gegated durch [tests/unit/sw-content-freshness.test.mjs](../tests/unit/sw-content-freshness.test.mjs) und [tests/unit/tree-catchup.test.mjs](../tests/unit/tree-catchup.test.mjs).
  - **Der Collab-Poll misst Gleichzeitigkeit, nicht Veränderung — dafür gibt es die Drift-Probe** ([book/tree/catchup.js](../public/js/book/tree/catchup.js)#`_checkTreeDrift`). Der volle 5s-Poll startet erst bei einer zweiten Partei am Buch (`_selfBookDeviceCount > 1`), und dieser Zähler kennt nur Geräte, die in den letzten 90 s gepingt haben. Die Probe fragt stattdessen `/changes?since=<jüngster Seitenstand im Baum>` — beim Kaltstart genau dann, wenn der Baum **nicht** frisch gelesen wurde, und danach am 40-s-Geräte-Ping, solange der volle Poll nicht läuft, sowie ohne Dedup nach jedem `changed`-Anstoss des Event-Streams (`_checkTreeDrift(bookId, { force: true })`). **Why:** ohne sie fällt das häufigste Muster durch — gestern am Mac-Client geschrieben, heute im Browser geöffnet. **How to apply:** der Cursor ist der Stand des **Baums**, nicht die Uhrzeit (sonst ist die Probe selbst-blind), ohne Baum gibt es keine Probe, und sie zeigt **keine Toasts** — wer was geändert hat, bleibt Sache des vollen Polls mit seinem eigenen Cursor. Sie ist selbstbegrenzend: nach dem Nachzug steht `_treeSince()` hinter der Änderung.
  - **Der Collab-Feed kennt `update` und `delete` — eine NEU angelegte Seite ist ein `update` auf eine unbekannte `page_id`** ([app-collab.js](../public/js/app/app-collab.js)#`_applyCollabChanges`). Sie muss den Baum nachziehen; ohne diesen Zweig setzt der Feed nur einen Plaketten-Marker auf ein Item, das die Sidebar gar nicht hat, und die Seite bleibt bis zum nächsten Voll-Load unsichtbar. Toast und Marker laufen unverändert weiter.
  - **Die Client-Hälfte derselben Regel: ein ereignis-getriggerter Reload liest frisch, nur der Kaltstart darf aus dem Cache** — SSoT [tree/load.js](../public/js/book/tree/load.js)#`readsFresh` (`FRESH_SOURCES` = `bookSwitch`/`wake`/`job`/`login`, plus explizites `fresh: true`). **Why:** SWR ist beim Kaltstart genau richtig (Sidebar steht sofort, offline überhaupt) und beim Reload die falsche Antwort auf die gestellte Frage. Drei Fälle können im Browser gar keinen Bust gesehen haben: der Wake-Refresh hat während des Schlafs nichts mitbekommen, Import-/Pull-/Push-Jobs legen ihre Seiten **serverseitig** an, und eine frische Anmeldung erbt einen Cache, dessen Entstehung sie nicht beobachtet hat (Sitzungs-Achse siehe nächster Punkt). Umgekehrt darf **nicht** jeder Read `fresh` sein: `__fresh=1` wartet auf das Netz, und damit wären die sofortige Sidebar und das Lesen ohne Verbindung beide weg — genau das, wofür der Cache da ist. **Der Marker sagt nur „beantworte MICH nicht aus dem Cache", nicht „lass die Offline-Kopie stehen"**: der Bypass zieht den Cache-Eintrag nach (unter dem Pfad **ohne** Marker), wie `handleConfig` es seit je tut. Ohne dieses Nachziehen frieren genau die Bücher ein, die man nur per Buchwechsel öffnet — sie werden ausschliesslich `fresh` gelesen, ihr Baum käme im Zug also nie aus dem Cache, weil er nie hineingeschrieben wurde. Gegated durch [tests/unit/tree-load-freshness.test.mjs](../tests/unit/tree-load-freshness.test.mjs) und [tests/unit/sw-content-freshness.test.mjs](../tests/unit/sw-content-freshness.test.mjs).
  - **Eine neue Sitzung ist ein Ereignis, kein Kaltstart** — beim Start vergleicht [boot/session-change.js](../public/js/app/boot/session-change.js) den Sitzungs-Fingerprint aus dem Cookie `sw_sess` (Server-SSoT [lib/session-fingerprint.js](../lib/session-fingerprint.js), gesetzt an den Login-Antworten selbst plus als Rückfall in der Aktivitäts-Middleware) mit dem gemerkten Wert; weicht er ab, fallen `CONTENT_CACHE` + `CONFIG_CACHE` über denselben SW-Griff wie beim Logout (`SESSION_CACHE_DROP_TYPES`) — und zwar **vor** dem ersten gecachten Read, sonst hat `/config` seinen Stale-Stand schon geliefert. **Why:** geleert wird der Cache sonst einzig vom Logout-Knopf der SPA, und der setzt einen Klick **in** der App und einen kontrollierenden SW voraus — eine abgelaufene Session, ein geschlossener Browser oder ein Login direkt von der Login-Seite kommen dort nie vorbei, und der erste Render nach dem Anmelden kommt dann aus einer beliebig alten Kopie. Der Client kann das nicht selbst feststellen: die E-Mail unterscheidet zwei Sitzungen **desselben** Users nicht, und `/config` (wo sie steht) ist selbst gecacht — darum ein Cookie und kein Antwortfeld, und darum ist es JS-lesbar (`httpOnly: false`) und ein Hash (kein Klartext, er liegt offen). **Geleert, nicht umgangen:** ein leerer Cache lässt SWR ans Netz gehen und **füllt sich dabei wieder**; `source: 'login'` ist nur der Rückfall, wenn kein SW erreichbar ist — dort gibt es auch keinen Stale-Hit. Der Fingerprint wird **nur bei bestätigtem Leeren** gemerkt, sonst schreibt eine ausgebliebene Quittung den Stale-Stand als „gleiche Sitzung“ fest — und **offline wird nichts weggeworfen** (`planSessionCacheAction` → `skip`): ein Cache, der sich nicht neu füllen lässt, ist dort das Einzige, was funktioniert, und der nächste Start mit Netz sieht die Abweichung erneut. Gegated durch [tests/unit/session-change.test.mjs](../tests/unit/session-change.test.mjs).
  - **Nicht lokal reproduzierbar:** der SW ist auf localhost aus ([public/js/app/boot/sw-register.js](../public/js/app/boot/sw-register.js)). Solche Fehler zeigen sich erst auf HTTPS, und ein Hard-Refresh umgeht den SW komplett — „nur nach Hard-Refresh richtig" ist das Symptom dieser Klasse. Gegated durch [tests/unit/sw-content-freshness.test.mjs](../tests/unit/sw-content-freshness.test.mjs).
