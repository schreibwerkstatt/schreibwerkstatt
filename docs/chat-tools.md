# Chat-Werkzeuge (agentische Chats)

Gemeinsamer Werkzeug-Katalog der vier agentischen Chats — **Buch-Chat**, **Plot-Chat**, **Ideen-Chat**, **Recherche-Chat** ([chats.md](chats.md)). Das Modell ruft pro Iteration Werkzeuge auf, deren Ergebnisse als neue `user`-Turns im Loop landen.

- **Definitionen** (Anthropic-Tool-Format) je Lese-Werkzeug genau einmal in [public/js/prompts/chat-tools/](../public/js/prompts/chat-tools/) (`catalog-text`, `catalog-world`, `catalog-analysis`, `catalog-planning`; `CHAT_TOOLS` in [index.js](../public/js/prompts/chat-tools/index.js), Facade `public/js/prompts.js`). Querverweise zwischen Werkzeugen stehen im Feld `see` und werden nur gerendert, wenn das Ziel im Lauf angeboten wird (`renderChatTools`).
- **Zugriff je Chat**: Zugriffstabelle [access.js](../public/js/prompts/chat-tools/access.js)#`CHAT_TOOL_ACCESS` — pro Werkzeug und Chat `slim`, `full` oder nicht angeboten. Die einzige Stelle, an der entschieden wird, wer ein Werkzeug bekommt.
- **Ausgabe-Werkzeuge** bringt jeder Chat selbst mit: Buch-Chat `final_answer` ([book-chat-output.js](../public/js/prompts/book-chat-output.js)), Plot-/Ideen-Chat `propose_*` + `final_answer` ([plot-chat.md](plot-chat.md), [ideen-chat.md](ideen-chat.md)), Recherche-Chat `web_search`/`read_web_page` + `propose_research_item` + `final_answer` ([recherche-chat.md](recherche-chat.md)).
- **Handler**: [routes/jobs/chat-tools/](../routes/jobs/chat-tools/) (ein `tools-<bereich>.js` je Domäne, `TOOLS` + `AVAILABILITY` in [index.js](../routes/jobs/chat-tools/index.js)); sämtliche SQL-Abfragen in [db/book-chat/](../db/book-chat/) (`analysis`, `catalog`, `figures`, `research`, `text`, `timeline`) bzw. bestehenden `db/`-Modulen — die Werkzeug-Module selbst führen kein SQL aus.
- **Auswahl pro Lauf**: [chat-tools/select.js](../routes/jobs/chat-tools/select.js)#`prepareChatTools` — für alle vier Chats derselbe Weg (siehe „Werkzeugsatz"). **Deckel**: [agentic-chat/limits.js](../routes/jobs/agentic-chat/limits.js), ebenfalls für alle vier.
- **Jobs**: Buch-Chat [book-chat-agent.js](../routes/jobs/chat/book-chat-agent.js)#`runBookChatJobAgent` (Dispatcher klassisch/agentisch: [book-chat.js](../routes/jobs/chat/book-chat.js)), Plot-/Ideen-Chat [proposal-chat.js](../routes/jobs/proposal-chat.js), Recherche-Chat [research-chat.js](../routes/jobs/research-chat.js) — alle auf dem geteilten Loop [routes/jobs/agentic-chat.js](../routes/jobs/agentic-chat.js)#`makeAgenticChatJob`.
- **Regeln für neue Werkzeuge**: [routes/jobs/chat-tools/CLAUDE.md](../routes/jobs/chat-tools/CLAUDE.md), gegated durch [tests/unit/chat-tools-contract.test.mjs](../tests/unit/chat-tools-contract.test.mjs).

## Vertrag

Jede Tool-Funktion: `(input, ctx) → JSON-serialisierbares Objekt` (sync oder async). Dispatcher: `executeTool(name, input, ctx)` aus [chat-tools/index.js](../routes/jobs/chat-tools/index.js) (Plot-, Ideen- und Recherche-Chat reichen Lese-Werkzeuge über ihren eigenen Executor dorthin durch).

**Fehler:** `{ error: '<Text fürs Modell>', errorKey: 'chat.toolError.<fall>', errorParams? }`. `error` bleibt deutscher Klartext mit Handlungshinweis fürs Modell; `errorKey` (+ `errorParams`) ist für die Werkzeug-Liste im UI und steht in **beiden** Locales. Der Loop nimmt `errorKey`/`errorParams` vor dem Senden aus dem `tool_result` heraus und legt sie in `toolLog[]` ab; das Frontend übersetzt sie (`toolLogRows` in [chat/tool-log.js](../public/js/chat/tool-log.js)), ohne Key zeigt es den Rohtext (unerwartete Ausnahme).

`ctx` (gebaut im `prepare` des jeweiligen Jobs; hier die Felder des Buch-Chats):
- `bookId` — aus `chat_sessions.book_id` der aktiven Session.
- `sessionId` — `chat_sessions.id` der aktiven Session (für Tools mit Session-Bindung, z.B. `generate_image` → `chat_images`).
- `images` — Array, in das `generate_image` `{image_id,prompt,mime}` pusht; der Loop persistiert es in `context_info.images`.
- `userEmail` — Owner-Scope für alle Reads (Reviews, Ideen, Werkstatt sind user-scoped).
- `jobSignal` — `AbortController.signal`, wird vor jedem Tool-Call und im Loop geprüft.
- `offeredTools` — `Set` der in diesem Lauf angebotenen Werkzeuge (`prepareChatTools`). Ein Hinweis im Ergebnis («weiter mit X») nennt X nur, wenn es angeboten wird: `toolHint(ctx, name, text)` / `offeredList(ctx, names)` aus [shared.js](../routes/jobs/chat-tools/shared.js). Ohne `offeredTools` (direkter Aufruf in Tests) gilt alles als angeboten.
- `resultCapChars` — Ergebnis-Deckel des Loops (`toolResultCap`); `executeTool` kürzt strukturiert darauf (siehe Truncation).
- `inputBudgetChars` — Input-Budget des effektiven Providers (Kapazitäts-`hint` von `list_chapters`).
- `citations` / `recherche` / `ideenProposals` — von `final_answer` gefüllt, landen in `context_info` (siehe Endpunkt).
- `logger` — Job-Child-Logger.

## Truncation

1. **Strukturiert** — `_truncateResult(obj, maxChars)` ([chat-tools/shared.js](../routes/jobs/chat-tools/shared.js) → [truncate.js](../routes/jobs/chat-tools/truncate.js)), aufgerufen von den Tools selbst und noch einmal von `executeTool` mit `resultCapFor(ctx)` = min(`MAX_RESULT_CHARS`, `ctx.resultCapChars`). Reihenfolge: (a) das jeweils grösste Array auf oberster Ebene halbieren (`results`, `pages`, `items`, `chapters` …), bis es passt oder jedes Array nur noch ein Element hat — Skalarfelder (Summen, `hint`, `total_*`) bleiben stehen; (b) lange Strings stufenweise kürzen; (c) letzter Ausweg harter String-Schnitt. Kennzeichnung `truncated: true`, für `results` zusätzlich `total_results` (falls das Tool es nicht selbst setzt), für andere Felder `truncated_fields[key] = {shown,total}`. Endlich in jeder Stufe — keine Rekursion. Gegated: [tests/unit/book-chat-truncate.test.js](../tests/unit/book-chat-truncate.test.js).
2. **Hart im Loop** — [agentic-chat/loop.js](../routes/jobs/agentic-chat/loop.js) schneidet ein Ergebnis über `toolResultCap` ([agentic-chat/limits.js](../routes/jobs/agentic-chat/limits.js)#`toolResultCapChars` = `max(4000, inputBudgetChars / (maxIter · 6))`) als String ab. Weil Stufe 1 schon auf denselben Deckel kürzt, greift das praktisch nie; `toolLog[].truncated` meldet beide Fälle.
3. **Pro Runde** — in allen vier Chats höchstens `MAX_TOOLS_PER_ROUND` (8) ausgeführte Aufrufe und zusammen höchstens `roundResultCapChars` ([limits.js](../routes/jobs/agentic-chat/limits.js), ein Viertel von `inputBudgetChars`, mindestens zwei volle Einzelergebnisse) Ergebnis-Zeichen. Was darüber liegt, wird **nicht ausgeführt**, bekommt aber ein `tool_result` mit `is_error` und Hinweis «in der nächsten Runde erneut anfordern» (`errorKey` `chat.toolError.roundLimit`/`roundBudget`) — jeder `tool_use` braucht genau ein `tool_result`, sonst ist die Folgerunde ein 400. **Why:** der Prompt fordert gebündelte `get_chapter_text`-Aufrufe; ungedeckelt hängt eine einzige Runde mehr an, als das Fenster trägt, und erst der nächste Call merkt es.

`MAX_RESULT_CHARS = max(4000, INPUT_BUDGET_CHARS / 36)` — skaliert mit `MODEL_CONTEXT`. Listen-Limits (`MAX_SEARCH_RESULTS = 30`, `MAX_PAGES_PER_FETCH = 20`) bleiben fix (UI-Ergonomie). Ergebnisse so bauen, dass **Zusammenfassungen vorne** stehen (Einfüge-Reihenfolge überlebt auch den harten Schnitt).

## Buch- und User-Scope

Jedes Werkzeug mit `page_id`/`chapter_id`/`ids`-Input prüft die Zugehörigkeit zu `ctx.bookId`, **bevor** es Inhalt lädt: `get_pages` meldet eine fremde Seite wie eine fehlende (`missing`, ohne Text), `quote_passage`/`list_revisions`/`get_chapter_text` antworten mit Fehler, die Listen-/Such-Werkzeuge filtern im SQL auf `book_id`. **Why:** die IDs kommen vom Modell und damit indirekt aus jeder Userfrage — ohne Prüfung liest ein «zeig mir Seite 4711» das Manuskript eines fremden Buchs. Szenen, Figuren, Orte und Welt-Fakten sind Analyse-Daten **pro User**, der Embedding-Index hängt nur am Buch: `search_similar` und die Erst-Kontext-/RAG-Blöcke lösen Treffer über `resolveEntityTitle(kind, id, { userEmail })` auf, die eines Mitautors fallen weg (Recherche-Einträge sind buchweit geteilt und bleiben). Gegated: [tests/integration/book-chat-scope.test.js](../tests/integration/book-chat-scope.test.js).

**`chapter_id` heisst Teilbaum.** Jeder `chapter_id`-Filter eines Werkzeugs meint das Kapitel samt Unterkapiteln (`chapterSubtreeFilter` aus [db/book-order.js](../db/book-order.js), [chapter-hierarchy.md](chapter-hierarchy.md#backend-helper)); die IDs kommen aus `list_chapters`, wo ein «Teil» oft keine eigenen Abschnitte hat. Ausnahme `get_chapter_text`/`get_edit_status` mit eigenem `include_subchapters`-Schalter; `get_stil_metrics` liefert dann eine Zeile je Kapitel des Teilbaums.

## Erst-Kontext + Kosten-Leiter

**Der Agent startet nicht mehr bei null.** Vor der ersten Iteration holt `prepare` über [routes/jobs/chat/book-chat-retrieval.js](../routes/jobs/chat/book-chat-retrieval.js)#`preContextPassages` die semantisch nächsten Passagen zur aktuellen Frage — dieselbe Pipeline wie das Tool `search_similar` ([lib/semantic-retrieval.js](../lib/semantic-retrieval.js)#`semanticQuery`, `kinds: ['page','scene','figure','location','fact']`) — und legt sie als Block vor die Frage in deren User-Nachricht (siehe Cache-Lage). `semanticQuery` liefert je Entität nur ihren besten Chunk; `withNeighbors` erweitert ihn um die Nachbar-Chunks (`chunk_ix ± 1`), damit die Antwort nicht an der Chunk-Grenze abreisst. Passt die Nachbarschaft nicht mehr unter den Zeichendeckel, bleibt der Treffer-Chunk allein.

- **Warum:** die häufigste Frageform ist eine schmale Faktenfrage («wie alt war Stefan», «wann hat Stefan die Schule abgeschlossen»). Ohne Erst-Kontext beginnt der Agent bei jeder davon mit einer Werkzeug-Runde und eskaliert im Zweifel auf `get_chapter_text` — ein Kapitel-Volltext kostet ein Vielfaches der einen Passage, in der die Antwort steht. Ein paar Tausend Tokens vorne sind billiger als eine einzige Volltext-Runde.
- **Grösse:** `jobs.book_chat.pre_rag_top_k` (Default 8) Treffer, hart gedeckelt auf `jobs.book_chat.pre_rag_chars` (Default 12000 Zeichen ≈ 3k Tokens). **`top_k = 0` oder `chars = 0` schaltet den Erst-Kontext ab** (Agent verhält sich wie vorher).
- **Non-fatal, mit Status:** der Block **fehlt nie ganz** (ein fehlender Block liest sich für das Modell wie «kein Index» und führt direkt zu den Volltext-Werkzeugen) und unterscheidet drei Lagen ([prompts/chat-pre-context.js](../public/js/prompts/chat-pre-context.js)#`passageStatusNote`, Status aus `preContextStatus`): **Index unvollständig** — kein vollständiger Lauf (`indexState().ready` false) oder Abschnitte mit `updated_at` nach `lastIndexedAt` (`semanticIndexStatus`); der Hinweis steht auch neben vorhandenen Treffern und verbietet, aus fehlenden Treffern «steht nicht im Buch» zu schliessen; **Suche ausgefallen** (Backend-Fehler, `agentPreContext` liefert `error`) — sagt nichts über den Text; **keine Treffer bei vollständigem Index**. Ohne Endpunkt: «keine Bedeutungssuche konfiguriert».
- **Relevanz fürs Modell:** jede Passage trägt `Rang` (1 = bester) und `Ähnlichkeit` (roher Cosinus `semScore`, 0–1) — nie den stufenabhängigen Pipeline-`score` (RRF ~0.03 sähe irrelevant aus). Kopfzeile mit `kind`, `entity_id`, Kapitelpfad: `passageHeader`, geteilt mit Plot- und Ideen-Chat.
- **User-Scope vor topK:** `semanticQuery(…, { user })` filtert Analyse-Entitäten eines Mitautors **vor** dem Top-K-Schnitt (Erst-Kontext und `search_similar`); `resolveEntityTitle` bleibt als zweite Sperre.
- **Cache-Lage (Pflicht-Invariante):** `buildBookChatAgentSystemPrompt` liefert **einen** System-Block (`ttl: '1h'`) mit dem über die Session stabilen Anteil (System, Strategie, Figuren, **Welt-Fakten**, Review, `final_answer`-Pflicht). Der Erst-Kontext (`buildBookChatPreContext`) trägt pro Frage andere Bytes und steht darum **nicht** im System, sondern als eigener Textblock **vor der Frage in deren User-Nachricht** (`userPreamble` des Loops; persistiert wird nur die Frage). So sind Werkzeuge + System + bisheriger Verlauf ein stabiler Präfix über alle Iterationen **und** Turns; den Verlauf deckt ein eigener Breakpoint am Historien-Ende (`cacheHistory`, siehe „Claude-/Opus-Call“). Stünde der Erst-Kontext im System, bräche er den Präfix direkt hinter Block 1 — der ganze Verlauf würde jeden Turn neu bezahlt.
- **Suchtext = Frage + letzte Runde** (`retrievalQuery` in [book-chat-retrieval.js](../routes/jobs/chat/book-chat-retrieval.js), geteilt von allen RAG-Pfaden: Buch-Chat klassisch (Semantik **und** Keyword-Scoring) + agentisch, Plot- und Ideen-Chat klassisch + agentisch, Buch-Kontext des Abschnitts-Chats): vorige User-Frage (≤ 400 Zeichen) + Anfang der vorigen **inhaltlichen** Antwort (≤ 300; i18n-Marker und deren Verlaufs-Platzhalter `FALLBACK_PLACEHOLDER` zählen nicht) + aktuelle Frage. **Why:** Folgefragen («und wie alt war sie da?») tragen ihr Subjekt nicht selbst. User-Scope wie `search_similar` (siehe „Buch- und User-Scope“).
- **Sichtbar:** `context_info.pre_context = {count, chars}` → erste Zeile «Vorab geladen: N passende Textstellen» im Werkzeug-Verlauf ([chats.md](chats.md#geteiltes)); der Verlauf erscheint dafür auch ohne Werkzeug-Aufruf. Damit lässt sich ablesen, ob eine Antwort ohne Werkzeug-Runde zustande kam.

**Welt-Fakten-Block** ([public/js/prompts/chat.js](../public/js/prompts/chat.js)#`buildWeltfaktenBlock`): die etablierten Welt-Fakten des Buchs (`world_facts`) im **stabilen Block 1**, gedeckelt über `weltfaktenBlockChars` ([routes/jobs/chat/shared.js](../routes/jobs/chat/shared.js), 10 % des Input-Budgets, Minimum 2000 Zeichen — kein eigenes App-Setting, gleiche Ableitung wie der Figuren-Deckel), im agentischen Pfad zusätzlich absolut gedeckelt auf `AGENT_WELTFAKTEN_MAX_CHARS` ([routes/jobs/chat/book-chat-agent.js](../routes/jobs/chat/book-chat-agent.js)). **Why:** auf einem 1M-Fenster griffen die 10 % nie, und ein ausanalysiertes Buch trug mehrere hundert Fakten in jede Iteration; den Rest holt `list_world_facts` gezielt. **Why Block 1 und nicht Erst-Kontext:** die Fakten hängen am Buch, nicht an der Frage — im ungecachten Erst-Kontext-Block würde derselbe Inhalt jede Iteration neu bezahlt. Zwei Regeln: was der Deckel geschluckt hat, wird im Block ausgewiesen (die Weltgesetze `regel`/`technik` stehen vorn, damit zuerst das Beiwerk fällt), und ein **nicht erhobener** Index liefert **keinen** Block — ein leerer würde als «diese Welt hat keine Regeln» gelesen (dass der Index fehlt, sagt `list_world_facts`, wenn der Agent fragt).

**Kosten-Leiter im System-Prompt** ([public/js/prompts/chat.js](../public/js/prompts/chat.js)#`buildBookChatAgentSystemPrompt`): Stufe 1 = Erst-Kontext + Figuren-/Welt-Fakten-/Review-Block (gratis, schon da) → Stufe 2 = gezielte Index-Tools, die Passagen liefern (`search_similar`, `search_passages`, `get_figure_profile`, `get_figure_mentions`, `get_timeline`, `quote_passage`) → Stufe 3 = Volltext (`get_pages`, `get_chapter_text`). Schmale Faktenfragen werden auf Stufe 1 oder 2 beantwortet. Jede Werkzeug-Erwähnung im Prompt läuft über `toolMentions` ([mentions.js](../public/js/prompts/chat-tools/mentions.js)) — fehlt ein Werkzeug im Lauf, fällt die Erwähnung weg. Die **Erzählweise** (Perspektive, Tempus) steht als eine Zeile im gecachten Block (`buildErzaehlweiseLine`, auch im Plot- und Ideen-Chat) — dafür braucht keine Stilfrage eine Werkzeug-Runde.

**Aussenwelt-Regel** (`buildBookChatOutsideWorldRule(toolNames)` in [prompts/book-chat-output.js](../public/js/prompts/book-chat-output.js), im Job an Block 1 gehängt): der Buch-Chat hat **keine Web-Suche**. Fragen zu realen Ereignissen/Fakten ausserhalb des Manuskripts beantwortet er nur, soweit das Buch etwas dazu sagt, sagt das offen und setzt in `final_answer` `recherche_hinweis: true` + `recherche_frage` — das Frontend bietet dann «Im Recherche-Chat fragen» an (Übergabe: [chats.md](chats.md#übergabe-buch-chat--recherche-chat)). **Ausnahme Lebensnormen:** allgemeine Normen (Einschulung ~6, Volljährigkeit, Pensionsalter …) darf er als Prüfmassstab an die Buchdaten anlegen («wann sollte X eingeschult werden?»), als Allgemeinwissen gekennzeichnet, Alter via `get_figure_age` — ohne Recherche-Hinweis. **Why:** sonst wich er gerade der Plausibilitätsfrage aus, für die Lebenslauf und Alters-Index da sind.

**Der `hint` aus `list_chapters` ist eine Kapazitätsaussage, kein Auftrag.** «Das ganze Buch passt in den Kontext» nennt darum zuerst die Bedingung (die Frage muss den ganzen Text sichten müssen) und danach die Erlaubnis — sonst wird Voll-Lektüre der Standardweg und ein einzelner Fakt kostet ein Kapitel. Die Voll-Lektüre-Strategie bleibt für ihren eigentlichen Fall bestehen: Auswahl oder Vollständigkeit über das ganze Buch (lustigste/schönste Stelle, alle Stellen zu X, Zusammenfassung, Ton des Buchs). Stellen nach einer Eigenschaft ohne Stichwort-Signatur (Beispiele für ein Stilmittel, eine Stimmung, ein Motiv, Umschreibungen) sucht der Agent dagegen zuerst mit `search_similar` und grossem `snippet_chars` (STRATEGIE-Zeile im System-Prompt, Werkzeug-Beschreibungen von `search_passages`/`search_similar`).

## Loop-Constraints

- Max. Tool-Iterationen: je Chat ein App-Setting (`jobs.book_chat.max_tool_iter`, Plot/Ideen/Recherche je eigenes), berechnet in [limits.js](../routes/jobs/agentic-chat/limits.js)#`maxToolIterFor`. Für Provider der Klasse `local` klemmt `jobs.book_chat.max_tool_iter_local` (Default 6) in allen vier Chats zusätzlich nach unten — ohne Prompt-Caching kostet jede Iteration den vollen Prompt erneut. Erschöpft ohne `final_answer` → **erzwungene Synthese-Runde** mit der Aufforderung `BOOK_CHAT_FORCE_FINAL_INSTRUCTION`. Die Werkzeugliste bleibt dabei **unverändert** — sie steht vorn im Prompt-Cache (eine auf `final_answer` verkürzte Liste liesse ausgerechnet den grössten Call des Laufs ohne Cache laufen) und Thinking-Blöcke sind an den unveränderten Gesprächsanfang gebunden. Die Anweisung sagt darum selbst, dass nur noch `final_answer` zählt; ruft das Modell trotzdem ein anderes Werkzeug, bekommt es einmal «nicht ausgeführt» (`chat.toolError.synthesisOnly`) und eine zweite Chance, danach `__i18n:chat.errors.maxIterReached__`.
- **Kosten-Deckel pro Antwort:** `jobs.book_chat.max_input_tokens_per_answer` (Default 500 000, 0 = aus; Admin → Jobs; gilt für alle vier agentischen Chats) begrenzt die **kumulierten** Input-Tokens aller Iterationen einer Antwort (cache-inklusiv, derselbe Wert wie die Token-Anzeige). Erreicht → die Ergebnisse der laufenden Runde werden noch angehängt, dann dieselbe Synthese-Runde wie beim Iterationsdeckel (Aufforderung `BOOK_CHAT_BUDGET_FINAL_INSTRUCTION`) — kein Hart-Abbruch. Die Synthese-Runde selbst kommt noch obendrauf. Daneben bleibt `jobs.book_chat.token_budget` der **Pro-Iteration**-Schutz des Kontextfensters.
- **Reihenfolge in einer Runde** ([agentic-chat/loop.js](../routes/jobs/agentic-chat/loop.js)): (0) `refusal` (Sicherheits-Klassifikator) → gespeichert wird `__i18n:chat.errors.refusal__`, Teil-Output und Werkzeuge der Runde verfallen (auch im Synthese-Turn); (1) `pause_turn` (serverseitiges Werkzeug pausiert, nur Recherche-Chat/Web-Suche) → Assistant-Inhalt anhängen, nächste Runde, kein Abschluss; (2) `final_answer` vorhanden → **erst** die übrigen Werkzeuge derselben Runde ausführen (Seiteneffekte in `ctx`: `generate_image`, `propose_research_item`), dann `final_answer` auswerten — auch wenn die Runde das Kontext-Budget überschritten hat; (3) Prosa-Abschluss; (4) Kontext-Budget überschritten → diese Werkzeug-Runde **nicht** mehr ausführen (der Erzähltext davor ist keine Antwort) und in die Synthese-Runde; (5) Werkzeuge ausführen, Kosten-Deckel prüfen. **Vor** jedem weiteren Call schätzt der Loop den Prompt (System + Werkzeugkatalog + Nachrichten, `charsPerToken`); läge er über `token_budget`, geht er direkt in die Synthese, die die Ergebnisse der letzten Runde bei Bedarf aufs Budget kürzt (die `tool_result`-Blöcke bleiben stehen). Ein `final_answer` mit kaputtem Argument-JSON (`parseError`) ist keine Antwort: in der Schleife läuft er als fehlgeschlagenes Werkzeug und das Modell ruft ihn neu, in der Synthese-Runde wird er zum Job-Fehler `job.error.agentFinalAnswerInvalid`; andere Werkzeuge mit `parseError` werden nicht mit `{}` ausgeführt, sondern bekommen ein ehrliches Fehler-`tool_result`. Die Synthese-Runde prüft `truncated` wie jede Runde (`job.error.aiTruncated`); ein Provider-Fehler dort endet als Job-Fehler (`job.error.agentSynthesisOverloaded` bzw. `…agentSynthesisFailed`, i18n-keyed Fehler unverändert) — nie als gespeicherte Platzhalter-Antwort. Eine leere Antwort wird nie roh gespeichert, sondern als `__i18n:chat.errors.emptyAnswer__`. Der Abbruchgrund steht in `context_info.stop_reason` (`final_answer|prose|max_iter|input_cap|context_budget|empty_tool_turn|refusal` bzw. der Wert aus `stopBeforeRound`); für `input_cap`, `max_iter` und `context_budget` zeigt die Antwortzeile einen Hinweis (`_bookChatStopNote`). Gegated: [tests/unit/agentic-chat-loop.test.js](../tests/unit/agentic-chat-loop.test.js).
- **Kosten gescheiterter Läufe:** endet ein Lauf ohne Assistant-Nachricht (Fehler, Abbruch, Truncation), bucht der Loop den bis dahin verbrauchten Input/Output über `recordChatLedgerEntry` ([db/cost-ledger.js](../db/cost-ledger.js), `source_ref = chatjob:<jobId>`) ins Ledger — sonst fehlten gerade die teuersten Läufe im Budget-Gate.
- **Verlauf** (`buildAgenticHistory`, geteilt von agentischem und klassischem Pfad): Anker (erste Runde) + die letzten 10 Nachrichten, **Rollen strikt alternierend ab `user`** (führende Antworten des Tails fallen weg). Gespeicherte Fallback-Marker (`__i18n:…__`) erscheinen dem Modell als neutraler Platzhalter, und an frühere Antworten hängen ihre gültigen Belege (`context_info.citations`, höchstens 6 à 160 Zeichen) als `[Belege dieser Antwort: …]` — Folgefragen kennen so die Stellen, auf die sich die Antwort stützte.
- **Opt-in-Hooks des Loops** (Recherche-Chat): `prepare` darf `stopBeforeRound({ iter, webSearches })` liefern — ab Runde 2 vor jeder Runde gefragt; ein String beendet die Recherche und führt mit diesem `stop_reason` in die Synthese (Recherche-Chat: Web-Such-Deckel → `web_cap`). Eine Werkzeugliste pro Runde gibt es bewusst nicht (Cache-Präfix). `buildContextInfo` bekommt neben `webSearches`/`webResults` auch `webQueries` (Suchanfragen der `server_tool_use`-Blöcke).
- Aktivierung (`_bookChatUseAgent`): `providerSupportsTools(effektiver Provider)` und `jobs.book_chat.mode != 'classic'`. Werkzeuge können `claude` (native `tool_use`-Blöcke) und `openai-compat` (OpenAI-Function-Calling, Schalter `ai.openai-compat.tools`); Ollama und `mode='classic'` nutzen den klassischen Single-Pass-Chat ohne Tools (`runBookChatJob`). Lehnt ein Endpunkt Werkzeuge ab, übernimmt derselbe klassische Pfad den Job (`AI_TOOLS_UNSUPPORTED` → `fallbackJob`), statt ihn scheitern zu lassen — nur solange noch kein Call geantwortet hat. Wire-Format-Details des openai-compat-Pfads: [ai-providers.md](ai-providers.md#tool-use).
- **Werkzeugsatz** (`prepareChatTools`, gleich für alle vier Chats): (1) **Slim oder voll** nach `jobs.book_chat.tool_set` = `auto|slim|full` (gilt für alle Chats; `auto` = voll für Cloud-, slim für lokale Provider), Stufen aus der Zugriffstabelle. Slim enthält im Buch-Chat Überblick, Suche (Wortlaut + Sinn), Volltext, Zitat, Figuren-Achse inkl. `get_figure_age`, Orte/Szenen, schon verdichtete Befunde (`list_world_facts`, `list_continuity_issues`, `list_ideen`, `list_redundancies` — ohne sie eskaliert ein kleines Modell für «welche Regel gilt hier», «wo sind Widersprüche?» auf Kapitel-Volltexte), Bewertung. (2) **Verfügbarkeit**: was einen fehlenden Endpunkt braucht (`search_similar`, `search_research_passages` ohne Embeddings, `generate_image` ohne Bild-Endpunkt) oder für das Buch keine Daten hat (kein Plot-Board, keine Motive, kein Kontinuitätscheck, leeres Recherche-Archiv …), fällt weg — `AVAILABILITY` in [chat-tools/index.js](../routes/jobs/chat-tools/index.js), jede Prüfung über dieselbe DB-Funktion wie der Handler. Eine fehlschlagende Prüfung blendet nichts aus. (3) **Gemeinsames Rendern** von Lese- und Ausgabe-Werkzeugen: `see`-Querverweise nur auf angebotene Ziele; dieselbe Namensliste geht als `toolNames` in den System-Prompt und als `ctx.offeredTools` an die Handler. **Why:** jedes angebotene Werkzeug kostet in jeder Runde Input-Tokens (ein Endpunkt ohne Caching zahlt sie jede Runde neu), und eine Beschreibung, die ein nicht angebotenes Werkzeug empfiehlt, verleitet zu einem erfundenen Aufruf. Bei lokaler Prompt-Variante kommt ein Block **Werkzeug-Disziplin** dazu. Gelaufener Satz + Anzahl stehen in `context_info.tool_set`/`tools_offered` (Buch-Chat), weggefallene Werkzeuge im Log.
- Per-Job-Claude-Override (analog Komplettanalyse): `ai.claude.model.bookchat` / `…context_window.bookchat` / `…max_tokens_out.bookchat` / `…timeout_ms.bookchat` / `…effort.bookchat` (App-Settings, leer/0 = folgt global). Greift nur bei `ai.provider = claude`, für **beide** Buch-Chat-Pfade (klassisch + agentisch). Gebunden via `setContext` in [routes/jobs/chat/book-chat.js](../routes/jobs/chat/book-chat.js)#`_applyBookChatAiOverrides` **vor** `getContextConfigFor`, damit Token-Budget/Tool-Result-Cap das Override-Kontextfenster reflektieren. Kein eigener Timeout-Default (anders als komplett). So läuft z.B. der Tool-Loop auf Opus, während global Sonnet 4.6 fürs Lektorat bleibt.

## Claude-/Opus-Call (Tool-Use)

Der agentische Loop ruft `callAIWithTools` → bei Claude `_callClaudeWithToolsAttempt` ([lib/ai/claude.js](../lib/ai/claude.js), Block-Verarbeitung in [claude-tool-blocks.js](../lib/ai/claude-tool-blocks.js)) — ein **eigener Pfad** neben dem Nicht-Tool-`_callClaudeAttempt`. Wer den Buch-Chat auf Opus optimiert, fasst diesen Pfad an, nicht den Nicht-Tool-Pfad. Die folgenden Punkte sind Claude-API-Eigenheiten; der openai-compat-Pfad hat weder Thinking-Blöcke noch Caching noch `effort` (sein Wire-Format: [ai-providers.md](ai-providers.md#tool-use)).

- **Adaptive Thinking:** auf Opus 4.7+ sendet der Tool-Pfad `thinking:{type:'adaptive'}` (Modell-Erkennung `_claudeUsesAdaptiveThinking`, identisch zum temperature-Verbot). **Pflicht-Invariante:** die im Stream erfassten `thinking`/`redacted_thinking`-Blöcke (inkl. `signature`) werden in `rawContentBlocks` in Originalreihenfolge zurückgespielt — der assistant-Turn MUSS mit dem Thinking-Block beginnen, sonst quittiert die Folge-Iteration mit HTTP 400. Sonnet 4.6 / Opus 4.6 / lokale Provider: kein `thinking`-Feld → unverändert. **Folge:** Thinking zählt gegen `max_tokens_out` — Output-Cap (`…max_tokens_out.bookchat`) großzügig halten (≥ 32–64K), sonst Truncation-Wurf.
- **Prompt-Caching (Multi-Turn):** System + Tools tragen einen Cache-Breakpoint (über `_buildClaudeSystemBlocks`); zusätzlich setzt `_withMessageCacheBreakpoints` pro Iteration einen Breakpoint auf den letzten Block der letzten Nachricht — die wachsende `tool_result`-History wird damit ab Iteration 2 aus dem Cache gelesen statt voll bezahlt — und einen auf jede mit `cacheBreakpoint: true` markierte Nachricht (Buch-Chat: Ende des Verlaufs vor der aktuellen Frage, `cacheHistory`). Damit liest der **nächste Turn** Tools + System + Verlauf aus dem Cache, obwohl Frage und Erst-Kontext neu sind (Render-Order tools→system→messages; 3 von max 4 Breakpoints, das Limit rechnet die Funktion gegen die System-Breakpoints). Die Markierung ist kein API-Feld und wird immer entfernt; openai-compat ignoriert sie. Nur der Tool-Pfad; das Original-`messages`-Array bleibt unangetastet (geklont).
- **effort:** je agentischem Chat ein Setting — `ai.claude.effort.bookchat` / `…researchchat` / `…plotchat` / `…ideenchat` (`low|medium|high|xhigh|max`, Default `medium`, Admin → Provider → Claude) → `output_config.effort` aller Runden einer Antwort. Der Buch-Chat legt ihn über `_bookChatAiOverrides` in den Job-Bag, die drei anderen über `effortSettingKey` im Loop ([agentic-chat/helpers.js](../routes/jobs/agentic-chat/helpers.js)#`applyChatEffort`, ergänzt einen bestehenden Claude-Bag). Tier-Mismatch wird geklemmt (`max`→Opus-only, `xhigh`→Opus-4.7+, sonst `high`) statt 400. Leer = Modell-Default (Opus 5.5: `medium`, sonst `high`). **Why explizit:** der Modell-Default wechselte mit Opus 5.5 von `high` auf `medium` — ohne Setting ändert ein Modellwechsel still die Denk-Tiefe.
- **Zwischenstände:** der Tool-Pfad sendet `thinking.display: 'summarized'` ([lib/ai/config.js](../lib/ai/config.js)#`_claudeToolThinkingParams`). Ab Opus 5.5 kommen die Notizen zwischen Werkzeug-Aufrufen als Thinking-Blöcke; unter dem Default `omitted` wären sie leer. Die letzte Zeile jeder abgeschlossenen Zusammenfassung geht als `onProgress({ note })` an den Loop und in die Statuszeile (`job.phase.agentNote`, 160 Zeichen).
- **Ablehnung (`refusal`):** Sicherheits-Klassifikatoren (Opus 5.5: cyber, bio, reasoning_extraction) antworten mit HTTP 200 und `stop_reason: refusal` (+ `stop_details.category`, geloggt). Mit `ai.claude.refusal_fallback` (Default an) schicken Tool- **und** Text-Pfad (`_callClaude`, alle JSON-Jobs) `fallbacks: 'default'` + Beta `server-side-fallback-2026-07-01` (nur Opus 5.5/5, Fable 5.1, Sonnet 5.5): die API rechnet die Anfrage im selben Call auf dem empfohlenen Modell neu; `message_start` nennt dann das Ersatzmodell, das ins Ledger geht. Nach einem Wechsel mitten in der Antwort markiert ein `fallback`-Block die Grenze; Thinking, `tool_use` und unvollständige Server-Werkzeug-Paare davor werden weder ausgeführt noch zurückgespielt ([lib/ai/claude-tool-blocks.js](../lib/ai/claude-tool-blocks.js)#`finalizeBlocks`).
- **Blöcke verbatim:** unbekannte Content-Block-Typen (neue Server-Werkzeuge, `fallback`) gehen unverändert in die nächste Runde, statt verworfen zu werden — eine Assistant-Runde ohne sie bräche Werkzeug-Paare und den Präfix, an den Thinking gebunden ist. `final_answer` trägt `eager_input_streaming: true` (die Antwort streamt live statt gepuffert); ihr Argument wird beim Blockende strikt geparst, ein kaputtes JSON ist `parseError`, nie eine still gekürzte Antwort. Strikte Werkzeuge (`strict: true`) sind bewusst **nicht** gesetzt: die API erlaubt höchstens 20 pro Request und 24 optionale Parameter insgesamt, der volle Buch-Chat-Satz hat bis zu 37 Werkzeuge.

### Endpunkt

| Tool | Input | Zweck | Quelle |
|------|-------|-------|--------|
| `final_answer` (Buch-Chat, [book-chat-output.js](../public/js/prompts/book-chat-output.js)) | `antwort: string`, `zitate?: [{page_id, offset, length, quote}]`, `recherche_hinweis?: bool`, `recherche_frage?: string`, `ideen?: [{page_id \| chapter_id, inhalt, begruendung?}]` | Pflicht-Endpunkt der Loop: Modell ruft das Tool als letzten Schritt mit der finalen Antwort an den User. Der Loop fängt es vor `executeTool` ab; stehen in derselben Runde weitere Werkzeuge, laufen **die zuerst** (Seiteneffekte), dann terminiert `final_answer`. **Halluzinationsschutz:** Wenn `zitate` mitgeliefert wird, validiert `validateFinalAnswerCitations` (Content-Store-Reload pro Seite, Buch-Scope) jeden Eintrag — `text.slice(offset, offset+length) === quote`. Stimmt das Zitat, aber nicht die Position, wird es **neu verankert** statt verworfen (exakt an der nächsten Fundstelle zum genannten `offset`, sonst tolerant gegenüber Anführungs-/Strich-/Whitespace-Varianten via [lib/quote-verify.js](../lib/quote-verify.js); `relocated: 'exact'|'tolerant'`, mindestens 12 Zeichen). **Why:** verzählte Offsets sind der häufigste `quote_mismatch`; die Neu-Verankerung kostet keinen KI-Call (ein zweiter Synthese-Turn schon) und zeigt das gemeinte Zitat — `actual` wäre der Text an der falschen Stelle. Ergebnis: `citation_validation` + `citations_invalid` im `toolLog`, und **als Fussnoten** in `context_info.citations[{n, page_id, page_name, quote, valid, reason?}]` (Seitenname/Sprungziel nur für Seiten des eigenen Buchs, Zitat ≤ 400 Zeichen). Ungültige werden nicht verworfen, sondern im UI markiert. `recherche_hinweis`/`recherche_frage` (Aussenwelt-Regel) → `context_info.recherche_hinweis`/`recherche_frage`. `ideen` (bemerkter Widerspruch/Fehler als Pendenz an einem Abschnitt oder Kapitel) → `context_info.proposals` als `idee_create`, normalisiert in [lib/chat-idee-proposals.js](../lib/chat-idee-proposals.js) (nur Orte im Buch, Abschnitt vor Kapitel, höchstens 5); **nichts wird angelegt**, der User erfasst jeden einzeln ([chats.md](chats.md#ideen-vorschläge-abschnitts--und-buch-chat)). | – (kein DB-Read; Validierung nutzt Content-Store) |

## Frontend

Buch-Chat-Karte ([public/partials/chat.html](../public/partials/chat.html), Zusätze pro Antwort per String-Include [book-chat-msg-extras.html](../public/partials/book-chat-msg-extras.html), Methoden [public/js/chat/book-chat.js](../public/js/chat/book-chat.js)). Quelle ist `chat_messages.context_info` (JSON) der Antwort:

- **Werkzeug-Verlauf**: geteilt mit Recherche-, Plot- und Ideen-Chat, siehe [chats.md](chats.md#geteiltes). `final_answer` erscheint nicht — es ist die Antwort.
- **Belege**: nummerierte Fussnoten aus `context_info.citations`, Link springt via `$app.gotoPageById`; ungültige Zitate durchgestrichen + Plakette «nicht bestätigt».
- **Recherche-Hinweis**: bei `recherche_hinweis` (und aktivem Recherche-Chat) Knopf «Im Recherche-Chat fragen» → Window-Event `EVT.RESEARCH_CHAT_ASK` (siehe [chats.md](chats.md#übergabe-buch-chat--recherche-chat)).
- **Abbruchgrund** (`stop_reason` `input_cap`/`max_iter`) als Hinweiszeile, **Kosten** der Antwort (`context_info.cost_usd`, nur Claude, aus [lib/pricing.js](../lib/pricing.js) zur Schreibzeit) in der Token-Zeile.
- **Abbrechen**: Knopf im Kartenkopf, solange die sichtbare Session läuft — Job-ID über `/jobs/active?type=book-chat&book_id=<sessionId>`, Abbruch über die Root-Mechanik `$app.cancelJob` (`DELETE /jobs/:id`).

Alle KI-/User-Felder laufen über `x-text`; die Antwort selbst über `_renderChatMarkdown` (markdown-it mit `html: false`, Roh-HTML wird escaped).
