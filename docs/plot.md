# Plot-Werkstatt (Beat-Board)

Planendes Pendant zur rückwärtsgewandten Szenen-/Ereignis-Analyse: Der User skizziert die Handlung seines Buches als Kanban-artiges Beat-Board — **Akte** als Spalten (`plot_acts`), **Beats** (einzelne Handlungspunkte) als Karten darin (`plot_beats`). KI assistiert ausschliesslich **planend/überwachend** (Brainstorm + Consistency gegen die Buchrealität), schreibt nie Fliesstext ins Manuskript (App-Philosophie: KI nur rückwärtsgewandt/weltaufbauend, nie generativ in den Buchtext).

**Optionale zweite Ordnungsachse — Handlungsstränge (Swimlanes, `plot_threads`):** Für grosse Multi-POV-Bücher wird das Board zum Raster **Akte (Spalten) × Stränge (Zeilen)**; ein Beat sitzt in der Zelle `(act_id, thread_id)`. Ein Strang ist optional an eine Hauptfigur gebunden (Katalog **oder** Werkstatt). **Opt-in / null Stränge = flaches Board:** ohne Strang rendert die flache Akt-Spaltenansicht unverändert ([plot-board-flat.html](../public/partials/plot-board-flat.html)); der erste Strang schaltet aufs Grid um ([plot-board-grid.html](../public/partials/plot-board-grid.html)). Die „ohne Strang"-Lane (`thread_id = NULL`) fängt alle nicht zugeordneten Beats.

Pro **Buch + User** skopiert (lokaler Karten-State, nicht im `catalog-store` — Plot ist nicht mit Figuren/Orten geteilt). Code: [db/plot.js](../db/plot.js) (Facade über [db/plot/](../db/plot/) — `structure` Akte/Stränge/Hybrid-Akte/Lückenlos-Nummerierung, `beats` CRUD/Brücken/Reorder, `figure-usage`, `relations`, `runs`, `anchor`, `shared`), [routes/plot.js](../routes/plot.js) + [routes/plot-helpers.js](../routes/plot-helpers.js) (`_loadOwned`, `_requireBook`, `_validChapterId`, Parser für Intensität/Flags, `_withAnchor`/`_anchorOpts`, Strang-Figur-Resolver), [routes/jobs/plot.js](../routes/jobs/plot.js) + [routes/jobs/plot/context.js](../routes/jobs/plot/context.js) (Kontext-Loader + Budget) + [routes/jobs/plot/result.js](../routes/jobs/plot/result.js) (Befund-Vertrag), [lib/plot-reading-order.js](../lib/plot-reading-order.js) (Lesereihenfolge), [public/js/cards/plot-card.js](../public/js/cards/plot-card.js), [public/js/book/plot.js](../public/js/book/plot.js) + [public/js/book/plot/](../public/js/book/plot/) (u. a. `beat-move.js`, `board-ui.js`, `konflikt-actions.js`, `derived/{board,coverage,tension}.js`), [public/partials/plot.html](../public/partials/plot.html) (Rahmen) + nested Partials (siehe „Swimlanes") + [plot-beat-cell.html](../public/partials/plot-beat-cell.html) (geteiltes Beat-Markup via Fragment-Include, bindet seinerseits [plot-beat-edit.html](../public/partials/plot-beat-edit.html) → [plot-beat-move.html](../public/partials/plot-beat-move.html) ein), [public/css/book/plot/board.css](../public/css/book/plot/board.css) + [plot/widgets.css](../public/css/book/plot/widgets.css) + [plot/swimlane.css](../public/css/book/plot/swimlane.css) + [plot/relations.css](../public/css/book/plot/relations.css) + [plot/tools.css](../public/css/book/plot/tools.css), [public/js/prompts/plot.js](../public/js/prompts/plot.js) + [prompts/plot/lines.js](../public/js/prompts/plot/lines.js) / [prompts/plot/board.js](../public/js/prompts/plot/board.js). Trigger: `tile.plot` (Quick-Pill / Palette-Aliase `handlung|beat|board|akt|struktur|outline|dramaturgie|story|wendepunkt`). Hash-Permalink `#book/:bookId/plot[/:beatId]` — der optionale `beatId` ist der gerade bearbeitete Beat (Root-SSoT `plotBeatId`, spiegelt `editingBeatId`); Deep-Link öffnet die Karte + fokussiert den Beat (Edit + zentriert ins Bild via `plot:focus-beat`-Event / `_pendingFocusBeatId` bis das Board geladen ist). Gruppe `world`, `minRole: 'editor'` (planendes Werkzeug, kein Lesezugang).

## Datenmodell

```
plot_acts (id, book_id→books CASCADE, user_email, name, farbe,
           thread_id→plot_threads CASCADE, archiviert, position, created_at, updated_at)
plot_threads (id, book_id→books CASCADE, user_email, name, farbe,
              figure_id→figures SET NULL, draft_figure_id→draft_figures SET NULL,
              chapter_id→chapters SET NULL,
              position, created_at, updated_at)
   └── 1:N plot_beats (id, book_id→books CASCADE, act_id→plot_acts CASCADE,
                       thread_id→plot_threads SET NULL, user_email,
                       titel, beschreibung, status, verworfen, chapter_id→chapters SET NULL,
                       intensitaet, zeit, sort_order, created_at, updated_at,
                       content_updated_at)
          ├── M:N plot_beat_figures (beat_id→plot_beats CASCADE, figure_id→figures CASCADE,
          │                          PK(beat_id, figure_id))
          ├── M:N plot_beat_draft_figures (beat_id→plot_beats CASCADE,
          │                                draft_figure_id→draft_figures CASCADE,
          │                                PK(beat_id, draft_figure_id))
          └── M:N plot_beat_locations (beat_id→plot_beats CASCADE,
                                       location_id→locations CASCADE,
                                       PK(beat_id, location_id))
```

- **`plot_acts`** — Board-Spalten (Akte/Phasen), geordnet via `position` **pro Scope** (geteilt vs. je Strang eine eigene 0..n-Sequenz). `farbe` optional (max 32 chars). **Hybrid-Akte (`thread_id`, FK → `plot_threads` CASCADE):** `NULL` = **geteilter** Akt (flaches Board + alle Stränge ohne eigene Aktstruktur); gesetzt = der Akt gehört **nur** Strang `T`. „Strang hat eigene Akte" wird allein aus der Existenz strang-eigener Akte abgeleitet (kein Flag, kein Drift). `forkThreadActs` klont die geteilten Akte in den Strang + hängt dessen Beats auf die Klone um (der Klon **erbt `archiviert`** — sonst tauchte ein abgeschlossener Akt beim Fork als offene Spalte wieder auf); `unforkThreadActs` hängt sie positionsweise zurück (Überzahl → letzte geteilte Spalte) + löscht die eigenen Akte. Welcher Akt zu welchem Beat passt, regelt die Hybrid-Regel (`actFitsThread`, siehe „Validierung"). **`archiviert` (0/1)** = der Akt ist abgeschlossen, seine Beats sind ins Manuskript eingearbeitet → siehe „Archiv" unten.
- **`plot_threads`** — Board-Zeilen (Handlungsstränge / Swimlanes), geordnet via `position`. `farbe` = Palette-Key (analog `plot_acts.farbe`). Optionale Hauptfigur-Bindung: `figure_id` (FK → `figures.id`, INTEGER; nach aussen als TEXT-`fig_id` exponiert via `_THREAD_SELECT`-JOIN) **oder** `draft_figure_id` (FK → `draft_figures.id`, INTEGER, bereits Frontend-Identität). Beide SET NULL — Figur löschen entkoppelt nur die Bindung. Ein Strang darf auch ungebunden sein (z. B. „B-Story"). Optionale Kapitel-Bindung: `chapter_id` (FK → `chapters` SET NULL; `chapter_name` via `_THREAD_SELECT`-JOIN). **Live-Vererbung Strang → Beat:** ein Beat einer Strang-Lane erbt implizit die Hauptfigur des Strangs (immer als beteiligt) und — sofern er kein eigenes `chapter_id` hat — dessen Kapitel. Die geerbten Werte werden **nie** auf den Beat geschrieben (nur Anzeige im Grid als Entitäts-Referenzen mit Zusatz „· Strang“ via `inheritedFigureForBeat`/`inheritedChapterForBeat` + KI-Kontext); Strang-Bindung ändern → alle Beats der Lane folgen automatisch.
- **`plot_beats`** — Karten in einer Zelle (Akt × Strang), geordnet via `sort_order` **pro Zelle** (`act_id` + `thread_id`). `thread_id` (SET NULL) ist die Strang-Zuordnung (`NULL` = „ohne Strang"-Lane; null Stränge → flaches Board). `status ∈ {geplant, im_buch}` (CHECK-Constraint) ist die binäre Realisierungsachse (Idee ↔ eingearbeitet). `verworfen` (0/1, CHECK) ist eine eigene, orthogonale Verwerfen-Achse — bleibt bei Status-Wechsel erhalten, hält verworfene Beats aus Spannungsbogen/Coverage/aktiver Verteilung raus. `chapter_id` (SET NULL) verknüpft den Beat mit dem Zielkapitel im Manuskript. **`content_updated_at`** ist die Inhaltszeit für die Verankerungs-Stale-Heuristik: gestempelt nur, wenn sich `titel`, `beschreibung`, `status` oder `verworfen` tatsächlich ändern (genau die Felder, die Query und Verankerungs-Auswahl bestimmen) — DnD, Fork, Kapitel, Intensität, Zeit und Figuren lassen sie stehen. **Why:** `updated_at` ändert sich bei jedem Verschieben; gegen sie gemessen, böte die Karte nach jedem Drag einen nutzlosen Anker-Neulauf an.
- **`plot_beat_locations`** — M:N-Brücke Beat ↔ Schauplatz (`locations.id`, INTEGER-FK; nach aussen die TEXT-`loc_id`, wie bei den Figuren — `routes/locations.js` mappt `id: r.loc_id`). **Vierte Brücke** neben Katalog-Figur, Werkstatt-Figur und Motiv, derselbe Schnitt, andere Achse: **WO** spielt der Handlungspunkt. Der Ort ist ein dramaturgisches Werkzeug (die Konfrontation findet dort statt, wo es anfing); ohne die Brücke konnte weder die Konsistenzprüfung noch der Brainstorm über Schauplätze urteilen. Kuratiert im Beat-Edit (`entityPicker` entity `ort`), read-only als `.tag--ort`-Badge auf der Karte (Klick → Orte-Karte).
- **`plot_beats.zeit`** — **WANN** in der erzählten Welt der Beat spielt. Freitext wie `figure_events.datum` (ein Plan trägt „Sommer 1987" so oft wie ein Datum); die Jahreszahl zieht derselbe Parser heraus wie überall sonst ([lib/figure-years.js](../lib/figure-years.js)#`yearFromString`). Schaltet die **deterministische Zeit-Messung** frei (siehe unten).
- **`plot_beat_figures`** — M:N-Brücke Beat ↔ Katalog-Figur (`figures.id`, INTEGER-FK), welche Figuren ein Handlungspunkt involviert. Nach aussen wird die TEXT-`fig_id` exponiert (Frontend-Identität), Schreib-/Lesepfad übersetzt via `resolveFigureIds`.
- **`plot_beat_draft_figures`** — parallele M:N-Brücke Beat ↔ Werkstatt-Figur (`draft_figures.id`, INTEGER-FK). Anders als bei Katalog-Figuren IST die `draft_figures.id` bereits die Frontend-Identität (keine TEXT-Indirektion). So kann ein Beat sowohl bereits extrahierte Buch-Figuren als auch vorwärts-entwickelte, evtl. noch nicht im Manuskript stehende Werkstatt-Figuren involvieren.
- **`plot_beats.intensitaet`** — optionaler Spannungswert 1–5 (CHECK `NULL OR BETWEEN 1 AND 5`), speist den Spannungsbogen. `NULL` = nicht gesetzt; verworfene Beats fliessen nicht in den Bogen.
- **`plot_consistency_runs`** — Historie der Konsistenz-Prüfungen, pro (Buch, User) skopiert: `book_id` (FK → `books` CASCADE), `created_at`, `konflikt_count` (denormalisiert fürs Listen-Rendering), `result_json` (`{ konflikte, fazit, erledigt, vorlauf_run_id }`; Alt-Läufe mit nur `{ konflikte, fazit }` bleiben lesbar), `model`. `ON DELETE CASCADE` — die Historie stirbt mit dem Buch. Anders als die Figuren-Werkstatt (`werkstatt_runs` pro Draft) bezieht sich Plot auf das Buch, nicht auf einen Draft.
- **`plot_brainstorm_runs`** — Historie der Brainstorm-Läufe, pro (Buch, User) skopiert **und** zusätzlich pro `act_id` (FK → `plot_acts` SET NULL) / `thread_id` (FK → `plot_threads` SET NULL): `book_id` (CASCADE), `created_at`, `vorschlag_count` (denormalisiert), `result_json` (`{ vorschlaege }`), `model`. **act_id/thread_id SET NULL** — ein gelöschter Akt/Strang entkoppelt den Lauf nur; `act_name`/`thread_name` kommen zur Lesezeit per JOIN (kein Snapshot, fallen bei gelöschtem Akt auf `null`). Nur Läufe mit ≥1 Vorschlag werden persistiert.
- **`plot_beat_relations`** — gerichtete **Beat-zu-Beat-Kante** (`from_beat_id --typ--> to_beat_id`, beide FK → `plot_beats` CASCADE; `book_id` CASCADE; pro Buch + User). `typ` ist Freitext (analog `figure_relations.typ`) mit kuratierten Frontend-Vorschlägen in zwei Familien: **Setup/Payoff** (`bereitet-vor`, `zahlt-ein`) + **Kausalität** (`fuehrt-zu`, `motiviert`, `blockiert`, `spiegelt`). `UNIQUE(from_beat_id, to_beat_id, typ)` verhindert Duplikat-Kanten. Modelliert Kausalketten und Tschechows-Gewehr-Paare **explizit**, statt sie nur aus der Prosa raten zu lassen — der Consistency-Check liest sie als Kontext (hängender Setup ohne Payoff, Wirkung vor Ursache, `im_buch`-Beat, der auf einen noch geplanten Beat baut). Read-only Badges auf der Beat-Karte (ausgehende Kanten), kuratiert im Beat-Edit. Nie generativ.
- **`plot_beat_occurrences`** — abgeleiteter **Ist**-Index der Beat-Verankerung (Pendant zu `motif_occurrences`): wo ein geplanter Beat semantisch/wörtlich im Buchtext auftaucht. `beat_id` (FK → `plot_beats` CASCADE), `book_id` (CASCADE), `kind` ∈ {page, scene} (sentinel-frei via CHECK, genau eine Ref gesetzt), `page_id`/`scene_id` (CASCADE, nullbar je `kind`), `score` (roher Cosinus der semantischen Suche, 0–1; `null` bei wörtlichen FTS-Treffern), `snippet`, `source` ∈ {semantic, trigger}. Full-Replace pro Beat je Anchor-Lauf (kein `content_hash` — die Erkennung nutzt den vorhandenen Embedding-/FTS-Index und ist billig). Rein abgeleitet, nie handgepflegt. Speist das **Drift-Badge** auf der Beat-Karte (siehe unten).

**Validierung (Server-seitig, Pflicht):**
- `resolveFigureIds(bookId, userEmail, fig_ids)` filtert die Katalog-Figuren aufs Subset, das wirklich zu (Buch, User) gehört, und übersetzt TEXT-`fig_id` → INTEGER `figures.id` — verhindert Fremd-Verschmutzung der M:N-Tabelle. Dient auch der Strang-Bindung (`figure_id`).
- `resolveDraftFigureIds(bookId, userEmail, draft_figure_ids)` analog für Werkstatt-Figuren: filtert die INTEGER-IDs aufs (Buch, User)-Subset von `draft_figures`. Unbekannte/Fremd-IDs fallen still raus. Dient auch der Strang-Bindung (`draft_figure_id`).
- `resolveMotifIds(bookId, userEmail, motif_ids)` analog für Motive: filtert die INTEGER-`motifs.id` aufs (Buch, User)-Subset — kein Cross-Buch-Leak in `motif_beats`. Der Beat-Schreibpfad macht Full-Replace **pro Beat** (`_setBeatMotifs`, `WHERE beat_id = ?`) und kollidiert nicht mit dem Motiv-seitigen Full-Replace der Werkstatt (`setMotifBeats`, `WHERE motif_id = ?`).
- `resolveLocationIds(bookId, location_ids)` analog für Schauplätze (TEXT-`loc_id` → INTEGER `locations.id`); filtert nur nach Buch — Orte sind ein buchweiter Katalog.
- `_validChapterId(bookId, chapterId)` ([routes/plot-helpers.js](../routes/plot-helpers.js)) erzwingt, dass das Kapitel zum Buch gehört, sonst `NULL`. Dient sowohl dem Beat-`chapter_id` als auch der Strang-Kapitel-Bindung (`plot_threads.chapter_id`).
- `_validThreadId(bookId, userEmail, threadId)` ([db/plot/structure.js](../db/plot/structure.js)) erzwingt, dass der Strang zu (Buch, User) gehört, sonst `NULL` — kein Fremd-Strang an einem Beat.
- Beim Beat-Anlegen/-Verschieben muss der Ziel-Akt zum selben Buch + User gehören (`ACT_MISMATCH` sonst).
- **Hybrid-Regel** `plotDb.actFitsThread(act, threadId)` (DB-Layer, exportiert): ein Strang **mit** eigenen Akten darf **nur** auf seinen eigenen Akten liegen; ein Strang **ohne** eigene Akte und die „ohne Strang"-Lane nur auf **geteilten** Akten. Verstoss → `ACT_THREAD_MISMATCH`. Geprüft bei `POST /beats`, bei `PATCH /beats` (gegen das **resultierende** Paar `act_id`/`thread_id`), in `PUT /beats/order` und in der Route des Brainstorm-Jobs. **Why die strenge Form:** ein geforkter Strang mit einem Beat auf einem geteilten Akt stünde in einer Spalte, die sein eigener Grid-Block nicht rendert — der Beat wäre unsichtbar, und die Lesereihenfolge wüsste nicht, wohin mit ihm.
- **`PUT /beats/order` validiert den ganzen Payload, bevor es schreibt** (eine Transaktion, jeder Verstoss rollt komplett zurück): Gruppe ist ein Objekt, `actId` eine Ganzzahl, `beatIds` ein Array, jeder Beat gehört zu (Buch, User) und kommt nur einmal vor, `threadId` ist leer oder ein eigener Strang (fremd/unbekannt → `ORDER_INVALID`), Akt gehört zu (Buch, User) (`ACT_MISMATCH`), Akt passt zum Strang (`ACT_THREAD_MISMATCH`, nur für Gruppen mit Beats — eine leere Quellzelle bewegt nichts).
- **Feld-Validierung** (`POST` + `PATCH /beats`, Parser in [routes/plot-helpers.js](../routes/plot-helpers.js)): `intensitaet` nur `null`/`''` oder Ganzzahl 1–5 (sonst `INVALID_INTENSITAET`), `status` nur `geplant`/`im_buch` (sonst `INVALID_STATUS`), `verworfen` (und `archiviert` am Akt) nur `true`/`false`/`0`/`1` (sonst `INVALID_FLAG` — kein truthy-Casting, `"false"` würde sonst zu 1).
- `createBeatRelation` validiert **beide** Beats (`from`/`to`) aufs (Buch, User)-Subset (`_beatBelongs`), verbietet die **Selbst-Kante** (`from === to`) und ist via `UNIQUE` idempotent — kein Fremd-Verweis, kein Duplikat. `typ` wird getrimmt + auf 40 Zeichen gedeckelt.
- Limits: Titel 200, Beschreibung 4000, Zeit 120, Akt-Name 120, Strang-Name 120, Farbe 32 Zeichen.

So kann der Plot Beats auf den **inneren Konflikt** der Figur zuschneiden statt nur auf den Namen — Brainstorm hat dafür eine eigene Regel-Bullet.

Gekappt über das Budget-Tier, nicht über ein fixes LIMIT.
- `anchorContext` (nur Consistency) — der persistierte Textbeleg-Index (`plot_beat_occurrences`, aus dem [beat-anchor-Job](#beat-verankerung-soll-status-vs-ist-fundstellen)) als plain object `beat_id → { count, top[] }`. **Nur wenn der Index befüllt ist** (`occTotal > 0`) — ein leerer Index bedeutet „nie verankert", nicht „nichts im Buch", sonst falsche Drift-Flut; dann `anchorMap = null` und die Prüfung läuft gegen den Szenen-Index. Der `[#id]`-Board-Marker + die Beat-Titel machen die Kanten für die KI referenzierbar.

Katalog-Bindung über TEXT-`fig_id` → Name (Direkt-SQL auf `figures`), Werkstatt-Bindung über `draft_figures.id` → Name, Kapitel über `chapter_name` (aus `listThreads`-JOIN). **Brainstorm:** schlägt 3–7 prägnante Beats (3–10 Wörter Label + 1-Satz-Begründung) für **einen** Akt vor, passend zum bisherigen Board + Buchkontext + Katalog- + Werkstatt-Figuren. Der **Zielakt wird per ID** übergeben und im Prompt mit seinem Scope benannt („eigener Akt von Strang …" bzw. geteilt); die „NICHT wiederholen"-Liste filtert per `act.id`. **Zell-granular bei Strang:** mit `thread_id` grundiert der Prompt einen `ZIEL-STRANG`-Block (Strang-Name + gebundene Hauptfigur → „Beats sollen diesen Erzählstrang vorantreiben"), und die „NICHT wiederholen"-Liste wird auf die Zelle (Akt × Strang) gefiltert. Ohne `thread_id` akt-weit. Die Job-Route prüft das Paar vorab mit `actFitsThread` (`400 ACT_THREAD_MISMATCH`) — ein Vorschlag für eine Zelle, in der kein Beat liegen darf, wäre nicht übernehmbar. `maxTokens` 8000 (Raum für adaptives Thinking). Der Job gibt `threadId` im Result zurück, damit das Frontend den Vorschlag in der richtigen Zelle anwendet. **Jeder Lauf mit ≥1 Vorschlag wird in `plot_brainstorm_runs` historisiert** (best-effort, `runId` im completeJob-Payload) — so kann der User frühere Vorschläge später wieder ansehen und anwenden.

**Consistency:** prüft den geplanten Plot in sich + gegen die Buchrealität — Beats mit `im_buch` ohne Szenen-Entsprechung, geschriebene-aber-noch-`geplant`-Drift, Chronologie-Brüche (Beat-Reihenfolge vs. verknüpfte Kapitel), Logiklücken, fehlende Wendepunkte, verworfene-aber-noch-präsente Inhalte. **Textbeleg-Erdung:** liegt ein befüllter Verankerungs-Index vor (`anchorContext`), trägt jeder `im_buch`-Beat im Board-Outline einen `⟨Textbeleg …⟩`-Marker aus der semantischen Suche über das **echte Manuskript** (`im_buch`+Beleg mit Seite/Ausschnitt · `im_buch` ohne Beleg = hartes Drift-Signal); geplante/verworfene Beats tragen keinen Marker (werden nicht verankert). Ein `TEXTBELEGE`-Regelblock weist die KI an, das als primären Realitätsanker (genauer als der Szenen-Index) zu nutzen und die belegende Seite im Befund zu nennen — Ähnlichkeit, kein Beweis, die KI urteilt am Ausschnitt. Der Marker ist verworfen-sicher (verworfene Beats bekommen keinen). **Mit Strängen** zusätzlich: vollständiger Bogen je Strang (Setup/Eskalation/Auflösung, besonders je Hauptfigur), Strang-Balance / POV-Lücken, Verweben der Stränge. **Spannungsbogen** (`_spannungLines`): der Intensitätsverlauf je Lane/Akt geht als eigener Block mit — Prüfpunkt flacher Mittelteil, Höhepunkt zu früh, kein Abfall nach der Auflösung; fehlende Intensitätswerte sind kein Mangel. Werkstatt-Figuren gelten als legitime, geplante Figuren (kein „nicht im Buch"-Befund allein deswegen). Leeres `konflikte`-Array + bestätigendes `fazit` bei Stimmigkeit. `maxTokens` 16000. **Jeder Lauf wird in `plot_consistency_runs` historisiert** (best-effort beim Job-Complete; DB-Fehler verschluckt das Resultat nicht) und der frisch persistierte `runId` im completeJob-Payload zurückgegeben — so kann der User frühere Prüfungen später nochmal ansehen.

**Delta-Check gegen den Vorlauf:** gibt es einen früheren Lauf, bekommt der Prompt dessen Befunde kompakt (`_deltaBlock`, gekappt über `ctxLimits().vorlauf`) plus die seit dessen `created_at` geänderten Beats. Das Modell markiert jeden Befund mit `seit_letztem_lauf` (`bestehend` = noch gültiger bekannter Befund, `neu`) und listet behobene Vorlauf-Befunde in `erledigt[]`. Ohne Vorlauf fehlen beide Felder (`erledigt` immer leer — es gäbe nichts, wogegen „behoben" behauptet werden könnte).

**Ergebnis-Vertrag** (`normalizeKonflikte`/`normalizeErledigt` in [result.js](../routes/jobs/plot/result.js), unit-getestet [tests/unit/plot-consistency-result.test.mjs](../tests/unit/plot-consistency-result.test.mjs)): Top-Level `{ konflikte, fazit, erledigt[] }`, Pflichtfelder geprüft (`konflikteMissing`/`fazitMissing`/`erledigtInvalid`). Jeder Befund = `{ beat, beat_id, schwere, typ, problem, vorschlag, aktion, fundstelle, seit_letztem_lauf? }`:
- `beat_id` wird aufs volle Board validiert; fehlt sie, matcht der Titel — aber nur ein **eindeutiger** (mehrdeutige Titel matchen nicht, lieber kein Beat als der falsche).
- `typ ∈ status | chronologie | kausalitaet | setup_payoff | strang | figur | weltgesetz | spannung | logik | struktur` (`PLOT_KONFLIKT_TYP_ENUM`, Schema-Pflicht; Unbekanntes → `logik`).
- `aktion` = `null` | `{ art:'status', wert:'im_buch'|'geplant' }` | `{ art:'verwerfen' }` | `{ art:'relation', typ, ziel_beat_id }` (`typ` aus `PLOT_AKTION_REL_TYPES`: `bereitet-vor|zahlt-ein|fuehrt-zu|motiviert|blockiert|spiegelt`). Das Modell emittiert ein flaches Objekt mit `art:'keine'` als Default; der Server normalisiert (`normalizeAktion`) und setzt `null`, wenn der Beat nicht auf dem Board steht, das Ziel der Beat selbst ist oder fehlt, ein Wert ungültig ist, die Aktion ein No-op wäre (Status schon so, schon verworfen) oder eine Status-Aktion einen verworfenen Beat träfe. **Why serverseitig:** der Aktions-Knopf in der UI führt die Aktion mit einem Klick aus — er darf nur erscheinen, wenn sie gültig und wirksam ist.
- `fundstelle` deterministisch aus dem Verankerungs-Index (siehe Consistency-UI).

`result_json` speichert `{ konflikte, fazit, erledigt, vorlauf_run_id }`, das Job-Result zusätzlich `vorlaufRunId` + `runId`. Alt-Läufe ohne `typ`/`aktion`/`erledigt` bleiben lesbar.

**Severity-Skala** `kritisch|stark|mittel|schwach|niedrig` (Schema-enforced enum `PLOT_SEVERITY_ENUM`) — gleiche Skala wie die [Figuren-Werkstatt](figur-werkstatt.md); die Farbe kommt aus `befundSeverityClass` (siehe Consistency-UI).

**Job-Labels:** `job.label.plotBrainstorm` (`{ akt }`-Param) / `job.label.plotConsistency`. Dedup via `findActiveJobId(type, entityKey, userEmail)`.

**Archivierter Zielakt:** wird ein Brainstorm-Lauf eines inzwischen archivierten Akts aus der Historie geöffnet, zeigt die Karte den Hinweis `plot.brainstorm.actArchived` statt des Panels (im Archiv wird nicht geplant, siehe unten).

## Archiv: abgeschlossene Akte (`plot_acts.archiviert`)

Ein Akt, dessen Beats **ins Manuskript eingearbeitet** sind, ist erledigt — er soll das Board nicht weiter füllen und in der Konsistenzprüfung nicht weiter als Arbeitsvorrat auftauchen. Genau dafür ist `archiviert` (0/1, Migration 275, additiv).

**Nicht zu verwechseln mit `plot_beats.verworfen`** — die beiden sagen das Gegenteil: *verworfen* = ausgemustert, soll **nicht** ins Buch; *archiviert* = fertig, **ist** im Buch. Daraus folgt die tragende Invariante:

> **Archivieren ist eine Anzeige- und Review-Achse, keine Daten-Achse.** Die Beats eines archivierten Akts bleiben unangetastet und zählen **weiter** in jeder Kennzahl: Status-Verteilung (`boardStats`/`actStats`), Spannungsbogen, Figuren-Coverage, `pageBeatCounts`/`chapterBeatCounts`, Beat-Verankerung, Buchübersichts-Tile. **Why:** sie stehen im Buch — würde der Bogen sie ausblenden, verlöre er beim Archivieren von Akt 1 seinen Anfang, und die Figuren-Coverage meldete plötzlich Lücken für längst verplante Figuren. Keine `beatsFor*`-Methode filtert nach Archiv.

**Was das Flag wirklich tut:**

- **Board:** die Spalte verlässt das Render-Set. Gefiltert wird an genau zwei Stellen in [derived/board.js](../public/js/book/plot/derived/board.js) — `sharedActs()` (flaches Board **und** geteilte Grid-Region) und `actsForThread()` (strang-eigene Grid-Blöcke, via `gridRows()`); beide über `_actVisible()`. Das flache Board rendert bewusst `sharedActs()` statt einer eigenen, scope-blinden Liste: ohne Strang ist jeder Akt geteilt (`plot_acts.thread_id` CASCADEt mit dem Strang), eine zweite Liste wäre nur eine zweite Filterstelle zum Vergessen. Der Schalter `plotShowArchived` (per User persistiert wie `plotHideImBuch`, **nicht** in `PLOT_FILTER_SCOPES` — Gewohnheit, kein buch-skopierter Filter) holt sie zurück ins Bild, sichtbar erst ab `archivedActCount() > 0`. Er steht in der **Filter-Leiste neben `plotHideImBuch`**, auf derselben Ebene: beides sind Schalter des Arbeitsmodus, und zwei getrennte Zeilen liessen sie unverwandt aussehen. Weil er aber nicht an den Beats hängt (ein archivierter Akt ohne Beats muss erreichbar bleiben), trägt die Leiste `beats.length > 0 || archivedActCount() > 0` und die Beat-Bedingung sitzt an den einzelnen Beat-Filtern. Die eingeblendete Spalte ist gedämpft + gestrichelt (`.plot-column--archiviert` / `.plot-swim-acthead--archiviert`) und trägt eine `archiviert`-Plakette (generisches `.badge .badge-neutral` — wertfreie Einordnung, siehe [DESIGN.md](../DESIGN.md) „Badges & Tags"; kein eigenes Badge daneben) — bewusst **nicht** durchgestrichen, das ist die Sprache der verworfenen Beat-Karte.
- **`_threadHasOwn` bleibt ungefiltert** — sind alle eigenen Akte eines Strangs archiviert, hat er weiterhin eine eigene Struktur. Sonst kippte er im Grid zurück in die geteilte Region und seine Beats hingen an Akten, die dort nicht stehen.
- **Kein Planen im Archiv:** „Beat hinzufügen", der Brainstorm-Knopf und das Brainstorm-Vorschlags-Panel fallen in der archivierten Spalte weg (flach **und** Grid-Zellfuss) — ein Vorschlag landete sonst in einer Spalte, die zugeht; ein Historien-Lauf eines archivierten Akts öffnet nur den Hinweis `plot.brainstorm.actArchived`. DnD bleibt erlaubt: einen Beat aus dem Archiv zu ziehen (oder bewusst hineinzuschieben) ist eine legitime Korrektur, kein Integritätsbruch — darum auch **kein** Server-Guard, `archiviert` ist keine Vorbedingung für Beat-Schreibpfade.
- **Konsistenzprüfung:** der Akt bleibt im Board-Outline (`AKT (…, ARCHIVIERT: …)`), weil Kausalketten und Setup/Payoff-Kanten über ihn hinweg prüfbar bleiben müssen — dazu der `ARCHIVIERTE AKTE`-Regelblock: keine Status-Pflege, keine fehlenden Beats, keine Lücken dort melden, **aber** jeden Befund melden, der in den offenen Plot hineinwirkt. **Why beides:** ihn ganz aus dem Prompt zu schneiden machte Archivieren zum Weg, Befunde zu verstecken; ihn unmarkiert zu lassen, produziert genau die Meldungen, die die Autorin zugeklappt hat.
- **Akt-Reihenfolge:** `moveAct` überspringt unsichtbare Nachbarn (`_actVisible`) — ein Tausch mit einer archivierten Spalte wäre ein Klick ohne sichtbare Wirkung.
- **Undo/Redo:** `toggleActArchive` zeichnet einen `act-fields`-Record wie name/farbe (`{ archiviert }`), damit über den generischen `_hPatchAct`-Applier. Kein Confirm beim Archivieren — es geht nichts verloren, und der Weg zurück ist derselbe Knopf.

## Beat-Verankerung (Soll status vs. Ist-Fundstellen)

Rückwärtsgewandtes Überwachungs-Feature analog zur [Motiv-Werkstatt](motiv-werkstatt.md#soll-vs-ist): findet für jeden als **`im_buch` markierten** Beat die **tatsächlichen Fundstellen im Buchtext** und gleicht sie gegen den `status` ab — die Frage ist „ist das, was laut Plan schon geschrieben sein soll, wirklich im Text?". Nutzt die vektorisierte Buchrealität (semantische Suche), schreibt nie in den Text.

**`im_buch`- UND `geplant`-Beats werden verankert — mit unterschiedlicher Schwelle, beide gegen den rohen Cosinus.** `im_buch`-Beats: Treffer ab der Bestätigungs-Schwelle **`plot.anchor.confirm_min_score`** (Default 0.45, 0 = jeder semantische Treffer) zählen (Soll-Ist-Drift — steht das laut Plan Geschriebene wirklich im Text?). **Why eine Schwelle:** die Nächster-Nachbar-Suche liefert für **jeden** Beat Treffer; ohne Untergrenze hiesse `confirmed` nichts. `geplant`-Beats: **nur** Treffer oberhalb der hohen Promotion-Schwelle **`plot.anchor.promote_min_score`** (Default 0.55, 0 = aus) — das ist die **Anker-Rückrichtung**: findet ein geplanter Beat einen *starken* Textbeleg, ist er offenbar schon geschrieben → Promotion-Vorschlag „Als im Buch markieren". Die hohe Schwelle verhindert die Flut schwacher `TOP_K`-Treffer, die praktisch jeden Beat träfe (darum wird sie beim Anchor-Lauf **beim Speichern** angewandt, nicht erst beim Lesen; ohne Semantik-Backend werden geplante Beats gar nicht gescannt — ein wörtlicher Titel-FTS-Treffer ist ein zu schwaches Promotion-Signal). Verworfene Beats sind immer raus.

**Job `beat-anchor`** ([routes/jobs/beat-anchor.js](../routes/jobs/beat-anchor.js)) — **kein `callAI`/Prompt** (Klon des `motif-scan`-Musters). Pro nicht-verworfenem Beat: Query `titel. beschreibung` über [lib/semantic-retrieval.js](../lib/semantic-retrieval.js) (`semanticQuery`, kinds page/scene; die Freitext-Pipeline fusioniert intern schon FTS). **Konfidenz ist der rohe Cosinus `semScore`**, nicht der fusionierte `score` — der ist bei Hybrid ein RRF-Rangwert (max. ~0.03) bzw. mit Rerank eine Relevanz, beides nicht gegen eine absolute Schwelle vergleichbar. Reine FTS-Fusionskandidaten (`semScore` null) sind semantisch nicht belegt und werden übersprungen; gespeichert wird der Cosinus. Gefiltert mit `confirm_min_score` (`im_buch`) bzw. `promote_min_score` (`geplant`). Fehlt das Embedding-Backend, fällt der Anchor für `im_buch` auf reine FTS über den Beat-Titel zurück (`score = null`, `source = 'trigger'`; für `geplant` nicht — s.o.). Full-Replace der `plot_beat_occurrences` pro Beat; für alle **verworfenen** Beats (und `geplant` bei `promote_min_score = 0`) werden die Fundstellen geleert (kein Stale-Index nach Rückstufung/Verwerfen). **Fehler kosten nur den einen Beat:** pro Beat `try/catch` — geloggt, übersprungen, seine bisherigen Fundstellen bleiben stehen (ein Ausfall ist keine Aussage „nicht im Text"); `AbortError` wird weitergereicht. Ein während des Laufs gelöschter Beat lässt `replaceBeatOccurrences` `false` liefern, nichts wird geschrieben. Das Ergebnis zählt die übersprungenen Beats in `failed`. Nacht-Cron `anchorAllBooks` ([server.js](../server.js)) zieht den Ist-Index aller (Buch, User)-Scopes mit Beats nach — hinter `embed-index`-Reindex + `motif-scan`, damit frischer Text eingebettet ist.

**Payload:** `GET /plot` hängt an jeden Beat `occ_count` + `occ_top[]` (Top-Fundstellen mit `page_id`/`page_name`/`snippet`/`score`) sowie `beatAnchor = { stale, ranAt }` ([db/plot/anchor.js](../db/plot/anchor.js)). `POST`/`PATCH /beats` liefern `occ_count`/`occ_top` mit demselben Filter (`beatOccurrenceEntry`), damit das Badge nach dem Speichern nicht kippt.
- **`ranAt`** (`beatAnchorLastRun`) = ISO-Zeitpunkt des jüngsten Anker-Laufs oder `null` = nie verankert. Quelle: Start des jüngsten erfolgreich beendeten `beat-anchor`-Jobs dieses (Buch, User) aus `job_runs`, Fallback `MAX(plot_beat_occurrences.created_at)`. **Why `job_runs`:** ein Lauf mit 0 Fundstellen wäre aus den Fundstellen allein unsichtbar — er beendet aber genauso den Stale-Zustand und macht den Index „bekannt".
- **`stale`** (`beatAnchorStale(bookId, userEmail, statuses)`) = es gibt einen relevanten Beat, dessen `content_updated_at` jünger ist als der letzte Lauf (bzw. es lief noch nie einer). Gemessen wird gegen den **Start** des Laufs — ein während des Laufs geänderter Beat gilt danach weiter als veraltet. Relevant sind die Beats, die tatsächlich verankert werden: immer `im_buch`, zusätzlich `geplant` **nur wenn** `promote_min_score > 0` (die Route reicht das Status-Set durch, damit die reine DB-Schicht die App-Setting nicht lesen muss — sonst würde ein geänderter geplanter Beat bei ausgeschalteter Promotion fälschlich „Verankerung aktualisieren" anbieten), plus Beats, die noch Fundstellen tragen (ihre Rückstufung räumt erst der nächste Lauf ab). DnD, Fork, Kapitel, Intensität und Figuren machen nicht stale (siehe `content_updated_at`).

Der Payload läuft durch **zwei Lese-Filter** in `beatOccurrenceMap(bookId, userEmail, { minScore, navigableOnly })` ([db/plot/anchor.js](../db/plot/anchor.js)) — `count` **und** `top` gemeinsam, damit Badge-Zahl und Popover-Liste konsistent bleiben:
- `navigableOnly: true` (immer für den Board-Payload) — Fundstellen ohne anspringbare Seite (Szene ohne verknüpfte `page_id`) fallen raus; ein Ziel ohne Seite kann man nicht öffnen.
- `minScore` = App-Setting **`plot.anchor.min_score`** (0 = aus, Default) — blendet schwache semantische Treffer aus (Vergleich gegen den gespeicherten Cosinus). Wörtliche FTS-/Trigger-Treffer (`score = null`) sind nie betroffen. Wirkt am Lese-Chokepoint → **sofort ohne Anchor-Neulauf**. Admin-Tab „Semantik" → „Plot-Verankerung" (dort auch `confirm_min_score` und `promote_min_score`). `anchorContext` (Consistency) ruft `beatOccurrenceMap` **ungefiltert** → die KI-Erdung behält den vollen Textbeleg-Kontext.

**Fundstellen-Popover:** Klick auf ein zählendes Badge (`confirmed`) öffnet ein in die Karten-Wurzel teleportiertes `.context-menu`-Content-Popover ([plot-anchor-popover.html](../public/partials/plot-anchor-popover.html), `openBeatOccPopover`/`gotoOccurrence` in [ai.js](../public/js/book/plot/ai.js), positioniert über `computePopoverPos`/`refinePopoverPos` aus [popover-anchor.js](../public/js/popover-anchor.js) wie das Strang-Menü) — listet die `occ_top`-Fundstellen (Seitenname + Snippet + Score, Score-Chip erst ab ≥ 1 %), jede Zeile springt an die Textstelle. „und N weitere", falls `occ_count > occ_top.length`. Styling `.plot-occ-*` in [board.css](../public/css/book/plot/board.css).

**Drift-Badge (Frontend):** reine Klassifikation `classifyBeatAnchor(status, occCount, verworfen, anchored)` ([public/js/book/plot/constants.js](../public/js/book/plot/constants.js), unit-getestet [tests/unit/plot-beat-anchor.test.mjs](../tests/unit/plot-beat-anchor.test.mjs)) → Badge pro Beat-Karte (`beatAnchorState`/`beatAnchorTip` in [derived/board.js](../public/js/book/plot/derived/board.js), Markup in [plot-beat-cell.html](../public/partials/plot-beat-cell.html); das Badge ist eine reine Plakette, die Legende steht im Tooltip des Anker-Knopfs und in `plot.help.anchor`). `anchored` liefert `beatAnchorKnown(beatAnchor, beats)`: primär `beatAnchor.ranAt`, ohne das Feld die Heuristik „mindestens ein Beat trägt eine Fundstelle". Der Board-Payload liegt im State `beatAnchorInfo`; das Buchübersichts-Tile ([book-overview/plot.js](../public/js/book-overview/plot.js)) wendet dieselbe Regel an.

| status | Fundstellen | Zustand | Bedeutung |
|--------|-------------|---------|-----------|
| `im_buch` | > 0 | `confirmed` (grün) | passt — als eingearbeitet markiert **und** im Text gefunden |
| `im_buch` | 0, verankert | `drift` (rot) | **Warnung:** als eingearbeitet markiert, aber im Text nicht auffindbar |
| `im_buch` | 0, nie verankert | `none` | unbekannt — kein Badge |
| `geplant` | > 0 | `promote` (amber)  | offenbar schon geschrieben (starker Textbeleg ≥ `promote_min_score`) → Vorschlag „Als im Buch markieren" |
| `geplant` | 0   | `none`             | kein Badge |
| verworfen | –   | `none`             | kein Badge |

Klick auf `confirmed` **oder `promote`** öffnet das **Fundstellen-Popover** (siehe oben); `drift` ist nicht navigierbar. Bei `promote` trägt das Popover zusätzlich einen Fuss mit der Aktion **„Als im Buch markieren"** (`promoteBeat` → `PATCH /plot/beats/:id { status:'im_buch' }`; der Autor prüft die Fundstellen darüber selbst, `occ_count`/`occ_top` werden lokal übernommen, damit das Badge sofort von `promote` auf `confirmed` wechselt statt auf `drift` zu fallen). **Derselbe Index erdet die Consistency-Prüfung** (`anchorContext`, siehe oben) — die KI-Befunde werden dort an echten Textstellen festgemacht statt am extrahierten Szenen-Index. Der „Verankerung aktualisieren"-Knopf im Card-Header (`runBeatAnchor` in [ai.js](../public/js/book/plot/ai.js)) hebt sich hervor, wenn der Ist-Index veraltet ist; ohne aktive semantische Suche (`anchorSemanticActive()` via `/config`) läuft nur der wörtliche Fallback (Tooltip weist darauf hin). Job-Label `job.label.beatAnchor`, Status `job.phase.beatAnchor`.

## Zeit-Messung (deterministisch, kein KI-Call)

Pendant zur Motiv-Messung und zur Bogen-Messung der Figuren-Werkstatt: pure Rechnung in [lib/plot-time-consistency.js](../lib/plot-time-consistency.js), Befunde tragen `quelle: 'messung'`. Angezeigt wird sie im Beat-Board als Panel **Zeit-Messung** unter dem Board, getrennt vom KI-Urteil (`GET /plot/time-check`, Frontend [time-check.js](../public/js/book/plot/time-check.js)); nachgeladen mit jedem Board-Load und nach jeder Beat-Mutation (Speichern, Löschen, Umsortieren — die Reihenfolge ist die Achse der Chronologie-Prüfung). Das Panel erscheint nur, wenn es Befunde gibt: ein undatierter Beat ist ungeprüft, kein Mangel.

**Reihenfolge pro Lane:** die Route ordnet die Beats über `beatsInReadingOrder` ([lib/plot-reading-order.js](../lib/plot-reading-order.js), siehe Pflicht-Invarianten); jeder Beat trägt sein Feld `lane`, und `chronologieBruch` vergleicht nur innerhalb einer Lane — parallele Stränge sind kein Rückschritt. **Beteiligte Figuren:** die explizit verlinkten Katalog-Figuren plus die geerbte Katalog-Hauptfigur des Strangs (Live-Vererbung). Werkstatt-Figuren fehlen bewusst — sie haben kein Geburtsjahr. Geburtsjahre kommen schlank über `listFigureIdentities` + `computeFigureYears` ([lib/figure-years.js](../lib/figure-years.js)).

**Why hier und nicht im KI-Check:** „Beat spielt 1987, Figur X ist laut Geburtsjahr dann acht" ist eine Subtraktion, kein Urteil. Ein Modell danach zu fragen kostet Geld und liefert eine Aussage, die niemand nachrechnen kann; hier ist sie reproduzierbar und gratis. Der KI-Check bekommt dafür den Prüfpunkt, den eine Rechnung *nicht* leisten kann — ob die **Zeitsprünge** zu dem passen, was dazwischen geschieht (eine Schwangerschaft braucht ihre Zeit, ein Streit nicht zehn Jahre) — und die ausdrückliche Anweisung, **nicht** nachzurechnen.

Vier Codes:

| Code | Schwere | Aussage |
|---|---|---|
| `beatVorGeburt` | kritisch | Der Beat spielt, bevor eine beteiligte Figur geboren ist — ein Rechenfehler im Plan |
| `figurKindImBeat` | mittel | Die Figur ist zur Beat-Zeit unter zwölf; die Meldung nennt die Zahl und überlässt die Bewertung der Autorin |
| `chronologieBruch` | mittel | Innerhalb einer Lane läuft das Board vorwärts, die Jahreszahlen rückwärts |
| `zeitAusserhalbBuch` | schwach | Der Beat liegt ausserhalb der datierten Buchspanne |

Pflicht-Invarianten: **undatiert ist ungeprüft, nicht falsch** (ein Beat ohne `zeit` erzeugt keinen Befund — die Angabe ist optional und ihr Fehlen kein Mangel); **verworfene Beats zählen nicht** (sie sollen nicht ins Buch, ihre Chronologie ist keine Aussage über das Werk); und der Chronologie-Bruch misst gegen das bisherige **Maximum**, nicht den direkten Vorgänger — sonst erzeugt eine einzelne Rückblende eine Kette von Folgefehlern, obwohl nur ein Beat aus der Reihe fällt. Eine Rückblende ist ein legitimes Mittel; darum `mittel` statt `kritisch`, und darum nennt der Befund beide Beats, statt eine Korrektur zu behaupten. Gegated: [tests/unit/plot-time-consistency.test.mjs](../tests/unit/plot-time-consistency.test.mjs).

## Frontend-Card

Sub-Komponente `plotCard` ([public/js/cards/plot-card.js](../public/js/cards/plot-card.js)), Methoden in [public/js/book/plot.js](../public/js/book/plot.js) (`plotMethods`). Buchebenen-Karte, exklusiv (`EXCLUSIVE_CARDS`-Eintrag in [feature-registry.js](../public/js/cards/feature-registry.js), `flag: showPlotCard`, `toggle: togglePlotCard`, `onReclick: refresh`).

**Lifecycle:** `setupCardLifecycle({ name:'plot', showFlag:'showPlotCard', onShow: loadSortable + loadBoard, onBookChanged: reset+reload, onViewReset: resetPlot, onCardRefresh: loadBoard })` — **ohne** `timerKeys`: die drei Poll-Timer (Brainstorm, Consistency, `_anchorPollTimer`) räumt ausschliesslich `_clearJobs` ([ai.js](../public/js/book/plot/ai.js)) ab, aufgerufen von `resetPlot` und `destroy()`. **Why:** eine Quelle pro Timer; zwei Aufräumer für dieselben Timer driften.

**Konsistenz-Historie:** persistierte Läufe (`plot_consistency_runs`) als klappbarer Verlauf unter dem Consistency-Panel (`history-bar`-Pattern, `created_at DESC`, Konflikt-Anzahl- + Modell-Tag). `loadConsistencyRuns()` lädt die Liste mit `loadBoard()` (best-effort, eigenständig vom Board). `openConsistencyRun(runId)` holt das Detail lazy und legt `{ konflikte, fazit }` ins **bestehende** Consistency-Panel (`consistencyResult` + `selectedRunId`) — genau wie ein Live-Lauf; erneuter Klick auf den aktiven Eintrag schliesst es. Spiegelt das [Figuren-Werkstatt](figur-werkstatt.md#run-historie)-Run-Pattern, nur buch- statt draft-skopiert und ohne Live-Job-Reattach.

**Undo/Redo** ([public/js/book/plot/history.js](../public/js/book/plot/history.js), Pendant zum [Buchorganizer](buchorganizer.md)): zwei Icon-Buttons links im Card-Header (`plotHistoryUndo`/`plotHistoryRedo`, disabled aus `_undoStack`/`_redoStack`/`busy`) + Cmd/Ctrl+Z · Cmd/Ctrl+Shift+Z · Cmd/Ctrl+Y (`bindBoardHistoryKeys` aus [board-history-keys.js](../public/js/cards/board-history-keys.js), geteilt mit dem Buchorganizer, Griffe aus `matchHistoryCommand`; greift nur bei sichtbarer Karte, **nicht** wenn der Fokus in `INPUT`/`TEXTAREA`/`contenteditable` steht — dort gilt die native Edit-Undo-Funktion —, nicht bei offenem `<dialog>` und nicht, solange der Fokus im offenen Beat-Edit-Panel steht). Undo/Redo verwerfen einen offenen Beat-Entwurf nur, wenn auf dem Stack wirklich etwas liegt. Ein Record, dessen Applier scheitert, wird einmal zurückgelegt; scheitert er erneut (Ziel weg, z. B. 404), wird die Historie verworfen statt alle älteren Schritte zu versperren. Max. 10 Records pro Stack (FIFO-Drop). Während ein Undo/Redo fliegt, steht `busy` (Buttons gesperrt, schreibende Methoden kehren früh zurück); `_historyEpoch` zählt jedes Leeren der Historie hoch — leert ein Applier sie (z. B. über einen `loadBoard`-Rollback), legt der Flight seinen Record nicht auf einen Stack zurück, den es nicht mehr gibt.

Jeder Record trägt `before` **und** `after`, dieselbe Struktur bedient Undo und Redo:

| Record | Auslöser | Applier |
|---|---|---|
| `beat-place` | Drag & Drop + Verschieben ohne Drag (beide `_dropBeat`) | `_hApplyPlacements` → `PUT /plot/beats/order` |
| `beat-fields` | `saveEditBeat`, `toggleBeatVerworfen`, `promoteBeat`, Status-Aktion eines Befunds | `PATCH /plot/beats/:id` |
| `act-fields` | `saveEditAct`, `setActColor`, `toggleActArchive` | `PATCH /plot/acts/:id` |
| `act-order` | `moveAct` (pro Scope) | `PUT /plot/acts/order` |
| `thread-fields` | `saveEditThread`, `setThreadColor` | `PATCH /plot/threads/:id` |
| `thread-order` | `moveThread` | `PUT /plot/threads/order` |
| `create-beat\|act\|thread\|relation` | jedes Anlegen (inkl. `applyBrainstorm`) | `DELETE` des Erzeugten, danach Redo-Stack leer |

**Nicht abgedeckt** (und darum `_clearHistory()`): jedes Löschen (Beat/Akt/Strang/Beziehung — Hard-Delete ohne Content-Snapshot, ein Wiederanlegen vergäbe eine neue ID und ältere Records zeigten ins Leere), Fork/Unfork der Aktstruktur (act_id-Remap über viele Beats) und jeder `loadBoard()` (kann fremde Änderungen mitbringen). `resetPlot` leert die Stacks mit.

**Vollbild:** Icon-Button (`maximize-2`/`minimize-2`) im Card-Header → `togglePlotFullscreen()` setzt die ganze Karte (`$root` = `.card--plot`) per Native-Fullscreen-API auf den Viewport, damit das horizontal scrollende Board mehr Platz für alle Akte hat. Status `plotFullscreen` wird vom `fullscreenchange`-Listener (`attachFullscreenSync` aus [public/js/fullscreen.js](../public/js/fullscreen.js), abgemeldet via Lifecycle-`signal`) gespiegelt; Die Vollbild-Hülle kommt aus `.fullscreen-shell` ([components/fullscreen-shell.css](../public/css/components/fullscreen-shell.css)), die Spalten-Regeln im Vollbild (`.card--plot:fullscreen .plot-column`) aus [plot/board.css](../public/css/book/plot/board.css). Esc beendet (Browser-nativ).

**Invariante — was im Vollbild sichtbar sein soll, muss im Karten-Teilbaum hängen:** im Native-Vollbild rendert nur der Teilbaum des Fullscreen-Elements über dem `::backdrop`; alles darunter (also jedes `<body>`-Kind) liegt dahinter und ist unsichtbar. Darum teleportieren **beide** Popover der Karte nach `.card--plot` statt nach `body` — das Fundstellen-Popover ([plot-anchor-popover.html](../public/partials/plot-anchor-popover.html)) und das Strang-Aktionsmenü ([plot-thread-menu.html](../public/partials/plot-thread-menu.html), per Fragment-Include im Grid); `position: fixed` bleibt trotzdem viewport-verankert, weil die Karte keinen Containing-Block etabliert (die `cardFadeIn`-Animation läuft mit `backwards`, lässt also keinen Transform stehen). Denselben Grund hat das Umhängen des SortableJS-Fallback-Ghosts in [dnd.js](../public/js/book/plot/dnd.js) (`relocateGhostForFullscreen`). Neues teleportiertes Element in der Karte ⇒ gleiches Ziel. Gilt gleichermassen für jede andere Karte mit Native-Vollbild (Motiv-Werkstatt: Graph-Kontextmenü → `.card--motiv`). Gegated durch [tests/e2e-app/fullscreen-popover-anchoring.spec.js](../tests/e2e-app/fullscreen-popover-anchoring.spec.js) — Karten-Liste dort erweitern, wenn eine weitere Vollbild-Karte ein Popover teleportiert.

## Swimlanes (Akte × Stränge)

**Render-Weiche:** beide Boards liegen als Geschwister im Card-Root, je `x-show`. [plot-board-flat.html](../public/partials/plot-board-flat.html) (`x-show="(acts.length || addingAct) && !threads.length"`) ist das **unveränderte** flache Akt-Board; [plot-board-grid.html](../public/partials/plot-board-grid.html) (`x-show="threads.length"`) das Raster. [plot.html](../public/partials/plot.html) ist nur der Rahmen (Header/Progress/Filter/Coverage) + nested-Partial-Placeholder (`partial-plot-tension`, `partial-plot-thread-bar`, `partial-plot-board-flat`, `partial-plot-board-grid`, `partial-plot-anchor-popover`, `partial-plot-ki-runs`, `partial-plot-chat`), gefüllt via `_loadPartials`-Cascade. Ausgelagert (File-Limit): der Spannungsbogen in [plot-tension.html](../public/partials/plot-tension.html), die KI-Konsistenz-Panels + Lauf-Historien (Konsistenz + Brainstorm) in [plot-ki-runs.html](../public/partials/plot-ki-runs.html). Innerhalb von `<template>`-Blöcken greifen stattdessen Fragment-Includes: `plot-beat-cell` (in beiden Boards) → `plot-beat-edit` → `plot-beat-move`, und `plot-thread-menu` (im Grid).

**Geteiltes Beat-Markup (SSoT):** die Beat-Karte (Ansicht + Bearbeiten) lebt **einmal** in [plot-beat-cell.html](../public/partials/plot-beat-cell.html) und wird in beide Boards per **string-seitigem Fragment-Include** `<!-- @include plot-beat-cell -->` eingebettet ([app-ui.js](../public/js/app/app-ui.js)#`_resolveIncludes`, vor `innerHTML`/`Alpine.initTree`). Anders als der DOM-Placeholder-Mechanismus (`<div id="partial-X">`) greift das auch **innerhalb** von `<template>`/`x-for` (querySelector steigt nicht in Template-Content ab). Das Fragment erwartet im Scope die `beat`-Loop-Variable + den plotCard-State; der umschliessende `.plot-beat`-Wrapper inkl. DnD-Handler bleibt pro Board-Datei (flach vs. Zelle unterscheiden sich). **Neue Beat-Felder → nur in `plot-beat-cell.html` pflegen** (kein Doppel-Edit mehr).

**Zeilen (Hybrid-fähig):** Das Grid rendert eine **flache Liste von Zeilen-Deskriptoren** aus `gridRows()` (eine `x-for`-Schleife, je Deskriptor ein Header- ODER Lane-Block; `display:contents`-Wrapper `.plot-swim-rowgroup`, damit Zeilen direkte Flex-Kinder von `.plot-swim` bleiben). Aufbau: (1) **geteilte Region** — ein Header über `sharedActs()` + alle Lanes ohne eigene Akte (Stränge **und** „ohne Strang"); ihre Spalten richten sich aus. (2) Pro Strang **mit eigener Aktstruktur** (`threadHasOwnActs`) ein **eigener** Header über `actsForThread(id)` + seine Lane darunter — eigene Spaltenzahl, bewusst nicht ausgerichtet. Da das Layout per Flexbox arbeitet (kein CSS-Grid mit fixem `--act-count`), tragen Zeilen unterschiedlicher Spaltenzahl problemlos nebeneinander. Cells weiterhin aus `filteredBeatsForCell(actId, laneId)`. Weil `gridRows` die Beat-Zell-Markup-Stelle EINMAL führt (Lane-Deskriptor mit `row.acts`), bleibt trotz Hybrid nur **eine** Zell-Kopie im Grid-File (+ die Flat-Kopie). Horizontaler Scroll via `min-width: max-content`. CSS: [plot/swimlane.css](../public/css/book/plot/swimlane.css).

**Eigene Aktstruktur (Fork-Toggle):** ein Eintrag im Strang-Kebab-Menü ([plot-thread-menu.html](../public/partials/plot-thread-menu.html)) → `forkThreadActs(thread)` (noch geteilt) bzw. `unforkThreadActs(thread)` (schon eigen). Beide bestätigen via `appConfirm`, rufen `POST`/`DELETE /plot/threads/:id/fork-acts` und laden danach das Board neu (`loadBoard` — der act_id-Remap betrifft viele Beats, lokales Spiegeln wäre fehleranfällig). Scoped **Akt hinzufügen** pro Header (`addingActScope`: `false`=aus, `null`=geteilt, `<threadId>`=strang-eigen) → `addActScoped`. `moveAct` reordert **innerhalb des Scopes** (`act.thread_id`), der andere Scope bleibt unberührt.

**Strang-Anlegen:** [plot-thread-bar.html](../public/partials/plot-thread-bar.html) („+ Strang", sichtbar sobald Akte existieren) — der Opt-in-Einstieg. **Strang-Management** (umbenennen/färben/verschieben/binden/löschen) erreicht man über das Kebab-Menü im Lane-Label des Grids ([plot-thread-menu.html](../public/partials/plot-thread-menu.html), `openThreadMenu` in [threads.js](../public/js/book/plot/threads.js)): `addThread`/`saveEditThread`/`setThreadColor`/`moveThread`/`deleteThread`. Figuren-Bindung exklusiv (Katalog **oder** Werkstatt) über zwei Comboboxen im Lane-Edit; `threadDraft.figure_id` führt die TEXT-`fig_id`, `threadDraft.draft_figure_id` die INTEGER-`draft_figures.id`. Kapitel-Bindung über eine dritte Combobox (`threadDraft.chapter_id`, Optionen aus `$app.tree`-Kapiteln). `deleteThread` spiegelt den Server-SET-NULL lokal (Beats fallen in die „ohne Strang"-Lane, werden nicht gelöscht); hatte der Strang eigene Akte, lädt es stattdessen das Board neu (`loadBoard` — der Server hängt die Beats auf geteilte Akte um, lokal nicht verlässlich nachzubauen).

**Live-Vererbung im Grid:** `inheritedFigureForBeat(beat)` / `inheritedChapterForBeat(beat)` (in [derived/board.js](../public/js/book/plot/derived/board.js)) liefern die vom Strang geerbten Werte für die Beat-Anzeige — geerbte Figur nur, wenn nicht schon explizit am Beat; geerbtes Kapitel nur, wenn der Beat kein eigenes `chapter_id` hat. Gerendert als Entitäts-Referenzen mit `inherited: true` neben den expliziten: gleiches Label, Zusatz „· Strang“, gestrichelter Rand. Lane-Label zeigt die gebundene Figur **und** das gebundene Kapitel (`lane.thread.chapter_name`) als Referenzen. Rein Anzeige — nichts davon wird je auf den Beat geschrieben.

**2D-DnD:** flaches Board und Grid nutzen dieselbe SortableJS-Anbindung — jede Beat-Zelle (`.plot-beats[data-plot-cell]`) trägt `data-act-id` + (im Grid) `data-thread-id` (leer = „ohne Strang"). `onBeatSortEnd` liest beide aus der Ziel-Zelle und ruft `_dropBeat(actId, threadId, beforeBeatId)` — setzt `act_id` + `thread_id`, nummeriert Ziel- + Quell-**Zelle** neu, persistiert via `_persistCells` → `PUT /plot/beats/order` mit `{actId, threadId, beatIds}`-Gruppen. Fehler → `loadBoard()`-Rollback. **Leere Grid-Zellen als Drop-Ziel:** im Ruhezustand kollabieren leere Zellen auf `min-height: 0` (kein Leerraum). Während eines Drags setzt `dnd.js` die Klasse `plot-dnd-active` + die Custom-Prop `--plot-drag-h` (Höhe der gezogenen Karte) auf `<body>`; die Swimlane-CSS bläht dann **jede** Zelle auf diese Höhe auf — bewusst ohne `:not(:has())`, damit die Zielzelle nicht auf Ghost-Höhe schrumpft, sobald der Ghost eindringt (sonst fällt der Cursor aus der Trefferzone → Beat springt beim Loslassen zurück). Nach dem Drag kehren die Zellen zur kompakten Höhe zurück.

**Spannungsbogen:** `tensionCurve()` liefert weiterhin die globale `points`/`polyline`/`count` (Board ohne Stränge) **plus** `series[]` (pro Strang eine farbige Polyline, dazu eine Serie „ohne Strang" mit key `'tnone'`, damit nicht zugeordnete Beats nicht aus dem Bogen fallen). Template rendert `series` wenn Stränge existieren, sonst die globale Kurve.

## Cross-Feature: Figuren-Werkstatt

Plot und [Figuren-Werkstatt](figur-werkstatt.md) befruchten sich gegenseitig — beide rein planend, nie generativ:

- **Psychologie im KI-Kontext** (s.o.): die Werkstatt-Mindmaps (Want/Need/Wound/Lie + Bogen + Konflikt) fliessen in Brainstorm + Consistency, damit Beats den inneren Konflikt der Figur bedienen.
- **`figurePlotUsage(bookId, userEmail, { draftFigureId, sourceFigureId })`** ([db/plot/figure-usage.js](../db/plot/figure-usage.js)) — Beats, an denen eine (Werkstatt-)Figur beteiligt ist (direkt verlinkt **oder** als Strang-Hauptfigur, Live-Vererbung) + die gebundenen Stränge. Lesefertig angereichert (Akt, Strang, effektives Kapitel, Status, Intensität), in Board-Lesereihenfolge; alle JOINs auf (Buch, User) skopiert. Speist die Werkstatt-Jobs (umgekehrte Richtung: „Figurenbogen ↔ geplante Handlung") **und** die `/figure-usage`-Route.
- **Figur-Filter mit Vererbung:** `_beatMatchesFilter` (Katalog **und** Werkstatt) trifft auch Beats, deren Strang die Figur als Hauptfigur bindet (`_beatInvolvesCatalog`/`_beatInvolvesDraft`) — dieselbe Beat-Menge wie das Badge. `applyDraftFigureFilter(draftId)` (Event `plot:filter-draft-figure`) ist der Landepunkt der Navigation Werkstatt → Plot.
- **Neue Filter-Achse = drei Stellen, sonst wirkt sie nicht:** `_beatMatchesFilter` (der Chokepoint, den beide Boards + der Zähler + der Verworfen-Collapse durchlaufen), `plotFilterActive()` (ohne Eintrag reicht der ungefilterte Array durch, wenn sonst kein Filter steht) **und** die Deps-Arrays der drei `_memo`-Aufrufe in [coverage.js](../public/js/book/plot/derived/coverage.js) (`fbeats`/`fcount`/`fcell` — ohne sie friert das Ergebnis ein). ## Kapitelbewertung: geplante Handlung als Kontext

## Weltgesetze als Prüfstein (Consistency)

Die Consistency-Prüfung bekommt zusätzlich die **Weltgesetze** des Buchs: `world_facts` der Kategorien `regel` + `technik` ([routes/jobs/plot/context.js](../routes/jobs/plot/context.js)#`weltgesetzeContext` → [prompts/plot/lines.js](../public/js/prompts/plot/lines.js)#`_weltgesetzeLines`, Cap über `ctxLimits().weltgesetze`, Befund-Typ `weltgesetz`).

**Why:** Szenen, Kapitel und Textbelege prüfen den Plan gegen das, was GESCHRIEBEN ist. Ein Beat, der gegen eine etablierte Regel der Welt verstösst («die Tote erscheint», «er telefoniert 1890»), wäre damit strukturell unentdeckbar: er widerspricht keinem Text, sondern dem Weltmodell.

Drei Regeln:
- **Nur `regel`+`technik`** — nur sie sind etwas, wogegen ein Plan verstossen kann; die übrigen Kategorien sind Aussagen über die Welt, und Fakt-gegen-Fakt prüft die Kontinuität.
- **Kein Index ⇒ kein Block und kein Prüfpunkt** (gleiches Muster wie `anchorMap === null`): ein nie erhobener Fakten-Index heisst „unbekannt", nicht „regelfreie Welt".
- **Der bewusste Regelbruch ist kein Befund** — und die Regeln sind KI-extrahiert, nicht von der Autorin kuratiert; passt eine Regel erkennbar nicht, urteilt das Modell nicht dagegen.

## Pflicht-Invarianten

- **Nie generativ in den Text** — beide KI-Jobs liefern nur Struktur-Stichpunkte (Beats) bzw. Befunde, nie Prosa. Der System-Prompt erzwingt das explizit; bleibt bei Änderungen erhalten (App-Philosophie: KI rückwärtsgewandt/weltaufbauend, nie in den Buchtext schreibend).
- **`truncated` vor `parseJSON` prüfen + Pflichtfeld-Check** nach jedem `aiCall` (`vorschlaege`/`konflikte`/`fazit`) — sonst Partial-Daten. Bereits in [routes/jobs/plot.js](../routes/jobs/plot.js) umgesetzt.
- **Scoping `WHERE book_id = ? AND user_email = ?`** in jedem DB-Pfad — Plot (Akte, Stränge, Beats) ist pro Buch **und** User isoliert (kein geteilter Katalog).
- **Figuren-/Kapitel-/Strang-/Motiv-Refs validieren** (`resolveFigureIds`/`resolveDraftFigureIds`/`resolveLocationIds`/`resolveMotifIds`/`_validChapterId`/`_validThreadId`) vor jedem Write — keine Fremd-Verweise in den M:N-Tabellen (inkl. `plot_beat_locations` und `motif_beats`), in `chapter_id`, `thread_id` oder der Strang-Figuren-Bindung. Katalog- und Werkstatt-Figuren sind getrennte Brücken (`fig_ids` = TEXT-`fig_id`, `draft_fig_ids` = INTEGER `draft_figures.id`); Frontend hält sie in `beatDraft.figure_ids` vs. `beatDraft.draft_figure_ids` getrennt.
- **Null Stränge = flaches Board (byte-gleich)** — das flache Akt-Board ([plot-board-flat.html](../public/partials/plot-board-flat.html)) bleibt unverändert; die Swimlanes sind opt-in (`thread_id`/`plot_threads` rein additiv).
- **Lückenlose Nummerierung** — `sort_order` ist **pro Zelle** (`act_id` + `thread_id`) und Akt-`position` **pro Scope** (geteilt bzw. je Strang) immer `0..n-1`. Hergestellt in der DB-Schicht ([db/plot/structure.js](../db/plot/structure.js)#`_renumberCell`/`_renumberActScope`) nach jedem Pfad, der eine Lücke reissen kann: `deleteBeat`, Zellwechsel per `PATCH` (Beat ans Ende der Zielzelle, Quellzelle neu), `PUT /beats/order` (Ziel- und verlassene Quellzellen), `deleteThread` (Strang-Beats **hinter** die vorhandenen „ohne Strang"-Beats), `deleteAct` und Teil-Listen in `PUT /acts/order`. **Why:** DnD, „oben/unten" und das optimistische Frontend rechnen mit Indizes; eine Lücke oder ein Doppel-Slot lässt Beats beim nächsten Drop springen.
- **Alles-oder-nichts-Reorder** — `PUT /beats/order` und `PUT /acts/order` prüfen den kompletten Payload in der Transaktion, **bevor** sie schreiben; jeder Verstoss (`ORDER_INVALID`, `ACT_MISMATCH`, `ACT_THREAD_MISMATCH`, `ACT_SCOPE_MIXED`) rollt alles zurück (Details: Validierung). **Why:** ein halb geschriebener Reorder hinterlässt ein Board, das weder dem alten noch dem gewünschten Stand entspricht — und der Frontend-Rollback (`loadBoard`) zeigte dann diesen Mischzustand als Wahrheit.
- **Strang löschen ≠ Beats löschen** — `plot_beats.thread_id` ist `SET NULL`; gelöschte Stränge entkoppeln nur, die Beats fallen in die „ohne Strang"-Lane. **Auch bei eigener Aktstruktur:** `deleteThread` hängt die Beats strang-eigener Akte VOR dem Löschen auf die geteilten Akte um (`_landThreadBeatsOnSharedActs`), bevor `plot_acts.thread_id`-CASCADE die eigenen Akte entfernt — sonst würden die Beats mit-kaskadieren. Gibt es keine geteilten Akte, werden die eigenen stattdessen zu geteilten **befördert** (kein Beat-Verlust).
- **Hybrid-Akt-Integrität** — ein Strang mit eigenen Akten liegt **nur** auf seinen eigenen Akten, ein Strang ohne eigene Akte und die „ohne Strang"-Lane **nur** auf geteilten. Eine Funktion, `plotDb.actFitsThread`, für alle Schreibpfade (Beat-Create, PATCH-Move, Reorder, Brainstorm-Route; `ACT_THREAD_MISMATCH`); strang-eigene Akte entstehen nur über `fork-acts` (`THREAD_NOT_FORKED`). `moveAct`/`reorderActs` sortieren nur innerhalb eines Scopes. „Eigene Akte" ist **abgeleitet** (Existenz strang-eigener Akte), nie als Flag persistiert.
- **Lesereihenfolge pro Lane** — „vorher/nachher" auf dem Board ist nur **innerhalb einer Lane** definiert. Verbindliche Regel in [lib/plot-reading-order.js](../lib/plot-reading-order.js) (`laneReadingOrder`, `beatsInReadingOrder`): Lane = Strang (nach `position`, `id`) oder „ohne Strang" (zuletzt); die Akte einer Lane = die eigenen Akte des Strangs (nach `position`), falls er welche hat, sonst die geteilten; Beats nach Akt-Rang, dann `sort_order`, dann `id`. Spiegel: Frontend `beatReadingOrder` ([constants.js](../public/js/book/plot/constants.js); Spannungsbogen, Plan-Reiter) und Prompt `plotReadingBlocks` ([prompts/plot/board.js](../public/js/prompts/plot/board.js)), Drift gegated in [tests/unit/plot-prompt-substance.test.mjs](../tests/unit/plot-prompt-substance.test.mjs). Konsumenten: Zeit-Messung, KI-Kontext, `figurePlotUsage`. **Why:** geforkte Stränge haben eigene Positions-Sequenzen; eine globale Ordnung nach „Akt-Position" setzte Akt 2 von Strang A mit Akt 2 der geteilten Struktur gleich und verzahnte Erzähllinien, die zeitlich nichts miteinander zu tun haben — die Zeit-Messung meldete dann Chronologie-Brüche zwischen parallelen Strängen.
- **Beat-Kanten sind gerichtet + fremdverweis-sicher** — `plot_beat_relations` speichert `from_beat_id --typ--> to_beat_id`; `createBeatRelation` validiert beide Beats aufs (Buch, User)-Subset, verbietet Selbst-Kanten und ist via `UNIQUE(from, to, typ)` idempotent. Beim Beat-Löschen kaskadieren die Kanten (DB) und werden lokal nachgezogen. Read-only im Board, kuratiert nur im Beat-Edit, **nie generativ** — die KI liest sie im Consistency-Check, schreibt sie nie.
- **Consistency-Befunde matchen primär per `beat_id`** — der Board-Outline trägt `[#<id>]`-Marker, das Schema-Feld `beat_id` + der `_konfliktIndex.byId`/`byTitle`-Split lassen einen Befund seinen Beat auch nach Umbenennung finden (Titel nur Fallback, und nur ein eindeutiger). Persistierte Alt-Läufe ohne `beat_id` bleiben über den Titel-Fallback kompatibel.
- **Verankerung: `geplant`-Promotion nur oberhalb `promote_min_score`** — `im_buch`-Beats verankern Treffer ab `confirm_min_score` (Drift), `geplant`-Beats nur starke (Promotion-Vorschlag); die Schwellen greifen beim Speichern (nicht beim Lesen), sonst flutet das Board. `promote_min_score = 0` schaltet die Promotion ganz aus (dann werden geplante Beats nicht gescannt und zählen nicht für die Stale-Heuristik).
- **Anker-Score = Cosinus** — gespeichert, gefiltert (`confirm_min_score`, `promote_min_score`, Lesefilter `min_score`) und angezeigt wird ausschliesslich der rohe Cosinus `semScore`; FTS-Fusionskandidaten ohne Cosinus zählen nicht als semantischer Beleg. **Why:** der fusionierte Retrieval-Score ist rang- bzw. rerank-relativ — gegen ihn wäre jede absolute Schwelle bedeutungslos (eine Admin-Schwelle von 0.45 träfe nie oder immer).
- **Nie verankert = unbekannt, nicht Drift** — ohne je gelaufene Verankerung (`beatAnchor.ranAt = null`) zeigt ein `im_buch`-Beat ohne Fundstelle **kein** rotes Drift-Badge (Board **und** Buchübersichts-Tile, beide über `beatAnchorKnown`), genau wie `anchorContext` einen leeren Index als „nie gescannt" behandelt. Ein Lauf mit 0 Fundstellen zählt dabei als gelaufen (`job_runs`). **Why:** sonst stünde nach dem Anlegen eines Boards jeder eingearbeitete Beat als Warnung da, obwohl niemand gesucht hat.
- **Undo/Redo zeichnet erst nach dem Server-OK auf, und der Gegen-Stack erst nach dem Flight** — ein Record entsteht nur, wenn die Mutation persistiert wurde (`_persistCells` liefert dafür `true`/`false`; bei `false` läuft der `loadBoard`-Rollback, der die Historie leert). `_pushUndo` verwirft Records, solange `_inHistoryFlight` steht — das verhindert, dass ein Applier sich selbst aufzeichnet, weshalb `plotHistoryUndo`/`-Redo` den Gegen-Stack **ausserhalb** des try/finally beschreiben; innerhalb aufgezeichnet, wäre nach einem Redo nichts mehr rückgängig zu machen. Die `_h*`-Applier sprechen die Routen direkt an und rufen **nie** die interaktiven Methoden (die zeichnen selbst auf). Neue Mutations-Methode ⇒ entweder `_record*` (reversibel), `_clearHistory()` (nicht reversibel) oder `loadBoard()` (leert selbst) — nichts stillschweigend auslassen, sonst macht ein Undo den Board-Stand inkonsistent statt ihn zurückzudrehen. **Tripwire:** [tests/unit/plot-history.test.mjs](../tests/unit/plot-history.test.mjs) durchsucht die Methods-Module im Quelltext — jede Methode, die `/plot` schreibend anspricht, muss einen dieser drei Aufrufe enthalten, sonst wird der Test rot.
- **Befund-Aktionen sind serverseitig validiert und laufen über die normalen Wege** — eine `aktion` erreicht die UI nur, wenn `normalizeAktion` sie für gültig und wirksam befunden hat (Beat auf dem Board, Ziel existiert und ist nicht der Beat selbst, kein No-op, keine Status-Aktion auf einem verworfenen Beat). Ausgeführt wird sie ausschliesslich über `PATCH` + `_recordBeatFields`, `toggleBeatVerworfen` bzw. `addBeatRelation` — dieselben Undo-Records wie die Handbedienung, kein eigener Schreibpfad. **Why:** ein KI-Vorschlag, der per Klick ausgeführt wird, darf weder ins Leere greifen noch an Undo und Validierung vorbeischreiben.
- **Vererbung ist live, nie persistiert** — die vom Strang geerbte Hauptfigur/Kapitel werden NIE auf den Beat geschrieben (keine `plot_beat_figures`-Einträge, kein `plot_beats.chapter_id`). Sie entstehen erst zur Lese-/Render-/Prompt-Zeit aus der aktuellen Strang-Bindung. Beat-Vorrang: eigene Beat-Figuren sind additiv, eigenes Beat-`chapter_id` überschreibt das Strang-Kapitel. So folgt der Beat automatisch, wenn die Strang-Bindung wechselt.
- **Kapitel-Kontext nur über die Content-Store-Facade** (`loadOrderedBookContents`), kein Direkt-SQL auf `chapters`/`pages`/`books`.
